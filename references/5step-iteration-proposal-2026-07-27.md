## 二、发现的 4 个结构性缺陷

### 缺陷 1：执行→审查之间无自检闸门

R1 的 8 项 FAIL 中，5 项是写完就能自查出来的：
- composite 加权没重算
- 定投映射没对照契约（写了 30% 而非"暂停"）
- D4.4 阈值没对照契约（写了 ±5% 而非 ±10%）
- 术语混用（"折价"同时指代两个不同概念）
- 新闻振幅与当前价格矛盾（$4,022-$4,082 vs $4,111）

→ **如果③后有一个 5 项自查清单，R1 可以从 8 FAIL 降到 3 FAIL。**

### 缺陷 2：审查层串行浪费轮次

当前流程：L1 跑完 → Opus 跑。Opus 在 L1 跑 4 轮期间干等着。

如果 L1 和 Opus **同时**看到初版交付物，Opus 第一轮就会指出"通缩 vs 油价"矛盾——这个问题涉及的术语修正会同时影响 L1 的审查，L1 就不需要在 R2/R3 反复因为用词问题 FAIL。

→ **L1 ‖ Opus 并行可省 2 轮。**

### 缺陷 3：D5 投递确认是结构性死锁

契约："未确认投递成功不得标记任务完成"
现实：审查发生在投递之前，L1 每轮都 FAIL D5
结果：L1 4 轮都无法 PASS——不是交付物有问题，是审查时机有问题

→ **D5 应标记为"投递后验证项"，审查阶段自动跳过。**

### 缺陷 4：3 轮上限无硬约束

契约写了"每层最多 3 轮，第 4 轮前停下告知用户"。实际：Agent 在第 3 轮 FAIL 后直接跑了第 4 轮。规则靠自觉 = 不靠谱。

→ **qwen_review.py 需内置轮次计数器，≥3 时拒绝执行。**

## 三、改进方案

```
改进前:  ①→②→③→④(L1串行→Opus)→⑤

改进后:  ①→②→③→③.5(自检闸门)→④(L1‖Opus并行)→⑤
                              D5跳过审查
```

| # | 改进 | 优先级 | 改动范围 | 预期效果 |
|:--|:--|:--|:--|:--|
| A | ③.5 自检闸门（5项必查） | **P0** | sprint-contract + 自查脚本 | 减少 60% R1 FAIL |
| B | D5 审查跳过 | **P0** | sprint-contract 契约模板 | 消除结构性死锁 |
| C | L1 ‖ Opus 并行 | **P1** | task-wrapup skill 审查步骤 | 减少 2-3 轮审查 |
| D | 轮次硬约束 | **P2** | qwen_review.py | 防止超限 |

### A. ③.5 自检闸门（5 项必查清单）

```
□ composite 加权重算对表（不等于 scorer 输出就修正并注明差异）
□ 定投映射逐字对照契约口径（<40→暂停，不是 30%）
□ D4 每项阈值对照契约原文（不是凭记忆写）
□ 术语表对照（"境内外价差"≠"公允价值偏离"≠"折价"）
□ 数据源真实性（SGE 用实盘不用换算值；跨源验证不可同源）
```

嵌入 `sprint-contract` 步骤 3 和步骤 4 之间。全部打勾才能进入审查。

### B. D5 审查跳过

契约模板中 D5 验收标准改为：
```
D5 投递确认 | 投递后验证项（审查阶段跳过）。投递时确认消息发送回执，
              失败重试并向用户报告。验收时机：⑤ 复盘前。
```

`sprint-contract` 模板和 `contract-checklist.md` 同步修改。

### C. L1 ‖ Opus 并行

`task-wrapup` 步骤 3 改为：
```
3a. 同时启动 L1（qwen_review.py）和 Opus（claude -p --model opus）
3b. 合并审查结果，按问题严重性排序
3c. 统一修复 → 重审（每层独立 ≤3 轮）
```

投资分析类强制 +Opus，其他类可选。

### D. 轮次硬约束

`qwen_review.py` 启动时读 `reviews/review_log.jsonl`，统计同任务 ID 的 L1 裁决次数：
```
if l1_rounds >= 3:
    print("L1 已达 3 轮上限，拒绝执行。请升级 Opus 或通知用户。")
    sys.exit(2)
```

## 四、待 Opus 判断的问题

1. **P0 和 P1 的优先级是否合理？** 我的理由是：P0 改动小（两个模板修改），收益直接（消除死锁 + 减少低级错误）。P1 涉及 task-wrapup 流程重构，风险更大。但 P1 节省的轮次（2-3 轮）比 P0（1-2 轮）更多。

2. **③.5 自检闸门由谁执行？** 选项：Agent 自己逐条打勾（成本低但可能敷衍），还是用脚本自动检查（可靠但需要可脚本化的检查项）？自查清单中 composite 重算、阈值对照可以脚本化，术语一致性目前只能人工。

3. **L1 ‖ Opus 并行是否有风险？** 两个审查同时跑，合并结果时可能出现冲突（L1 说 PASS 的项 Opus 说 FAIL——以谁为准？）。我的初步想法：以更严格的为准，但需明确规则。

4. **是否遗漏了其他缺陷？** 比如 ② decision-gate 的打勾遗漏——是 Agent 的问题还是流程设计的问题？

请逐缺陷评估并给出改进建议。
