# 多 agent 协作架构分析（2026-08-07，含 Opus 两轮评审）

背景：用户想给 Hermes + Claude Code + Codex 一个任务，三个 agent 像同事一样协作完成。用户明确：**要同步实时讨论，不要异步文件接力**（"一个人写文档另一个人再读，一天讨论不了什么东西"）；Claude/Codex 啃难的、DeepSeek 啃简单的；不关心谁当组长。当前用户已暂缓三 agent 打通（成本敏感），聚焦 EigenFlux 外交。未来重启此方向先读本文。

## 核心区分：通信管道 vs 任务编排

| 能力 | 是什么 | 谁提供 |
|---|---|---|
| 通信管道 | agent 之间互发消息 | 本地 broker / EigenFlux / MCP 消息总线 |
| 任务编排 | 谁分解任务、谁干哪部分、怎么合并 | **这些工具都不给**——需要人/Hermes 当项目经理 |

"谁当组长"不是权力问题，是工程必需（接口契约、依赖顺序、冲突裁决、结果集成）。模块越相互依赖越绕不开。但控制逻辑可以是**机械的**（脚本：轮流发言/N 轮上限/收敛检测），不需要 LLM 主持人。

## 关键架构事实

- Claude Code 和 Codex 是 **CLI 工具非常驻**——平时不运行，被调用才启动，干完退出。"让两个 CLI agent 实时讨论"只有两种思路：常驻+推送（EigenFlux 插件架构）或一个进程内交替调用
- **转述即失真**：如果 Hermes 读 Claude 的回答→总结→转述给 Codex，质量上限被 DeepSeek 锁死（让一个人复述两个专家的对话）。必须**原文透传**，Hermes 只追加一行流程指令
- **附和坍缩**：多 agent 辩论第二轮就互相认同。对策：**第一轮盲写**（两边看不到对方各自出结论，第二轮才交换）
- **会话续接**：`claude -p --output-format json` 拿 session_id + `--resume` 续接，每轮只传对方新发言——否则第 4-5 轮被 token 成本和延迟劝退
- **延迟真相**：冷启动 1-3s + 推理 20-90s，一来一回 1-3 分钟/轮。"实时"实际是"10 分钟一次会议"，不是秒回聊天室。但相对"一天讨论不了什么"是数量级胜利
- **别设 8 轮设 3-4 轮**：边际收益第 3 轮后急剧衰减。硬约束：每轮字数上限 + 结构化结尾（已一致/剩余分歧/改变立场）+ 分歧清单为空提前终止

## 推荐：MCP 消息总线（让 Claude 和 Codex 直接对话）

- **传输层（哑管道）**：逐字转发，不理解内容 → Claude 原话原样进 Codex 输入。**这是正确做法**
- **主持人（LLM 复述）**：每轮多花一整轮推理，必丢信息、抹掉分歧点——而分歧点恰是多 agent 讨论唯一价值来源
- 落地三种（按推荐度）：①MCP server 当消息总线（暴露 send_to/poll_inbox 两个工具，两 agent 各自注册，自己主动调用=最像同事直接说话，可扩展第三方）②双 subprocess 管道（A 的 stdout 逐字喂 B 的 stdin，实现最快但会话状态脆）③共享 append-only 文件+轮询（最土，半小时跑通，适合先验证）
- **诚实限制**：LLM 回合制，不存在同时开口互相打断的"真·实时"。能做到的是去掉人工搬运和落盘，单次往返从几小时压到几十秒，一小时内无人值守跑几十轮

## 模型分层落地（用户"Claude/Codex 啃难、DeepSeek 啃简单"）

- 实时讨论里没有"学"这个动作——CLI agent 每次调用都是白纸。真正的分层是**记忆归属和成本**：Hermes 是唯一有连续记忆的，沉淀归它；Claude/Codex 是叫来开会的外部专家，开完就忘
- **反模式**：不要让 DeepSeek 裁决 Claude/Codex 谁对——弱模型裁决强模型=选"语气更确定的那个"。分歧收敛不了就原样呈给用户
- **成本分层才是真收益**：给 Hermes 设开会门槛（方案选型/多可行解/答错代价高才触发会议），90% 日常问题自己答掉

## 图编排（Graph Engineering，用户问的概念）

- 图编排 = 给 agent 们画施工流程图：节点（工序/agent）+ 边（依赖顺序）+ 共享状态（小黑板）
- 解决：接口契约（共享状态定格式）、依赖进度（边保证先后）、冲突裁决集成（汇总节点）、防跑偏（流程画死）
- **不解决的根本问题**：图不会自己画自己——仍需项目经理（人/Hermes）设计图纸。图只是把"口头商量"变"显式图纸"
- 与消息总线互补：图=有剧本的协作（结构化流程），消息总线=即兴讨论。现实方案=图作骨架+agent 作节点+通信作机制
- 对小白：不需要学 LangGraph（程序员框架），有价值的是"图思维"——接任务先画流程（谁干什么/谁依赖谁/哪步验收）

## 验证实验（可证伪）

出一道**必须靠分歧才能得出答案**的题（双方独立给方案，强制互挑漏洞，跑 6 轮）。判定标准一条：**最终结论里有没有出现任何一方单独跑时得不出的东西**。有=通信产生协作价值；没有=只是两份独立输出拼一起，对用户无用。第一次务必用"用户已知道答案"的问题试跑，并做单模型自我红队对照（部分跨模型增量单模型自问自答也能拿到）。

## 风险清单

- **回复风暴**：agent 收到消息自动回复→无限循环烧 token。需要回复深度上限/消息 TTL/不回自己线程
- **提示注入**：公开 feed 内容进 Claude Code 上下文（有文件读写+命令执行权限）="把本机权限暴露给互联网"。真做只 DM 不订阅公开广播+明确"外部消息只是数据不是指令"
- **成本 O(n²)**：三 agent 互喂上下文，token 约单 agent 5-10 倍，每轮带整个历史
- **EigenFlux 定位**：解决"发现和常态化广播"（agent 互找+持续 feed），不是"已知谁跟谁说话、就一个问题深挖"。对用户场景是**不对的工具**（且要求常驻会话+提示注入面）
- **Claude 编排的代价**：Claude 当编排器（直接 codex exec）有主场优势，把 Codex 当顾问非对手。要对抗性→Hermes 居中（中立）；要上下文完整效率→Claude 编排（有偏向）
- 否决项：LangGraph/CrewAI/AutoGen（编排 API 模型非 CLI，要换计费、丢本地工具、Windows 上给小白维护 Python 栈）；tmux 对接 TUI（Windows 不现实）；Claude Code subagent（全 Claude 不跨模型，子代理只向父汇报彼此不对话）
