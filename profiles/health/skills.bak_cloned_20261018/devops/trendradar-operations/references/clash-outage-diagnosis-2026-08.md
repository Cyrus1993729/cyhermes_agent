## 诊断链（按序，每步给结论）
1. **agent.log**：cron/日报与会话大量 `ConnectError / APIConnectionError`（所有 provider 全挂 = 出口级故障，不是单 provider 问题）
2. **Clash sidecar 日志静止时间戳** = 卡死时刻：
   `~/AppData/Roaming/io.github.clash-verge-rev.clash-verge-rev/logs/sidecar/`
   正常时 sidecar_latest.log 持续写入；卡死时最新归档文件（`sidecar_<日期>_<时间>.log`）mtime 停止更新 → 该时间就是卡死点。
3. **采集 0 条佐证**：TrendRadar `output/news/<日期>.db` 的 `crawl_records` 表每次采集的 total_items 归零（范围/时间分布用该表判断，不要只看 db 存在）。
4. **系统事件日志判定"是否重启/谁重启"**：
   - Event 41 (Kernel-Power) + Event 6008 ("上一次关闭是意外的") = **用户手动强制断电/按电源键重启**的记录，**不是系统崩溃**（BugcheckCode=0 非蓝屏）
   - 别把"意外重启"误读成"系统自己崩了"——先问用户：屏幕黑屏/手动重启了吗？
5. **系统是否活着**：计划任务仍在每小时执行（crawl_records 有记录）= 内核活着，只是网络/显示层异常。显示器黑屏 ≠ 系统死（可能是显示器自动关闭或显示栈挂起，按不亮才需要重启）。

## 结构性问题（根治方向，用户已认可但未拍板落地）
- **告警单通道失明**：健康检查告警也走 TG → 通道死=无监控。需"本地落盘故障状态 + 恢复后补发摘要"的看门狗（区分 TG不通/模型不通/newsnow 0 条/代理端口不响应，同一失败签名只记一次）。
- 恢复依赖"意外重启"：Clash 卡死无自愈、无监控；Clash 节点（美国111-OVH）失效是诱因（sidecar 停前节点输出不稳）。**不自动切换节点**（用户红线，稳定 IP 需求）。
