# 双引擎审查层设计（2026-08-01 共识稿）

## 背景

经过三轮 Opus + Codex 独立咨询，确认审查层重构方向。此文为设计共识存档，尚未实现。

## 关键环境信息

- Codex CLI 已接入，模型 gpt-5.6-sol，ChatGPT Plus $20/月会员
- Claude Code CLI 已接入，模型 Opus，Claude Pro $20/月会员
- 两边成本对等，调用方式一致（CLI），无额外开销
- Codex exec 模式不需要 pty=true（加 pty 会导致进程完成后不退出）

## 审查层现状（④）

```
L1: 千问 Qwen 3.7 Max → 全量6维审查 + 疑点标记（D5只做存在性检查）
  ↓ 疑点
L2: Opus → 只审 L1 标出的疑点，确诊/排除
```

核心局限：L1 是天花板——千问漏掉的疑点，L2 永远看不到。

## 目标架构（共识稿）

```
④ 审查（新）
  ├─ Codex GPT-5.6-sol  全量6维审查（正向重建验证）
  └─ Opus                全量6维审查（反向证伪找茬）
      （并行跑，不串行）
        ↓
    对比脚本 → 接地校验 → 归并 → 仲裁
```

千问退场。

## 审查分工（核心共识）

| | Codex | Opus |
|---|---|---|
| 角色 | 正向重建验证者 | 反向证伪者 |
| 心法 | "不信结论，独立重做，看能不能复现" | "假设它错了，找出裂缝" |
| 强制产物 | 可复现的确定性证据（重算值、回表、行号） | 反例、承重假设、盲区、反方视角 |
| 主责 | D1/D3/D6（可重做验证的） | D2/D4/D5（需判断对抗的） |
| 另一半维度 | 陪审确认式轻扫 | 陪审确认式轻扫 |

关键：都审全部6维（不按维度切分），但每一维有一个主责（深查低门槛）+ 一个陪审（轻扫高门槛）。

## 仲裁架构（8 点共识）

### 1. 统一输出 schema

两个模型输出必须包含：引擎标识、维度覆盖声明（含"已查无发现"）、finding 数组。每条 finding 带 `locator.quote`（交付物原文逐字引用）+ 严重度 + 证据链。

### 2. 证据接地校验（防幻觉，仲裁前第一道闸）

拿 `quote` 去原文精确匹配。对不上 → `unverified`，永不阻断，severity 上限降级。

### 3. 问题归并

按（维度 + 归一化位置 + 根因 + 验收项）聚类。关系分：duplicate / same_root_cause / causes / contradicts / independent。

### 4. 风险分级仲裁

- **阻断条件**：`接地成功 + (双方确认 或 交叉质证通过)`，且 severity ∈ {critical, high}
- **单方发现不直接阻断**，必须进交叉质证
- **CONFLICT（一方block一方no_issue）→ 一律上抛用户**
- major/minor/nit → 不阻断，进修复清单

### 5. 交叉质证

单方发现（severity ≥ major）→ 甩给沉默方：「确认 / 证伪 / 不确定」。对方确认→升级双方共识；对方反证→降级；对方不确定→上抛。

### 6. 修复后复审

- 最多 2 轮，R2 后仍 block → 硬上抛
- 复审范围 = 改动区域 + 影响半径，不全量重审
- issue 用稳定 ID，防止改名重开
- 新问题必须证明是修复引入，否则不计入

### 7. 上抛用户场景（仅 7 种）

1. 契约本身含糊或冲突
2. 价值取舍（非真假对错）
3. 必须新增范围/预算/权限
4. 外部事实无法验证但决策依赖它
5. 修复会改变用户批准过的方向
6. 两模型证据强度相当但互斥
7. 达到修复轮次上限仍有 high 分歧

### 8. 最终状态只有四种

`PASS` | `PASS_WITH_NOTES` | `REPAIR_REQUIRED` | `USER_DECISION_REQUIRED`

## 影子模式三阶段

| 阶段 | 行为 | 门槛 |
|---|---|---|
| 静默影子 | 双审运行，不影响交付，纯收集数据 | — |
| 软门禁 | Critical 经核验后阻断，High 可人工覆盖 | Critical 误报率接近零 |
| 正式门禁 | 双审结果绑定流程 | High 精确率 ≥80%，接地率 ≥95% |

建议 2-4 周或 50 个真实任务后评估。

## 复盘闭环（两条反馈回路）

1. **标定回路**：复盘误报/漏报 → 回调触发判据阈值和接地门槛
2. **上游回路**：反复出现的 finding 类型 → 回写到①契约做成前置条件

## 相关 skill 改动计划

- `l1-review`：从"单审 prompt"重构成编排器（双引擎拉起 + 接地 resolver + 归并 + 仲裁）
- `task-wrapup`：加审查 hook（查触发判据 → 调编排器 → 按裁决处理 → 写台账）
- `workflow_check.py`：升级为确定性控制器（10 项校验 + 状态码输出）
- `post-task-review`：加审查层指标统计（双审效果、根因归因）

## Opus + Codex 每次咨询的问题设计

三轮有效实践：明确问题边界 → 两边用相同的 prompt → 并行发 → 对比共识/分歧 → 用户做方向选择。未来类似架构讨论沿用此模式。
