# 交付前完整性核查

适用于**任何产出文件/方案/报告的交付**，尤其是「要给第三方（别的 agent / 同事 / 外部模型）用」的。

一个任务从开头干到收尾，中途用户会一路加要求；而交付那一刻的注意力全在最后一段上，
**最容易漏的恰好是中段加的、你当时“听到了但没写下来”的那几条**。

---

## 🔴 核查 A：用户中途追加的要求，逐条回扫

```
1. 把本轮用户所有消息按时间顺序过一遍（不是只看第一条需求）
2. 每条「你要……」「要包含……」「注意……」「等等这些」句出一行清单
3. 对着交付物逐条标：已包含 ✓ / 未包含 ✗ / 部分 △
4. 有 ✗ 或 △ → 补完再交付，不靠「我记得写了」
```

### 实踩（2026-11-17，两次被打回）

给第三方 agent 写一份方法分享文档。用户中途补了一句：
「我们从薄荷去拿数据的、薄荷数据有缺失怎么办、碰到菜库里没有怎么做拆解，这些要包含进去」。

交付后回查：数据源那节只写了「成品菜条目库」四个字——
**既没说库从哪找，也没写「库里没有这道菜怎么拆」**。用户连问两轮：

> 「我后来的这些要求你有检查过你写的这个分享文档包没包含吗？」
> 「你好像没有告诉他成品的库从哪里找对吧」

**根因**：把用户中段那句当成背景补充听过去了，交付前只按「我自己定的目录结构」打勾。

### 两个抓手

- **把用户发的每一个问号当成一条必须回答的条目**，而不是语气词。
  用户说话常断句（「我们怎么从薄荷去拿数据的」后面没说），那一句本身就是待回答项。
- **他重复提第二次的要求 = 判定为硬需求**，立即自查而不是再解释一遍。

---

## 🔴 核查 B：对外交付必须先问「对方能不能直接开工」

方法、理念、原理**不是交付物**。写给别人的东西，每个环节都要能给到：

| 必须给到 | 反面 |
|---|---|
| 去哪拿（具体域名 / 仓库 / 文件位置） | 「主数据源用公开营养库」 |
| 怎么鉴权（申请路径、签名方式、token 时长） | 「需要 API key」 |
| 有没有额度 / 频率限制（多少、何时重置、被限怎么办） | 不提 |
| 具体地址 / 命令 / 参数形态 | 只画流程图 |
| 降级/兼容的备选源及标注要求 | 「查不到就拆」 |

**写完自问一句：只靠这份文档，一个不了解背景的 agent 能不能直接开工？**
答不上来就说明还没写完。

反面例子：把「窗口看门狗会重启进程」写成方案，而没告诉对方 Windows 上根本没有
the supervisor（→ 对方照做后依然被卡）。

## 🔴 核查 C：对外交付的脱敏扫描

涉及“给朋友/同事/外部 agent”时，交付前用一行命令扫一遍，**0 命中才算过**：

```bash
grep -ncE "<姓名>|<体检指标关键词>|<体重/TDEE 等具体值>|<带用户名的绝对路径>|<API key 前缀>|6vdh<...>" 交付物.md
```

- 路径换成 `{HERMES_HOME}` / `~/` 占位符，不写 `C:\Users\<名字>\`
- 凭据只写「自己申请自己的，不要共用」，**绝不把现成的 key 写进公开文档**
- 真实数字（体检值、体重、订阅额度）换成「若用户有 X 类关注点则…」的条件句式
- 扫完把命中数告诉用户（「0 命中」比「我检查过了」可信）

---

## Pitfalls

- **不要在“收尾自检”里只对 skill 的 SOP 打勾**。SOP 不会包含用户本轮临时加的东西，
  两份清单要分开跑：SOP 的 + 用户追加的。
- **不要用“已经覆盖了同类信息”自我说服**。用户点名的那几个字（比如“拆解”）如果文档里没有对应小标题，
  就是没写。
- **补写新章节后要回头改总述**：开头如果写了「本文 12 节」，加完节要回头对。
- **交付后用户又补要求的，当轮就重扫全篇**，不要只补那一节——常有多处连带（比如补了“数据源在哪”，
  降级源、额度、鉴权三处都跟着缺）。
