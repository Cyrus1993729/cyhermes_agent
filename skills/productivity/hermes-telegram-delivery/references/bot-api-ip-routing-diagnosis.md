# 「线路抖动」定位法 —— 2026-10-08 全记录

## 症状

gateway.log 里 `[Telegram] Telegram network error (attempt 1/10) ... httpx.ConnectError: `（消息被 token 脱敏成空串）持续刷屏，
最终导致 `send_path_degraded` 丢消息。累计统计：日志窗口内 **5427 次**，单日约 **900 次**。

用户会质疑「这是我优化过的线路，怎么会抖」——这个质疑是对的，问题确实不在他优化的那一段。

## 第一步：先证明「和用量无关」

从日志算三个量（Python 解析 gateway.log，时间戳正则 `^(\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2})`）：

- 错误到达间隔：中位数 **70s**、均值 92s（不是严格定时器）
- 错误点前后 120s 内有 agent 活动的比例：**8%**（435/5427）→ 不是被自己的流量挤出来的
- 逐小时分布：**24 小时均匀**，凌晨 3-4 点用户零活动时仍 40-60 次/小时

结论：这是**持续状态**，不是偶发故障。900 次/天 ÷ ~1% 失败率 ≈ 每天上万次新建连接，对得上「轮询每秒都在开新连接」。

## 第二步：排除本地代理与带宽

| 实验 | 结果 |
|---|---|
| 空载串行探测 51 次（含 50MB 满载下载期间） | 0 失败 |
| 40 路并发轰炸 3 轮 | 0 失败 |
| 本机 127.0.0.1:10808 TCP 直连 | 始终可连，非代理宕机 |
| TIME_WAIT / 动态端口 | 135 / 16384 端口可用，非端口耗尽 |

⚠️ **这些「0 失败」是采样不足造成的假象**：串行小样本看不到 ~1% 的失败率。

## 第三步：加大样本 + 剂量效应（关键）

400 次 / 并发 20：**30 失败 = 7.5%**。
再按并发梯度各跑 60-100 次：

| 并发 | 1 | 4 | 10 | 20 | 30 |
|---|---|---|---|---|---|
| 失败率 | 6.7% | 8.3% | 6.7% | 3.0% | 7.0% |

**失败率与并发无关** → 不是限流/拥塞，是**每条新连接固定的失败概率**。

## 第四步：对照目标（分清楚是谁的问题）

同样 20 并发各 80-100 次：

| 目标 | 失败率 |
|---|---|
| `api.telegram.org` | **3-11%** |
| `core.telegram.org` | 0/80 |
| `telegram.org` | 0/80 |
| `t.me` | 0/80 |
| `www.google.com` | 0/100 |
| `api.github.com` | 0/100 |

→ 排除 GFW 泛封锁、排除节点路由到 Telegram 整体劣化、**锁定到 Bot API 这一个端点**。

## 第五步：连接复用对照（为什么会天天中招）

| 方式 | 结果 |
|---|---|
| 同一个 httpx client 复用连接，间隔 45s 打 7 次 | 7/7 全通 |
| 每次新建 client，同样间隔 45s 打 5 次 | **5 次挂 1 次** |

→ **只有新建连接会中招**。而适配器的 getUpdates 池 `max_keepalive_connections=0`（故意不复用）→ 每次轮询都新建 → 天天踩。

## 第六步：钉到具体 IP

DoH 查 `api.telegram.org` 的 A 记录 → **只有 `149.154.166.110`**。逐 IP 各 160 次：

| IP | 失败率 |
|---|---|
| `149.154.166.110`（api 现用） | 8/160 = **5.0%** |
| `149.154.167.220`（另一 Bot API 入口） | **0/160** |
| `149.154.167.99`（core 实际） | 0/40 |
| `149.154.175.50`（另一 DC） | 40/40（本来就不通，无关） |

端到端确认钉 IP 可行：用真 token 打两个 IP 的 `getMe`（`Host: api.telegram.org`，`verify=False`）→ **都是 200，同一个 bot**。

## 失败签名

统一是 `httpx.ConnectError('SSL: UNEXPECTED_EOF_WHILE_READING ...')`：TCP 连上了、TLS 握手被中途掐断。
复现判据（怎么区分异常类型）：

| 构造的场景 | httpx 抛什么 |
|---|---|
| 代理侧连不上目标（域名不存在） | `ConnectError` + `SSL: UNEXPECTED_EOF_WHILE_READING` ← **本次就是这类** |
| 代理侧连上了但握手无响应 | `ConnectTimeout`（握手超时） |
| 本地代理端口写错/进程挂了 | `ConnectError` + `WinError 10061 积极拒绝` |

## 判定阈值备忘

- 判「线路没问题」：≥300 次采样 + 至少两个对照站点，否则不下结论
- 判「单点 IP 问题」：目标站点内多个子域/多 IP 对照，差异稳定复现两轮以上
- 探针不要用真 token 起 getUpdates（会与网关抢更新），用根路径或无效 token

## 修复选项

- **治本**：VPS 上钉 `api.telegram.org → 149.154.167.220`（`/etc/hosts` 或 xray `dns.hosts`；xray 自带 DNS 时 `/etc/hosts` 不生效）。需要 SSH。
- **兜底（已落地）**：`scripts/tg_delivery_watchdog.py` 每分钟扫 `state.db` 台账自动补发。路由问题会漂移，兜底比钉 IP 耐久。
