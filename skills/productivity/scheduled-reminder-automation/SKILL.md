# 定时提醒 / 每日简报管线

用户说「每天提醒我今天的安排」「会前提醒」「每晚收尾」「定时推一份 X」时加载。

## 三个部件

| 部件 | 频率 | 职责 |
|:--|:--|:--|
| 早报 | 每日定点（如 07:30） | 当天全貌 + 主动询问 |
| 心跳 | 每 5 分钟 | 变更检测 + 会前 N 分钟提醒 |
| 收尾 | 每日定点（如 21:30） | 列未完成，等用户确认 + 复盘 |

全部用 `no_agent` 脚本，不调模型——高频轮询零额度消耗。

## 四条设计铁律

1. **节流靠快照 TTL**：本地快照未过期就不碰上游 API。TTL 取**上游同步周期**（钉钉/邮件同步是 15 分钟 → 快照 TTL 15 分钟），5 分钟心跳只读本地快照判断提醒，几乎零接口开销。
2. **幂等靠去重键 + 成功才记账**：键用 `事项id|开始时间|日期`；**发送成功才写去重记录**，失败不记以便重试。
3. **兜底绝不静默**：主通道失败自动转备用通道，并在文案里注明「XX 通道没发出去，这条走 YY」。
4. **长度预算按拆块线折半**：先查平台分块阈值，主动推送取一半（微信拆块线 1800 → 单条 ≤900），既防截断又少占配额。

## 先出消息样例，再谈方案

不要一上来给架构表。把用户**手机上会看到的那三条消息原样写出来**（用真实数据做样子），他能直接指着改数字和口径——比选项按钮有效。本用户明确要求「可整段复制编辑的纯文本」，不要按钮。

## 用户口径（本用户已确认，沿用）

- **渠道分级**：日程类提醒走微信，且**只讲结果、不报过程**；Telegram 才分步汇报。
- **无内容不等于不发**：当天没安排也要发，并**主动问要不要安排事**（像秘书）。
- **冲突只提示不自动改**：列出撞了哪两件，问他是真并行还是去掉一个。
- **历史遗留只追最近 N 天**（默认 3 天），更早的静默且**不删数据**。判据：会议开过就是开过、通知不是任务、一周前的个人小事无追问价值；只有体检这类重事项值得单独问一次。
- **完成但没打勾 → 只标 completed，不补 actualMinutes**。否则时间统计全是假数。实际投入只在用户真报分钟数时记。
- **收尾消息兼作会话刷新**：让用户回一句，同时重置对方平台的会话配额（微信 context_token 机制）。

## 对话侧必须接住的两件事

- 用户在对话里说「加个安排」→ 当场写系统，**然后刷新今天的快照文件**，否则心跳会再推一次「已更新」，变成重复。
- 用户回「2 做完了、3 取消」→ 读收尾时落盘的**编号→事项映射**，批量改，别让他逐条点。

## 验证顺序（不能跳）

1. `DRY` 环境变量让 send() 只打印不发送，先看文本长得对不对。
2. **假数据单元测试**：冲突检测、提醒窗口边界（±2/±3 分钟）、变更 diff（新增/取消/改期）、超长日截断。**不碰真实记录**。
3. 真实 run 一次，确认对方**真收到**（不是只看脚本 exit 0）。
4. 查 cron 状态字段（`last_status` / `last_delivery_error` / `last_delivery_unverified`）才算交付。

## 坑

- 脚本自己发 → cron 必须 `deliver='local'`，否则 stdout 被再投递一次，一内容双发。
- 事项多时不要静默丢行：给列表设上限 + 「还有 N 项未显示」。
- 别每天甩一次历史清单的数量——用户会反感，改成静默或只追近期。
- 深夜（0-6 点）直接退出，别空转拉接口。
- 验收测试若会落盘，用隔离日期（如 2099 年）并事后清理，别写脏真实档案。
