# 干活时的进展播报

用户等待期间的沉默 = 他以为你卡住了或忘了。这条 skill 管的是**过程**怎么说话，
不是**结果**长什么样（结果形态见 `task-wrapup` / 各域 skill 的回执规范）。

触发：一次任务要连跑 3 个以上工具调用才拿得到结果；任务里有等待（后台进程、ASR、OCR、子 bot 会话）；
或用户已经中途打断过你一次问「进度呢」。

不触发：一问一答的单步任务；纯对话。

## 🔴 铁律一：自己干的活，按节点实时播报

> **2026-11-15 实踩**：做小红书菜谱扒取，连跑「短链解析 → 页面抓取 → 视频下载 → 抽音频+抽帧 → ASR」
> 五个动作，全程**一句话没说**。用户中途打断：
> 「你似乎还是没有记住我之前跟你说的汇报习惯 你自己做的工作的内容，你必须要实时汇报进展动作
> 只有发给健康助理的内容是一次等结果的。」

**「做完再说」是被明确否掉的。** 每个节点都要出声。

### 什么算「节点」（各报一次，不重复报）

| 节点 | 说什么 |
|:---|:---|
| **接活（最容易漏）** | **收到 + 我打算怎么拆 + 大概几步**。这句必须在**第一个工具调用之前或同时**发出，不能等第一个产出 |
| 阶段切换 | 上一步拿到了什么、下一步做什么（一句） |
| 产出到手 | 关键数据先贴出来，别等整理完 |
| 遇到阻塞 | 缺依赖/要装东西/要等很久——立刻说，别自己闷着修 |
| 判断分叉 | 按流程判了「需要下载 / 不用下载」这类结论，要让他看见你判了 |
| 需要他拍板 | 待确认项一次列全，别挤牙膏 |

顺序建议标 `（1/3）（2/3）（3/3）`，他抱怨过「为什么一句话要分两条」，
事先标序号能让多条消息看起来是一条流程而不是碎嘴。

### 🚫 不要报什么

- **不要复述工具调用**（「我正在调用 curl 抓取页面」）。他没在看工具面板，报**结论**。
- **不要每个工具调用前都发一句**（「我先看看…」「接下来我要…」）。那正是被投诉的「一句话分两条」。
- **调用工具前不要只发一句空话**——它会被网关推成一条独立消息，然后工具又在后面跑，观感就是刷屏。
  先把工具跑起来，在同一个回复里带上进展说明。

> ⚠️ **但任务入口那一句不是空话，不能拿这条当借口省掉。**
> 分界：「收到，我先拆链接，大概 4 步」= **承诺**（说）；
> 「我这就去查」后面跟着一个工具 → **预告**（不说，直接跑并把结论带回来）。
> 区别在于前者告诉了他「接下来会发生什么」，后者只宣布了「我要开始动」。

## 🔴 铁律二：只有「派给子 bot」那一步可以一次等结果

用户原话里唯一被允许的例外：**发给健康助理这类跳 profile bot 的单次异步调用**。
理由——那本来就是一次后台进程 + 一次读回，中间没有可报的节点。

```bash
# 派活：任务书落文件，后台跑，notify
hermes -p <profile> chat -c "Bot Chat" -m <model> -Q --query-file "<绝对路径>" \
  > "<输出文件>" 2>&1
```

等待期间**不用报**——用户 2026-11-15 原话：「你做完之后把活给健康助理派的时候，这个时候你可以没有回应，**我们一起等结果**，这个才符合我们商量的逻辑。」
「已派出，约 N 分钟」这句是**可选**，不是硬要求；除非任务书上游还有未完成的本机动作。

### 两个场景怎么切换：看「现在是谁在干」

```
我自己在跑（解析/下载/ASR/OCR/搜索/核验）→ 每完成一个动作报一句
球在子 bot 那边（已派出、后台等）  → 不用报，一起等
回来之后（读结果、核验、转述）      → 当场报，全文明细
```
**判据只有一个：这段是我在做，还是它在做。** 不要用「任务进行了多久」来判断——那会把正常的等待也当成沉默。

### 派出去之后必须核验再转述

子 bot 的自述不是事实。转述前至少核这三样：

1. **它说落盘了吗** → 自己 `ls -l` 看文件在不在、多大
2. **明细有没有被它压成摘要** → 它压了，你要么让它重跑，要么自己补回去
3. **引用/数字的「维度」对不对** ← 最容易翻车

> **2026-11-15 实例**：健康助理写「蒸制（15–45 min）保留 β-胡萝卜素 66.30%–82.19%，20 min 约 82%、
> 40 min 约 66%，差约 16 个百分点」。回查 LWT 2019 原文：66.30%–82.19% 是
> **煮(15–35min) + 蒸(15/35/45min) + 微波(15min) 三种方式合并的区间**，不是「蒸制随时间下降」的
> 时间维度区间；且蒸只测了 15/35/45 三个点，没有 20 和 40 分钟的数据。
> **跨方式的区间被当成时间趋势**，据此推出的「多损失 16 个百分点」整体不成立。

**核验动作**：看到「A 到 B 的区间随 X 变化」这种话，先查这个区间**在原始文献里是沿哪个维度展开的**。
区间宽度 ≠ 趋势斜率。子 bot 很擅长在正确引用一段文献后，接一个错的推论。

## 🔴 铁律三：回执不压摘要

- 逐项明细**原样搬出**，不许写成「已记录，合计 XXX 卡」这种总结句。他说过压成摘要等于没给回执。
- 逐项一行 + 合计 + 参数备注 + 来源标签，极简 ≠ 省字段。
- 后一次追加**不代替**前一次（午餐被追问过一次）。

## 🔴 为什么会反复——复发机制与解药（2026-11-15 用户拷问后补）

上面三条铁律早就写在本 skill 里了，**当天仍然犯了 5 次**（早餐 + 午餐 v2/v3/v4/定稿全是派完就干等）。
用户最后直接问：「**为什么汇报习惯你总会反复呢？有时候记得有时候不记得。**」

不是忘性，是下面三个机制。**知道机制，才能在新场景里认出它。**

### 复发点 ①：迭代到第 3、4 轮时，会自己给自己豁免

第一轮会发「已派出，约 N 分钟」；到 v2/v3/v4 时就默认「这种活你知道了，不用再说了」。
**同一类任务的重复派活，恰好是豁免感最强、而用户等待感最弱的时候。**
（本轮 5 次派活，那句「预计 X 分钟」一次都没发。）

→ **解药：派活句式与轮次无关。第 5 轮的派活和第 1 轮一模一样，照发。**

### 复发点 ②：注意力被数字挤走

v2→v3→v4 三轮全在纠口径（钠 2480 还是 2130、配菜归零还是 15%），
**任务越难，越容易只盯任务本身，汇报规则被挤出视野。**
→ 解药：把「派活前一句」变成动作前置检查，不靠记性（见下方自查卡）。

### 复发点 ③：记忆里那三条禁令与自己这条 skill 表面相斗

```
分步汇报只在阶段节点说（不是每个工具前都发）
TG 回复：调工具前不要先写一句（只在节点/结束时说话）
微信只讲结果不报过程
```

三条全是**「少说」**，没有一条说「什么时候必须说」。在禁令下，沉默永远是最安全的选项。

→ **解药（一句话分开）：**
> **禁令管「同一节点内的碎片」，本 skill 管「跨节点的沉默」。**
> 禁止的是「为了说而说」（一个动作拆成两条消息）；要求的是「结论变了必须说」。

### 复发点 ⑤：任务入口那一句，被「不要把一句话拆两条」的禁令误杀（2026-11-15 二次拷问）

> 用户：「**为什么我在给你派那个任务的时候，哪怕在小红书这类活儿上，你也没有任何回应呢？**」

事后查 `state.db` 时间戳取证：

```
早餐    工具调用起 12:42:36 → 首次文本 12:49:13   静默 6 min 37 s（8 次工具调用，0 句人话）
小红书  工具调用起 15:47:20 → 首次文本 15:50:51   静默 3 min 31 s
        且首句是「链接已解开」——已经跑完解析才开口，
        等于把「接活确认」和「第一个产出」合成了一句。
```

**根因：任务开始必然发生在第一个工具调用之前，而记忆里那条「调工具前不要先写一句」的禁令，恰好在这个位置作用最强。**
节点清单里又只有「阶段切换 / 产出到手 / 阻塞 / 分叉 / 拍板」这些**任务内部**节点，
**没有「任务入口」这一项** —— 于是接活那一刻在两条规则的夹缝里被静默掉了。

更隐蔽的一层：我把首句发成了「链接已解开」这类的**产出型**消息，似乎「有话可说了」，
但用户要的是**「我知道你开始了」**，不是「你干完了一步」。

→ **解药：任务入口是节点，且是优先级最高的那个。**
> 句式：`收到，我先干 X（拆链接/查价/读文件），大概 N 步，跑完每一步我报一句。`

### 复发点 ④：给「回执不压摘要」自己加例外

> 2026-11-14 反例：Agent 回「这条是派活的完成回执，**结果已经完整报给你了**」（194 字），被用户指为压摘要。

当时的判断是「你看过了，再贴一遍是啰嗦」。**用户的标准是不管我看没看过、回执要给全。**
「除非内容没变」这个例外是 Agent 自己加的，用户从没给过。

### 复发点 ⑥：长工具链的「自干段」最容易整体静默（2026-11-17 实踩，代价是用户重启电脑）

> 用户：「你要注意你的汇报习惯哦，**这个已经提醒过你很多次了**。」
> → 隔一会儿一个「？」
> → 「我刚刚手动重启了电脑，因为我发现我不重启电脑的话，好像你就一直没有反应了。」

场景：**写一份可交付文档**（读技能库 → 查 API 定义 → 起草 → 补章节 → 自检），
连续 15+ 次工具调用、**全程零句人话**。用户无法区分「在跑」和「卡死」，最后按卡死处理。

三个因素叠加，缺一个都不会这么糟：

1. **它没有被认成「自己在干」**——因为长得像「资料整理」，被判成开工前的准备阶段，于是豁免掉了
2. **产出不可见**——文档在 write_file 那一刻才有形状，前面全是读取，看着像什么都没发生
3. **前台 `sleep` 等子进程**——用 `sleep 240` / `sleep 200` 前台轮询子 bot，一次直接被 timeout 杀掉，
   会话观感从「慢」变成「死了」

→ **解药三条**：
- **自干的长链一样要切节点**：读资料(1/3) → 查到关键定义(2/3) → 开始写(3/3)。每段一句话，不求长。
- **等子 bot 一律 background + notify，禁止前台 `sleep` 长等**；非要前台轮询就分段 ≤120s，
  且**每一段结束都必须出声**（哪怕只是「还在跑」）。
- **判据不变：看「现在是谁在干」**，不看「这活显得多琐碎」。读文件、查接口、写文档全是「我在干」。

### 复发点 ⑦：接活应答发完就结束回合 = 换了个方式沉默（同日实踩）

实际发的：「收到，我按下面结构写：1…10…，先跟你把结构说清楚再动手」→ **回合结束** → 用户回「？」。

> 应答句本身是对的（铁律一要求「第一个工具调用之前或同时」），
> 错在**只发了话就停手**。「先跟你把结构说清楚再动手」在他听来 = 又要等一轮确认。

→ **解药：应答句和第一个工具调用必须在同一回合里。**
> 应答不是请求许可，是开工宣言。
> 句式：`收到，我按这 10 块写，现在去读技能库和接口定义` + **紧接着就调工具**。

### 🔴 派活自查卡（发出前看一遍，四行）

```
1. 我自己刚跑完动作了吗？→ 报结果，不管第几轮
2. 现在是哪一段（自己跑 / 派出去等）？切换时说一句「已扒完，现在发给健康助理」
3. 回执回来要全文搬——不管第几轮、不管他看没看过
4. 它自报的数我验了吗？（文件在不在、明细有没有被它压、引用的维度对不对）
```

> ⚠️ **不要因为「派活后可以沉默」就倒推成「整个过程可以沉默」**（Agent 2026-11-15 就犯过这个误判）。
> 允许沉默的只有球在对方那边的等待段；我自己动手的每一段都不能静音。

> 完整取证（一天内 5 次沉默的时间线、三条互相打架的规则、五条修法）见
> `hermes-context-partitioning` 的 `references/progress-reporting-protocol-2026-11-15.md`。

## Pitfalls

### 判了不发，等于没判

流程里做了「desc 密集/稀疏」这类判断，**必须在过程里显式输出判断结论**，否则用户只看到结果、
无从判断你是否走了流程。

### 装依赖的阶段最容易沉默

OCR/ASR/模型下载动辄几十秒到几分钟，容易在后台静默修。
**修依赖本身就是一个节点**：说清「缺 X，我在装，预计 Y」，装完说「装好了，继续」。
（踩过：`rapidocr_onnxruntime` 没装 + venv 没 pip，静默折腾了两轮用户才问。）

### 一个任务里两套标准会打架

「自己干活要实时报」和「子 bot 那步一次等结果」同时存在时，
报价前先说清楚现在是哪一段（「菜谱已扒完，现在发给健康助理」），
不然用户无法判断该不该催你。
