# Opus + Codex 双审实证（2026-08-01）

## 测试设计

同一 prompt 同时发给 Opus（Claude Code CLI）和 Codex（Codex CLI），独立回答同样的 4 个问题。

Prompt 描述的方案：砍掉千问 L1→Opus L2 的分层审查，改为 Codex + Opus 并行全量审查再对比裁决。

## Opus 核心结论

**方向判断**：「大方向对，值得做。推理链比上轮方案一过渡→方案三终点更直接。」

**暗坑发现**：
1. 双模型同质盲区→合谋放行（静默失败）
2. "任一否→采纳"太糙——一票否决让幻觉误伤。应改为接地校验+交叉质证
3. 砍千问砍掉了唯一异质来源（弱模型的不完美=价值）

**仲裁升级版**：五分支取代三分支
- 都过→放行+盲区标签
- 都否→直接修
- 一方否→接地校验→甩给沉默方交叉质证→确认/上抛
- 互斥证据→上抛
- 无证据→丢弃

**三件事先做**：接地校验、交叉质证、影子模式量分歧率

## Codex 核心结论

**方向判断**：「自洽，逻辑成立。全量双审是分层模式的正确演进方向。」

**暗坑发现**：
1. "任一否就修"太激进→应区分 severity
2. 提示注入风险→审查材料视为不可信数据
3. 无止境优化→区分 correctness/requirement/risk/enhancement
4. 超长跨文件→双模型同时漏相同内容

**落地架构**：七层
1. 审查策略差异化（A 找满足证据，B 找反例）
2. 统一输出 schema（每个 finding 独立原子、可定位、可复现）
3. 确定性预验证（schema/文件/行号/公式/测试 8 项）
4. 问题归并（6 种关系类型）
5. 风险分级仲裁（十分支，区分 critical/major/minor）
6. 修复后定向复审（不重审全量）
7. 监控指标（8 个 KPI）

**三条原则**：
1. 任一可信、在范围内、可验证、达阈值→才修
2. 确定性验证优先，模型判断其次，用户裁决最后
3. 不要两模型用相同审查路径

## 双方共识

| 共识点 | 内容 |
|---|---|
| 方向认可 | 全量双审比筛子式分层更优 |
| 最大反对 | "任一否→采纳"必须改，一票否决太激进 |
| 核心改进 | 证据必须可机械验证（接地校验 = 确定性预验证） |
| 上线前 | 先跑影子模式量分歧率 |
| 独立性 | 审查 prompt 必须刻意差异化，否则假独立性 |
