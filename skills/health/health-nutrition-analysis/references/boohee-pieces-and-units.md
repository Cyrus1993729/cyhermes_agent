## 一、结论先给：**不用买会员，公开接口白给**

| | 接口 | 结果 |
|:--|:--|:--|
| ❌ 付费 | `GET /api/v2/foods/:code/units` | `{"success": false, "message": "权限不足！"}` |
| ✅ 公开 | `GET https://food.boohee.com/fb/v1/foods/<code>` | **带 `units[]` + `is_liquid`，零额度** |

⚠️ 付费接口返回的是「**权限不足**」而不是「次数超过限制」——说明**权限检查卡在档位上，
跟额度无关，买调用次数解不开**。这个区别很重要：别误以为提高套餐次数就能拿到。

返回值形状：

```json
{
  "name": "鸡蛋", "is_liquid": false,
  "units": [
    {"unit": "只(中)", "weight": "60.0",  "eat_weight": "52.8"},
    {"unit": "只(大)", "weight": "70.0",  "eat_weight": "61.6"}
  ]
}
```

### 🔴 换算一律取 `eat_weight`（可食部），不是 `weight`

他说「吃了一个蛋」= 吃进去的 **52.8g**，不是连壳的 60g。
`weight` 只在需要「整颗长什么样」时才用。
**薄荷比《中国食物成分表》强的地方正在这里——它连可食部都分好了**（苹果去核、
鸡蛋去壳、橙子去皮），省掉了自己查可食率那一步。

## 三、🔴 怎么挑默认量词（调了三轮才算对）

同一个食物薄荷给一堆量词，**默认挑哪个直接决定他动不动手改**。
**规则是「挑他会说出口的那个」，不是「挑列表第一个」。**

```python
_ORDER = ("个", "只", "颗", "枚", "根", "块", "片", "条", "碗", "杯", "份", "串", "盒")
_AVOID = ("勺", "口", "粒", "把", "袋", "瓶", "罐", "盘", "碟", "茶匙", "汤匙")

r = 在 _ORDER 里的下标（不在则 50）
若命中 _AVOID → +25          # 计量单位，不是他说话的方式
若含"中"      → -0.5         # 他说"一个"通常指中等
重量 0         → +30          # 没重量，不可用
重量 < 8g      → +12          # 太小，不像"一份"
重量 > 600g    → +6           # 太大，多半是整只/整袋
```

**走过的弯路（三轮）**：

1. 第一版只按 `"中"优先` → 米饭挑中「**勺 40g**」、苹果挑中「**盘**」
2. 第二版把 瓶/盘/罐 加进 _ORDER → 更糟：牛奶挑中「**瓶 1500g**」
3. 定稿：**按「他会说出口的顺序」排 + _AVOID 重罚 + 重量合理性加罚**

⚠️ **关键认识：单位名不能决定量级合理性**。「瓶」对牛奶是 1500g、对饮料可能才 300g；
所以词表排序之外**必须**再叠一层重量合理性判断。

## 四、🔴 公开接口有频率限制：**HTTP 429**

```
HTTP Error 429: Too Many Requests
```

**踩过的坑（丢了一轮数据）**：

我为了重建表先删了 `piece_weight.json`，接着连打了一串 `public_units()`，
结果撞上 429 —— **而且被限之后一段时间内，*所有*请求都失败**（不只是被限的那个接口）。
已抓到手里的数据已经删了，**白跑一轮**。

**所以建表必须满足三条**：

| 条 | 做法 |
|:--|:--|
| **慢** | 每个请求间隔 2.5s 起 |
| **退避** | 撞 429 指数退避（3s、6s、9s…），连续失败则停 20s |
| **断点续传** | **每抓一条立即落盘**，不是跑完再存 |

🔴 **千万别删 `piece_weight.json`**。要重查就单条删，别整个文件删。
日常使用是「按需查 + 永久缓存」，不会触发限流；**只有批量建表才会**。

**7 条抓失败的不用管**——运行时按需会自动补，补不到就走降级链。

## 五、🔴 匹配错配：「猕猴桃」→「猕猴桃晶」

薄荷公开搜索返回的第一条不一定是你要的。实测「猕猴桃」匹配到了
「**猕猴桃晶**」（一种冲剂粉末）→ 结果被判成 `is_liquid=true`、单位成了「**勺 10g**」，
**错得离谱且看不出来**。

**修法：查询词后面直接跟「制品后缀」的，匹配分直接压到 20。**

```python
_PROCESSED = ("晶", "粉", "汁", "浆", "饮料", "酱", "糕", "脯", "脆", "酥",
              "味", "片剂", "冲剂", "浓缩", "提取物", "胶囊")
# 只罚**不带括号**的直接后缀：
#   「猕猴桃晶」→ 罚 ✓（冲剂，不是水果）
#   「核桃(干)」→ 不罚 ✓（干了还是核桃，合理的写法）
```

修完重查 → 正确匹配到「猕猴桃」→ `个 70g / 中个 150g(可食124.5) / 小个 90g`。

🔴 **顺带的验收动作**：建完表要查一遍 **`is_liquid=true` 的条目合不合理**。
理论上的液体只有牛奶/豆浆/酸奶/果汁/咖啡/奶茶；**多出来的就是错配**。

## 六、⛔ 已知收不干净的地方（别自己编，让他改）

用户的约束是「**最好在有参考的情况下建**」——所以**薄荷只有一种量词且不合理时，就照实存**：

| 食物 | 薄荷给的 | 为什么不好 |
|:--|:--|:--|
| 蒸蛋 | 盘 200g | 只有「盘」这一个单位 |
| 馄饨 | 袋 500g | 只有「袋」这一个单位 |
| 豆腐 | 块 450g | 一块豆腐整斤，他吃的可能是一小块 |

**处理方式：照存入表，不编替代值**——他碰到时改数字即可（人工核对本来就是最终兜底）。
这比编一个「看起来合理」的假数据好：**编错了会让他多改，且破坏了整表的可信度。**

## 七、架构定稿：**显示层用「个/ml」，底层一律归克**

用户原话：**「你可以把底层逻辑统一成克」**。

| 层 | 用什么 | 例 |
|:--|:--|:--|
| **显示**（他核对） | 个 / ml / g | `2 茶叶蛋 1个`、`3 鲜牛奶 280ml` |
| **计算**（不可见） | **一律克** | 营养按 `edible_g` 算 |
| **换算依据** | 薄荷 `units` 的 `eat_weight` | 他说「2个」→ 查表 → 100g |

`unit` / `count` 只是展示层字段；`edible_g` 始终要填，**两者必须同时给**。
