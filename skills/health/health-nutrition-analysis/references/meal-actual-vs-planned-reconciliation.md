# 「打算吃」评估 → 「实际吃了」落盘：两个阶段的口径与归因

> 2026-11-02 三餐全流程实测（早餐口述 / 午餐照片＋他逐条纠正 / 晚餐外卖单先评估后报实际吃法 / 加餐补报）。
> 这篇补的是现有 references 里没有的一块：**评估阶段与落盘阶段是两套口径，中间必须显式切开**。

---

## 一、两阶段必须先分开，否则就是「打算吃＝已吃」

| 阶段 | 他说什么 | 能不能写档案 | 措辞 |
|---|---|---|---|
| **评估** | 「我在考虑点这个」「按这4个来的话你看适不适配」 | ❌ **一个字都不许写进 diet 档案** | 「**如果**点这单」「**假设**吃下」 |
| **落盘** | 「只吃了8个虾」「米饭都吃完了」「各加餐吃了一个苹果」 | ✅ 立刻写 | 直接陈述，不再加条件式 |

任务书里要写死这一条，否则它会把评估结果当已吃入账。

**做法**：评估阶段的任务书写「这是『打算吃』不是『已吃』，只把结论写在回复里，不许在 `diet/YYYY-MM-DD.md` 新增或修改任何小节」。
落盘阶段再单独派一次活。**两次派活，不要合并。**

---

## 二、评估阶段的交付形态：微调档按影响排序，每档给「省多少卡/多少钠」

他要的不是「这单健不健康」，是**改哪一句备注能变多少**。

正确形态（2026-11-02 实测，他没再要求改）：

```
档 A｜番茄炒蛋备注「少油少糖」（油 20→10g）
  省 90 卡、脂肪 10g。→ 全天 2382（114.8%）
档 B｜A + 米饭减半（180→90g）
  再省 104.40 卡、碳水 23.31g。→ 全天 2277.76（109.8%），碳水回到 91.7% 线内
档 C｜B + 粉丝只吃一半、底汁不喝
  再省 61.78 卡、钠约 −250。→ 全天 2216（106.8%），钠 105.3%
```

硬要求：
- **按影响大小排序**，A 是性价比最高的那条（一句话备注就能改）。
- 每档必须落到**全天百分比**，不是「这顿省 90 卡」——他要看的是对目标的影响。
- **同时给「不推荐怎么改」并说明交换比**。2026-11-02：
  「减虾不建议：少一半省 61 嘌呤，但蛋白一起掉 11.2g——你今天蛋白本来就差 26.62，这个交换是亏的。」
- 只能提**这份订单能改的开关**（备注少油／少饭／不喝汁／粉丝减半），不许写「多吃蔬菜」这类他做不到的空话。

## 三、🔴 他说了实际吃法之后，必须单列「与整盘口径的对照」并归因闭合到 0

这是这轮最有价值的一块。**实际吃法经常离整盘很远**，只报最终数他会不知道省在哪。

2026-11-02 晚餐实测：他不吃粉丝、不蘸汤汁、只吃 8 只虾 → 整盘 1004.70 卡 vs 实际 743.00 卡。

```
热量 −261.70 = 粉丝剔除 −123.55 + 蒜蓉油 15→4g (−99.00) + 生抽 5→2g (−1.95) + 虾 120→80g (−37.20)
钠   −263.88 = 生抽 −195.00 + 虾 −66.08 + 粉丝 −2.80
嘌呤 −70.30  = 虾 −69.60（按基围虾熟 174.0） + 粉丝 −0.70
```

**要求**：
1. 差额必须**逐项归因、合计闭合到 0**，闭合不了就说明漏了一项或换了条目，回查。
2. 一句话总结「这一顿省在哪」——「一半功劳在粉丝没吃（123.55 卡），另一半在油没入口（99 卡）」。
3. **吃法改变会重构口径，不是简单打折**：
   - 不吃粉丝 + 不蘸汁 → 盘里的油**跟着粉丝和汤汁走**，只剩虾表面附着 → 蒜蓉油 **15g → 4g**，不能按比例打折。
   - 不蘸汁 → 生抽只剩表面附着 → **5g → 2g**。
   - 撇汤汁挑菜吃 → 菠菜不再加油盐，只取食材自带钠（他的原话「把汤汁撇掉了没有怎么蘸汤汁」）。
4. 同时给**没变的那一项**：「这顿 +196.68 嘌呤里 122.50 来自虾，但今天嘌呤爆掉是午餐造成的」——
   别让他以为问题在这顿。

## 四、水果「一个」的估重主值（他没给克数时）

他会说「各加餐吃了一个苹果」，不给克数。

| 水果 | 主值可食/个 | 依据 |
|---|---:|---|
| 苹果 | **180 g** | 薄荷 `pingguo_junzhi` units「1 中个 = 210 g 毛重 / **可食 178.5 g**」交叉校验，差 0.8% |
| 小果档 | 150 g | 下方三档下限 |
| 大果档 | 220 g | 上方三档上限 |

**三档必须给**（每个 150 / 180 / 220 g），因为水果大小是他凭手感就能判断的事，摆出来他能一句话定。
2026-11-02 实测三档极差 74.20 卡、碳水差 19.18g，**但结论不变**——所以照主值记、把区间留档即可，不必卡住等他确认。

**苹果核/皮都不额外折算**（皮是吃的）。表1-2「水果类及制品 / 苹果 = 1.0 mg/100g」是直接条目，记 **†** 不走推算。

## 五、🔴 条目自身数据自相矛盾时怎么办（2026-11-02 苹果条目实测）

`pingguo_junzhi`「苹果」：

| 字段 | 值 | 折算 kcal/100g |
|---|---|---:|
| `calory` | **53** | 53 |
| `units`「1 中个，可食 178.5 g」的 `calory` | **111.3** | **62.4** ← 自相矛盾 |

**处理**：以 `calory`（每 100 g 主字段）为准，**不采用 units 里那份 calory**，并在档案里写明
「units 的 111.3 与 calory 53 互相矛盾，本表按 53 记（与中国食物成分表苹果 53 一致）」。

**判据**：`units[].calory` 是薄荷按整份算的预烘焙值，可能与主字段不同源。**逐项可验算的 100g 主字段优先。**

同一个条目的 `calcium` 字段是 **None（未收录）** —— 这时钙要另找来源（本例用中国食物成分表苹果代表值 4 mg/100g），
**并且必须在表下注明「这一格不是薄荷值」**。他要的是每个数都有出处（原话「最好在有参考的情况下建」）。

## 六、验收：`verify_diet_tables.py` 的输出要数张表数

它只认「合计」两个字。写成「加餐合计」「本餐合计」→ 该表被当普通数据行**跳过且不报错**。
2026-11-02 加餐小节踩到：脚本显示通过，实际整张表没验。

跑完先看「N 张表」是否等于当天的小节数，少一张就是被跳过了。详见 `references/health-assistant-delegation.md`。

## 七、全天合计表随新餐次滚动更新

一天里餐次是陆续报的。**新增一餐/一次加餐后，要把「全天合计」那张表整张重算**（加一列、改占比、同步表下自检算式），
不能只在末尾追加一节——否则档案里会同时存在两个互相矛盾的全天口径。

2026-11-02 的演进：早餐+午餐小计 → 加了晚餐 → 再加加餐。每次加都要重算那张表，并在正文注明
「本节替代前面的临时口径」。
