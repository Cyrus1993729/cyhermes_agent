# 「我要看估算过程」——核算过程的可展示化 + 份量口径的迭代

> 实证日期：2026-11-08（11-08 午餐，7 张照片、三人共餐、v1→v3 三轮改口径）
> 关联：SKILL.md 的「回复用户时的输出格式」节；`health-assistant-delegation.md`

## 一、🔴 他要的不是结果表，是**可复算的过程**

原话（2026-11-08）：

> 「我需要你告诉我，每一道菜你都是怎么去估的它的营养素含量。我需要看到你估算的过程。
> 目前我只看到了结果，而且还不是完整的结果。」

**验收要求：只给「菜名 + 克数 + 一行合计」不够。** 哪怕档案里写了「拆：炒鸡蛋 35 g＋蟹肉 15 g」，
他看到的是**两个原料名和一个结果**——中间的「每 100 g 是多少、乘了几次」全缺，所以他判定「不完整」。

### 交付形态（照这个给）

1. **先声明字段顺序一次**：`热量kcal／蛋白g／脂肪g／碳水g／纤维g／钠mg／钙mg／嘌呤mg`（每 100 g）。
   后面所有方括号都按这八位读，不再重复解释。
2. **每道菜一个块**，块内每个原料两行：
   ```
   炒鸡蛋   35g × [149/10/11/1.6/0/145/66/1] ÷100 = 52.15/3.50/3.85/0.56/0/50.75/23.10/0.35
   河蟹肉   15g × [103/17.5/2.6/2.3/0/0/126/144] ÷100 = 15.45/2.62/0.39/0.34/0/0.00/18.90/21.60
   小计           = 67.60/6.12/4.24/0.91/0/50.75/42.00/21.95
   ```
3. **数据来源分三类，每个原料标明**：`薄荷·实时 <code>` / `薄荷·缓存` / `表1-2 <条目名>` / `推算`。
4. **结尾给合计 + 算术自检**（4P+4C+9F）。
5. **单列一节「这套估算里哪几处不可靠」**，按影响从大到小排——不是笼统说「有误差」。
   本次给的是：①6 道菜克数全是估的 ②钠系统性偏低 ③饺子皮是折的不是查的
   ④水饺单重 20 g 是通用值 ⑤表里没有的条目 ⑥钙主要由海参一条撑起。

### ⚠️ 逐行四舍五入会和合计差 0.01

逐行相加 `45.06/66.86/232.17`，合计写的是 `45.05/66.87/232.16`（行级 round 后再加 vs 全精度累加）。
**这不是两套账，要主动说明一句**「逐行四舍五入导致 0.01 差异，不是口径不一」，否则他一眼看出来当错账。

## 二、复用姿势：直接摊开核算脚本的中间量

健康助理每次会把 `每100g 表 P + 拆解清单 MAIN` 写进 `<tool>_calc.py`。**不要重算一遍**，
而是写一个 20 行的展示脚本 exec 它的头部复用 `P` / `MAIN`：

```python
src = open(r'...\_ph1108_calc.py', encoding='utf-8').read()
head = src.split('print("=== 主值逐项')[0]
head = "\n".join(l for l in head.splitlines() if not l.startswith("sys.stdout"))  # ← 关键
ns = {}
exec(head, ns)
P, MAIN = ns['P'], ns['MAIN']
for name, g, parts in MAIN:
    for k, gg in parts:
        contrib = [P[k][i] * gg / 100.0 for i in range(8)]   # 8 字段固定序
```

🔴 **必须剥掉 `sys.stdout = io.TextIOWrapper(...)` 那一行再 exec**，否则它把外层 wrapper 关掉，
紧接着的第一句 `print` 就报 `ValueError: I/O operation on closed file`（本次连踩两次）。

## 三、🔴 份量口径是**他要动的地方**，算法不归他动

### 他调的三类量，各归谁

| 他说的 | 归属 | 做法 |
|---|---|---|
| 「虾球我总共吃了两个」 | **个数** | 立刻改用个数口径（单球重量从整盘毛重 ÷ 个数 反推），**不要再拿「口」套他** |
| 「剩下的每样按 6 口估」 | **口数** | 口数 × 单口口径（荤 20 g / 素 15 g）→ 克；口数是他的判断，换算归你 |
| 「米饭是垫在那道菜下面的，是菜的一部分」 | **结构归属** | 整盘合成一道（菜:饭 按重量比分），再按他那份的比例拆开；**原独立主食行要删掉，不能叠加** |
| 「红色蘸料不用估」 | **删除** | 整行去掉、按 0，并在档案写明「用户明确不估」，别留一行 0 又参与显示 |

### 🔴 口数会来回改，必须留多版本对照

本次 3 口 → 8 口 → 6 口，隔十几分钟一改。做法：

- **旧版数字一个都不删**，档案里按 `v1（三口）/ v2（八口）/ v3（六口）` 并列，注明「被谁取代」。
- 每次重算都给 **v(n-1) → v(n) 的逐字段对比差**，他关心的是「改口数到底动了多少」。
- 敏感性口径跟着换：原来的「保守／宽松」若与新口数不搭，改成 **新主值 ±25%**（表达「一口多少克」本身的不确定度）。

### 「8 口太多了」这类自我修正要顺着接，别辩护

他先说 8 口、几分钟后自己推翻：「我现在感觉我都按 8 口估好像有点太多了，按每样 6 口来估吧」。
→ 直接重算。**不要解释「8 口也有道理」**，那不是他要的。

## 四、三人共餐：这是误差最大的一类，必须三档并列

- 他报了数量的项（水饺、虾球）→ **严格执行他给的个数**，其余一律【估·未确认】。
- 他没提量的菜 → 主值按「N 口」估，**同时给保守档（全 0，只算他报过的）**。
  本次三档 218.95 / 825.68 / 1310.37 卡，**跨度 5.9 倍**——这个跨度本身就是要给他看的信息。
- **油随菜量同比放大时给第二档**：8 口辽参若把油从 8 g 放大到 21 g，要说明这是推算上限，
  另给「油不同比放大」的对照，否则等于把整锅油算到他头上。

## 五、钠永远是虚低的

表1-2 里蟹、虾、蔬菜、米饭**本来就没有钠字段**，全记 0 → 餐厅炒菜盐酱一点没进来。
每份报告都要写：**「钠 xxx 别当清淡，真实值大概率 600–900 mg」**。他会被这个数骗到。
