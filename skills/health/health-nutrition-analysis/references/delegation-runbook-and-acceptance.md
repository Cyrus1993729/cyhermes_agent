# 派活 → 收活 → 验收 的实操执行手册

> 补充 SKILL.md「派活给健康助理」一节。那一节讲**任务书写什么**，这里讲**怎么调用、怎么跑长任务、怎么验收**。

## 🔴 任务书里要它跑的脚本一律给绝对路径（2026-11-05 踩到）

写 `python scripts/verify_diet_tables.py <diet文件>` → 它会回「本机不存在，find 找不到」。
**它的 cwd 不是 skill 目录，也不在 ~/health/scripts。** 正确写法：

```bash
python "C:/Users/Administrator/AppData/Local/hermes/skills/health/health-nutrition-analysis/scripts/verify_diet_tables.py" \
       "C:/Users/Administrator/health/diet/YYYY-MM-DD.md"
```

否则它会自己临时搓一个等价校验器（`~/health/tools/_verifyNNNN.py`）顶上——数算对了，但你要求的「贴回校验器原文」拿不到。
能用的 script 目录在 skill 的 `scripts/` 下：`verify_diet_tables.py` / `verify_diet_table.py` / `verify_meal_rows.py` / `verify_plan_tables.py` / `verify_tdee_table.py`。

## 一、调用姿势（一次就对）

```bash
# ✅ 长 prompt 走文件，-Q 是布尔开关
hermes -p health chat -c "Bot Chat" -Q --query-file "<绝对路径>.txt"

# ✅ 短 prompt 内联
hermes -p health chat -c "Bot Chat" -q "<一句话>"
```

- `-q/--query` 才是**装问题**的参数；`-Q/--quiet` 是**布尔**（安静 + oneshot）。
  写成 `-Q "问题"` 会报 `unrecognized arguments: ...`——踩过一次。
- `--query-file` 优于内联：不做任何 shell 解释，引号、`$(...)`、反引号原样保留。
- 健康 profile 有独立 session（`-c "Bot Chat"` 续用同一会话），跨轮上下文在它那边保留。

## 二、跑长任务：后台 + 落盘 + 轮询

一次完整的餐次核算/收盘要 **4–8 分钟**，超过 terminal 前台 600s 上限。固定做法：

```bash
hermes -p health chat -c "Bot Chat" -Q --query-file "<任务书>" \
  > "<输出文件>.txt" 2>&1
# terminal: background=true + notify=true
```

然后在**另一条** terminal 调用里 `sleep N` 后读输出文件。判断进度不能只看输出文件（它跑完才写），
要看**档案 mtime**：`ls -la ~/health/diet/YYYY-MM-DD.md` 变了就说明它已经在写了。

## 三、验收义务：它的自述不算数

按这个顺序做，缺一步就别报给用户：

1. **回到源头核 per-100g 值** —— 读 `~/health/fooddb/boohee_api/cache.json`，按 **code** 取字段，不信它转述的。
2. **按 code 复核 units，不要按名字搜** —— 实测 `public_units("西兰花炒鸡胸肉")` 命中的是
   「西兰花炒鸡胸肉(少油少盐)」300g/70 卡（匹配分 92），而正确条目是 `老乡鸡 40a9eac7…` 220g/94。
   **凡品牌 SKU，一律用 code 复核份量。**
3. **自己按 `每100g × 克数` 重算全部列**，不采信它给的合计（差 0.02 这种四舍五入要能解释）。
4. **跑 `verify_diet_tables.py` 扫全部表**，不是只看它说「全绿」。
5. 🔴 **每一列都要问「这列数从哪来」**——不只是热量蛋白脂肪。
   2026-11-03 午餐验收时我只核了 cal/P/F/C/纤/钠 六列，没追问钙列；事后才发现
   **薄荷 `public_detail` 根本没有 `calcium` 字段**，钙其实来自成分表同名条目、却被写进了「薄荷·免费 code」标签里。
6. 🔴 **逐行核嘴呤标记 † / ‡**：`purine_table12.json` 里 `_ALIAS` 命中的（鸡腿→乌鸡肉173、鸡胸→鸡肉208、
   鸡蛋→鸡蛋(熟)1.0）一律是 **借同类＝‡**，不是 †。2026-11-03 晚餐把鸡腿标成 † 是错的。

> 另：`verify_diet_tables.py` 报「钙: N/M 行不是数值」＝表里有「—（未收录）」，**属预期，别改成 0**。
> 只要看它那行 `重算 [...]` 与合计行逐项对得上就算 PASS。

## 四、🔴 它报的「工具 bug」要先复现再认

2026-10-30 它报「`verify_diet_tables.py` 无法处理带 †/‡ 标记的表格，会静默跳过」。
实测：脚本的 `_num()` 本来就 `.replace("†","").replace("‡","")`，**根本没有这个缺陷**。
它误判的真实原因是**它第一次跑的时候晚餐表还没写出来**，只看到 4 张表。
→ 收到「工具坏了」类反馈，先自己跑一遍复现；复现不了就明确告诉用户「这条是误判，不用改」。

## 五、🔴 任务书里我写的断言，它可能会当真并据此出错

2026-10-30 我在任务书写「早餐蛋白密度 3.92 最低」（错误，最低是加餐 3.28）。
**它没照抄**，按实测值写并标了纠正——但这是运气，不是保证。
→ **派活前自查任务书里的每一个数**；它顶回来纠错时，公开认下来（用户在场时这条很重要）。

## 六、任务书不必重述已知口径，但必须重述「本次的特殊判断」

例：老乡鸡同款套餐吃过两次、档案里已有官方 units —— 这条**必须写进任务书**，
不写它大概率按图重新估重（估重 vs 官方 units 一天钠能差 1670 mg）。

## 七、🔴 肉/菜类餐次的任务书必须带「三问」，并提前锁好对比口径

派活前把这三条写进任务书（他凭常识就能答，不须等）：

1. **带皮还是去皮？**（带皮鸡腿 11.0 g/100g 脂肪 vs 去皮 4.2，300 g 差 20 g 脂肪 / 179 卡）
2. **生重还是熟重？**（杂粮饭 180 g 生 vs 熟差 417 卡）
3. **去骨净肉还是带骨？**（薄荷 units「1 只带骨 120 g／可食 88.8 g」＝ 74%）

并且**同一锅油不得算两次**（煎完沥油再炒配料 → 油只算一项），他 2026-11-03 亲自纠正过。

→ 完整案例、带皮条目选法（国标「鸡腿」091113 的 7.2 是偏瘦口径）、嘴呤 †/‡ 错误实例、
胆固醇口径分歧、以及**他问「比我以前那些天低吗」时怎么从 diet/ 历史建排序表**，
全在 `references/meat-cut-oil-and-cross-day-comparison-2026-11-03.md`。

## 八、双脑分工：他凭常识纠正时，直接照改并留改正记录

2026-11-03 两处他当面纠的：
- 「黄皮还是有皮的」→ 主值该换档，不是解释为什么原来那样估
- 「油估多了，两个保留一项就可以了」→ 删重复项

做法：**先改数字、再留一行「YYYY-MM-DD 他本人纠正：……」写清原值与修正值**，
然后把变动项 + 新合计重新报一遍（不要把整表再抄）。
他要的不是解释，是改后的数。

## 九、🔴 回执必须逐项全抄，一个字都不能省（2026-11-05 被当面投诉）

**事故**：午餐派活回来，我把健康助理的 8 行逐项明细**压成一行「今日档案 10796 bytes，早+午合计 679 卡」** 发给他。
他直接回：**「没有看到午餐的回执」**。

**根因**：把「档案已落盘」当成了交付物。他要的是**每一行吃了多少、每项数据从哪来、哪些数是估的**。

**铁律**：
1. 回执的**逐项行必须原样转述**：`食材 克数｜热量｜蛋白｜脂肪｜碳水｜纤维｜钠｜钙｜嘌呤｜〔数据来源标签〕`，一行不少。哪怕有 9 行也要全发。
2. 合计、自洽校验、参数备注（假低值改数、拆原料推定比例、未收录记「—」不记 0）**全部保留**。
3. **可以另外加**一段我的解读（哪项超、哪项是主因），但**不能用解读替代明细**。
4. 一条消息发不完就分段，不要为了塞进去而砍明细。

> 判断标准：他看完这条，能不能指出「第三项你算错了」。指出不了，就是没交付。

## 十、🔴 任务书引用 skill 里的 reference 文件名，必须逐字核对

**事故（2026-11-05）**：我在任务书写「按 `references/boochie-entry-selection-pitfalls` 的口径处理」。
正确文件名是 **`boohee-entry-selection-pitfalls.md`**（b-o-o-h-e-e，薄荷拼音）——我打错两个字母。
健康助理回「skill 目录里没找到这个文件，现有 references 是 …等 7 个」。

**后果**：看起来像 skill 坏了、要「修掉」，实际是我打错字。差点误改技能。

**做法**：
- 任务书里引用的 reference，**从 `references/` 目录实际 ls 一遍全名再复制**，不要凭记忆打。
- 收到「文件不存在」时，**先核对是不是自己拼错**，再判断是不是技能缺文件。
- 全量校验命令（查技能正文里引用了但实际不存在的文件）：解析 SKILL.md 里的 `references/xxx.md`，逐个 `os.path.exists`。
  ⚠️ 会被误报：`profile.md`、`MEMORY.md`、`USER.md`、`YYYY-MM-DD.md`、`_raw_ocr.md`、`xxx.md` 是**运行时数据文件名示例**，不是技能文件，不算失效。
  跨技能引用（A 的正文引用 B 的 references）也算正常，只要文件在全库某处存在即可。

## 十一、🔴 它报「文件被别的改动改过了」——先溯源，别急着重写

**场景（2026-11-05 晚餐落盘）**：健康助理在回执末尾主动告警「早餐节的燕麦纤维/钠/钙被另一处改动改过，标着『用户要求修正』，我没回滚」。

**正确处置**：
1. **先查** `~/AppData/Local/hermes/state.db`（主 profile）和 `profiles/health/state.db` 的 `messages` 表，按 `content LIKE '%关键词%'` 找谁改的、什么时候改的。
   ```python
   import sqlite3, datetime
   c = sqlite3.connect(r'C:\Users\Administrator\AppData\Local\hermes\state.db')
   cur = c.cursor()
   cur.execute("SELECT role, timestamp, substr(content,1,200) FROM messages "
               "WHERE content LIKE '%2346397%' ORDER BY timestamp ASC")
   ```
   本次一查就清楚：**08:47 用户本人说「钢切燕麦的纤维含量改一下」**，改在 08:45 —— 合法变更，不用回滚。
2. **确认是用户要求的 → 保留，并把溯源结论告诉他**（「这是你今天早上亲口让改的」），别让他以为档案被污染。
3. **确认不是用户要求的 → 才停下来问，不要自己回滚**（回滚会覆盖可能真实的修正）。
4. 受影响字段要**逐项列出来**（哪些变、哪些没变）。本次：纤维 / 钠 / 钙 变，热量/蛋白/脂肪/碳水/嘌呤 一个数没变——这个区分他很在意。

## 十二、落盘后必检：档案头部状态行有没有跟着更新

`~/health/diet/YYYY-MM-DD.md` 第 3 行是状态行。
**事故（2026-11-05）**：全天都收盘了，头部还写着「状态：**进行中**（仅早餐已入档；午餐/晚餐/加餐/运动均未报）」，与文末汇总表直接矛盾。

**做法**：每次落盘收尾，`sed -n '1,5p'` 看一眼状态行；
餐次变化后改成 `> 状态：**已收盘**（早餐 / 午餐 + 加餐 / 晚餐均已入档；运动未报）。全天口径与差额见文末汇总表。`
同时核对 `## ` 小节列表是否与实际餐次一致。

## 十三、🔴 派生统计量（均值/中位数/名次标签）必须主 Hermes 自己复算（2026-11-10 实抓 4 处）

逐项营养表它有 `verify_diet_tables.py` 兜底，**但「派生统计」没有任何校验器** —— 均值、中位数、排序名次、
「第 X 高/低」这类标签，是它自己拼的，实测**四类错**：

| 错法 | 实例（2026-11-10 评价） | 正确值 |
|---|---|---|
| 表内 14 行相加不等于均值 | 脂肪均值写 85.55、碳水 190.85、嘌呤 685.81 | 84.03 / 192.86 / 703.61 |
| **名次高/低写反** | 「摄入 1848.29 第 10 **低**」 | 应第 10 **高**（即第 5 低） |
| **「中位数」取成上中位数** | 摄入 1977.95、蛋白 120.61、纤维 12.67 | 真中位数 1974.03 / 111.50 / 11.99 |
| 排除理由与档案事实不符 | 「11-02 未写入赤字」 | 11-02 已收盘，按休息档 PAL 1.20 算成**盈余 −290.46**，性质不同才排除 |

**做法：**
1. 收到含均值/中位数/名次的回执，**用 `statistics.median` 与 sorted+index 重算一遍**，别目测。
2. 名次一律同时报「第 X 高 / 第 Y 低」，单写一个方向必然会被写反。
3. 逐日历史数值要**回源** `diet/*.md` 的「全天合计」表抽查（本次抽查 10-31 / 11-04 / 11-05 / 11-06 / 11-08 全对，错的只在派生层）。
4. 订正后**在 reviews 文件末尾追加「修订留痕」节**（写明原值→新值→原因），不要静默改；
   同时声明「未改动的部分」清单（结论、来源拆解、逐日数值），否则他无法判断改动范围。

### 🔴 附带：「方案对比表」的加和比主表更容易算错（2026-11-11 实踩）

主营养表有校验器兵底，**但「如果要补 X，吃这些行不行」这类推演表没有任何校验器**，而且它经常把同一个食材
在多个方案里复用——**复用就会重复相加**。

实测（11-11 补纤维方案）：
- A＝木耳水发 250 g ＋ 蓝莓 150 g，原写「+220.5 卡」，实际 **+153.0**（木耳 250 g 的 67.5 卡被算了两次）
- C＝菠菜 300 g ＋ 木耳 200 g，原写「+234.0」，实际 **+180.0**（木耳 200 g 的 54.0 卡重复）
- B 原本就是对的（+242.0）——**一错一对混在同一张表里，不逐个算就发现不了**

**后果不只是数字错**：A 修正后赤字 416.10 **仍在 400–550 带内**，原文「三个方案都会跌破 400」
的结论方向直接被推翻——**一个加和错能把结论从「两者不可兼得」翻成「可以兼得」**。

**做法**：推演表逐行按「克数 × 条目值」重算一遍，特别注意**同一食材出现在不同方案**时不要跨行相加；
订正后在文件末尾追加修订留痕。

## 十四、🔴 只读评价类任务的边界

### 🔴 附带："成品重"与"逐项克数"永远对不上（2026-11-11 实踩）

他报的是**一道菜的成品总重**（如「杏鲍菇牛肉 150 g」），拆原料时又单列了**推算烹调油**；
而成品重本身已含油 → 逐行克数相加必然大于合计行。

实测：五盘成品 660 g，逐项相加 681.90 g，差 21.90 g = 三笔推算油（7.5＋8.4＋6.0）。

**做法**：合计行克数保留他报的成品总重，**在表格图例里补一句差在哪**；
热量/营养素按逐项行累加，不受影响。**不要为了凑平方而把油从逐项里删掉**（删了热量就少算）。

他让「评价一下今天的饮食」时，产物是 `reviews/YYYY-MM-DD_<主题>.md`，**`diet/` 下的档案一个字都不许动**。
验收时核对两件事：① diet 文件 bytes 与 mtime 未变；② 评价文件里没有「额度/预算」式表述、
没有 App 定性标签、没有脱脂奶/蛋白粉建议、没有「建议你…」段落。

## 十五、🔴 他说「跟之前一样」＝ 回源历史档案取口径（2026-11-10）

- 问「黑虎虾 500 g 是带壳毛重还是净虾肉」→ 「**带壳称的毛重，跟之前的白灼黑虎虾都是这个口径**」
  → 回源 2026-10-24 定稿：毛重 × **出肉率 55%**（薄荷 `fdbef4a3` units：1 只 60 g 毛重 / 33 g 可食）。
- 问「沙拉有没有加酱」→ 「**跟之前的做法一样，你让他参考一下之前的做法**」
  → 他说的「之前」是 **无沙拉酱、但加薄盐生抽 8 g ＋ 木姜子油 3 g ＋ 醋 3 g**（11-04 / 10-24），
    **不是「无酱就完事」**。按字面理解会漏掉 341.6 mg 钠与 27 卡。

**做法**：派活前 `grep` 历史 `diet/*.md`，把「同一口径」的具体数字直接写进任务书，不让他重复报一遍。

## 十六、🔴 他的自评只覆盖四项，复核时必须补全后三项（2026-11-10）

收盘后他会主动自评，句式固定：热量控制住了 / 脂肪相对低 / 蛋白理想 / 碳水不错 → 「整体比较理想」。
**实测这四项方向全对（4/4），但系统性漏掉钠、蔬菜、纤维三项** —— 而那三项正是当日常见的短板
（当日钠 170%、蔬菜 52%；纤维反而是长板，12 天第 3 高）。

**复核规矩：**
1. 逐条给 **成立 / 部分成立 / 不成立** ＋ 数据，**不许附和**（他要的是评估，不是认可）。
2. 赤字说「合理范围」时用**四档参照**：推荐带 400–550、摄入目标、他自己历史的均值/名次、有无运动加持。
   当日三档指向「偏少」，只有「确实有赤字」这个方向成立。
3. **补全未提到的项**，句式用「你这四项都成立；同一份档案里另外三项是这样的数字…」，
    **不用「你忽略了」**。
4. 单项支撑要拆开说：当日 46.5% 蛋白来自虾，拿掉只剩 70.17 g（54.4%）—— 区分「单点支撑」与「稳定输出」。
5. 收口必须回答「他的自评准确率」：几条成立、几条部分成立、总结在什么范围内成立。
6. 他自己报的数可能比结论更准（当日「300 多大卡」→ 实际 350.46），该认就认；
   **我转述它的百分比也要复算**（当日把 36.9%＋15.7% 转成 53.6%，实为 52.6%）。

## 十七、🔴 多菜餐次的拆解流程审计

## 二十、🔴 校验器不报的格式坑：合计行加粗会串成 `****X**`（2026-11-12）

`verify_diet_tables.py` 只看数值，**不管 markdown 语法**。2026-11-12 早餐的合计行写成：
