# 派活回执的交付与任务书卫生

> 来源：2026-11-05 午饭记账实战（主 Hermes 派给 health profile，用户追问「没有看到午餐的回执」）。

## 🔴 铁律一：核算回执必须**逐项完整贴出**，不能压成摘要

**实际踩的坑**：午饭派活跑完，我在正文里只写了一句「午饭已落盘（10796 bytes，早餐+午餐合计 679 kcal / 蛋白 35.8g / 嘌呤 338.6mg）」，把逐项明细省了。随后用户又追加火龙果，我报了追加的完整明细——**然后用户说“没有看到午餐的回执”**。

原因不是他漏看，是**后一条承前的回执不能代替前一条的回执**。用户脑子里的“午饭”是那 8 行菜，不是那个合计。

**规则**：
- 每一餐/每一次核算的派活回来后，**原文结构化输出**：逐项一行（菜名/克重/热量/蛋白/脂肪/碳水/纤维/钠/钙/嘌呤）+ 合计 + 参数备注。
- **后来追加的项目（如餐后水果）不代替原单**——两单都发。
- 他说的「极简」= 不要长篇分析和说教，**不是“把明细删掉”**。他明确要「逐项一行+合计+参数备注」「极简≠省字段」。
- 如果确实已经把两单合在一起报了，**要显式说明**：「以下合并了午饭 + 火龙果」，否则他会以为午饭那份没发。

## 🔴 铁律二：任务书里引用 reference 文件，**必须核对全名**

**实际踩的坑**：任务书写 `references/boochie-entry-selection-pitfalls`（把 boohee 拼成 boochie），健康助理照实报告「找不到这个文件」，反引发一轮排障。预算被浪费在一次拼写错误上。

**做法**：
- 写任务书引用文件时，用 `search_files` 或 `ls` 核对一次，别凭记忆抄。
- 常用文件名速查：`boohee-entry-selection-pitfalls.md`（b-o-o-h-e-e，**不是 booch**）、`tdee-deficit-calibration.md`、`user-health-baseline.md`、`provenance-and-match-traps-2026-10-21.md`。
- **反过来**：健康助理说「文件不存在」时，先怀疑自己打错字，再怀疑技能坏了。本次扫了三个 skill 的 41 条引用，**0 条失效**，全是我拼错。

## 🔴 铁律三：主 Hermes 只派活，不做健康判断

派活时任务书应包含：
1. **事实**：菜品/克重/时间；明确标「**实际已吃，不是打算吃**」（这条不能省，他对此被纠正过）。
2. **口径**：不要自创规则，让他按 SKILL.md 正文既有口径处理。
3. **产出要求**：每项带来源标签（条目 code / match_name / quality）、不要估值凑数、查不到就说查不到。
4. **验算要求**：写入后从磁盘读回验算，确认落盘内容与核算一致。
5. **真实/测试标记**：真实饮食写真实档案；测试必须标「测试数据勿写真实档案」或给隔离路径。
6. **极简输出**：逐项一行 + 合计 + 参数备注，不要长篇分析。

## 🔴 铁律四：派活用 background + notify，**结果文件比进程状态可靠**

- `hermes -p health chat -c "Bot Chat" -Q --query-file <file> > out.txt 2>&1`，background=true + notify=true。
- 首行会有 `Warning: Unknown toolsets: a2a` 和 `↻ Resumed session ...`，**都是无害的**，不要在报告里当异常。
- 后台完成通知到达时，**产物早已可取**——通知只是确认，不是触发。先看 out.txt 有没有内容。
- 提取时清 ANSI：`re.sub(r'\x1b\[[0-9;]*[a-zA-Z]','',raw)` + 剔控制字符，否则 `read_file` 判 binary。
- **用户催「没看到回执」时不要重跑**——结果就在 out.txt 里，取出来重发即可。重跑会重复写档案。

## 交付时的“必须点名”三项

每个回执末尾都要有：
1. **落盘文件 + 字节数**（证明真写了）。
2. **验算结果**（逐行 vs 合计是否一致、4P+4C+9F 偏差百分比）。
3. **当天的付费额度消耗/剩余**（他关心成本）。
