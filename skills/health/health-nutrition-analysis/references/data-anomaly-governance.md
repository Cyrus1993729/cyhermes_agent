# 食物库异常值处理：排除 + 留痕，不篡改数值

> 2026-11-17 实踩。维生素 E 这个坑踩了两层：先误判，再误修。

## 坑的完整过程

1. 算今天维生素 E 得到 31.74 mg（AI 14 mg 的 227%）——**一眼就可疑**。
2. 拆开后发现 28.00 mg 来自素鸡（16.91）和香干（11.09），豆制品条目报的是 17.8 和 15.85 mg/100 g。
3. 第一反应（错的）：「豆制品不可能有这个量级，判条目录入错误，改掉」。
4. 交叉校验后被打脸：**这两个值忠实抄自《中国食物成分表》**（素鸡 17.8；豆腐干(酱油干) α-TE 16.41）。
   → 可疑的是**成分表本身这一项**，不是录入过程。

## 正确做法

```
有出处 → 不能改数值。只能把它排除出计算 + 把原值留痕。
无出处 → 标「缺录 null」，不许用均值/估算填。
```

**为什么不能硬改**：薄荷 `public_detail()` 是每次实时拉 API，本地没有可写的权威库
（`cache.json` 只缓存付费接口结果）。硬改缓存会被下次拉取覆盖 = 假修。

## 已验证的实现（健康助理侧）

```
health/tools/anomaly_fix.py            覆盖层：读到条目后把 status='excluded' 的字段置 None
health/tools/boohee.py:216 起            在 public_detail 返回前调 anomaly_fix.apply()
health/fooddb/anomaly_registry.json    登记表（code/name/field/original/status/reason/source_check）
health/tools/DATA_ANOMALY_RULES.md     规则文档（阈值表 + 五步处理顺序 + 四条铁律）
```

新增异常只改 json，不改代码。改 `boohee.py` 前先备份（`.bak_<时间戳>_pre_anomaly`）。

## 三类问题要分开（不要都当「错误」）

| 类型 | 例子 | 处理 |
|:---|:---|:---|
| **真 0** | 油的蛋白/碳水/纤维/钠；肉的纤维 | 保留 0，不标异常 |
| **缺录** | 蔬菜 `fiber_dietary = 0`；燕麦 `kalium` 空；所有条目 `sugar` 字段空 | 置 null，不许静默记 0 |
| **可疑值** | 豆制品 VE > 10 mg/100 g；燕麦片脂肪 0.2（应约 7） | 保留原值但标 suspect，不得单独作结论 |

## 量化判据（可复用）

```
VE/脂肪 > 1.0 mg α-TE/g 脂肪 → 超过任何食用油脂量级，判可疑
  （素鸡：17.8 mg / 12.5 g 脂肪 = 1.42 mg/g → 可疑）
```

## 汇报纪律

- 每轮回执必须带一节「数据完整性检查」，分三块写：真 0 / 缺录+已补(借同类 ‡) / 可疑已排除
- **主 Hermes 自己说错了也要认**：这次主 Hermes 跟着健康助理说「豆制品不可能有这个量级」，
  后来被推翻，必须向用户明说「我之前那句是错的」，不能悄悄改口。

## 用户明确要求的长期规则

> 「以后如果再吃类似的东西的话……如果以后再问你的话，你要能就是记住碰到这种数据要修正错误。」

所以碰到异常值：**先判异常 → 交叉校验 → 有据则排除/无据则标缺录 → 当次不参与结论 → 回执明写 → 登记入表**。
每修一条登一条，登记表是资产，不能只修不记。
