# 派活回执转述 与 落盘闸门（主 Hermes 侧规范）

> 适用范围：主 Hermes 把饮食核算派给健康助理（`hermes -p health chat -c "Bot Chat" -Q --query-file`）之后，**如何把回执转给用户**、**什么时候可以直接落盘**。
> 健康判断本身不归主 Hermes，但「转述」和「闸门」是主 Hermes 的职责。
> 来源：2026-11-05 / 11-06 / 11-07 连续三天的实踩。

---

## 🔴 铁律一：回执必须**逐项全文转述**，不许压成摘要

**实踩（2026-11-05）**：午饭派活结束后，我只回了一行摘要——「午饭已落盘（679 kcal / 蛋白 35.8g / 嘌呤 338.6mg 已超线）」。用户立刻回：**「没有看到午餐的回执」**。

他的真实需求是：**每一项一行 + 数据来源标签 + 参数备注**，不是汇总数字。摘要等于没给。

**正确做法**：健康助理返回的逐项行，**逐字搬运**给用户，包括：
- 每一行的：食材名 / 克数 / 热量 / 蛋白 / 脂肪 / 碳水 / 纤维 / 钠 / 钙 / 嘌呤
- 每行的 `〔来源标签〕`（薄荷 code、表1-2、标签换算、推算）
- 参数备注（改了数的、估的、缺字段的）
- 自洽校验百分比
- 剩余额度
- 红黄绿超限项

**允许压缩的只有**：健康助理的过渡废话、「好的我来帮你」这类过程话术、重复段落。**数据行一个都不能省。**

> 判断标准：他要能拿着你这条消息，直接对档案里的表逐行核对。做不到就是没给回执。

## 🔴 铁律二：落盘闸门看措辞，不看心情

| 用户原话 | 含义 | 你的动作 |
|---|---|---|
| 「让健康助理**记一下**」/「**记一下**我的午饭」 | 已授权落盘 | 直接派活 + 落盘，回执照常给 |
| 只描述吃了什么（「晚饭吃了两小碗白米饭…」） | **没说记** | 派活时明写「**本轮只出核算稿，不落盘**」，出稿后等确认 |
| 「估算完以后**发给我确认**」 | 显式确认闸门 | 同上，并且必须给保守/主值/宽松三档 |
| 「按主值记」/「就按这款存档吧」 | 确认完毕 | 派第二轮，**参数逐项照抄，不许重算** |

**依据**：memory 里长期规则是「核算/产出类先返回结果、他确认后才落盘」。「记一下」是显式的例外授权，其余一律走确认闸门。

**派活任务书里必须显式写这一条**，否则健康助理默认会直接写档案。

## 🔴 铁律三：任务书里引用 references 文件名，必须**照抄不手打**

**实踩（2026-11-05）**：我在任务书写了 `references/boochie-entry-selection-pitfalls.md`，正确的是 **`boohee-`**（薄荷的拼音）。健康助理回复「skill 目录里没找到这个文件」，我一度以为技能坏了，去扫了全量引用——结果 41 个引用**全部有效**，是我打错字。

**做法**：写任务书时，references 文件名从 skill 里复制，不要凭记忆敲；引用后如果健康助理报「找不到」，**先怀疑自己拼错**，不要先怀疑技能缺文件。

---

## 🔴 铁律四：截图要分清「订单页」和「商品详情页」——后者才告诉你碗里有什么

**实踩（2026-11-07）**：午饭先给的是**订单页**（只有菜名 ×2、金额），我按「馄饨 + 汤 + 生煎」算了。用户随后补发**商品详情页**，图里清楚显示碗中还有**面条、金针菇、青菜(菠菜/生菜)、番茄块**——整整漏了四样。

**做法**：
- 只拿到订单页 → 派活时明写「**本单只有订单页，碗内配菜未知；请按菜名解析，并在档案里标『配菜未计入』**」。
- 拿到商品详情页 → 认真看配图里的**每一类食材**，逐个列进任务书。详情页的卖点文案也常有用（本次「不加一滴番茄酱」→ 影响钠的估计）。
- 漏了之后要**做加法补记，不动已落盘的口径**：明写「这是漏项，不是口径变更」，避免健康助理重算全餐。

## 🔴 铁律五：同一笔歧义，用第二张单据交叉核对

**实踩（2026-11-07）**：早餐外卖生煎显示 `×2` + 「2只起购」，无法确定是 2 只还是 4 只。下午堂食订单是**同店同品**，原价 ¥8 ×2（外卖是 ¥12 ×2）——两单价格不同但都是「只」计价，**由此确认 ×2 = 2 只**，早餐记录正确，「若为 4 只」的备用口径当场作废。

**做法**：同一店铺/同一商品的第二张单据，是解开数量歧义最便宜的办法。看到 `×N` + 「N起购」这类拍不平的写法，**先找有没有第二张图**，别再问用户。

## 🔴 铁律六：「口」「小碗」这类生活单位，必须把换算依据摆给用户看

用户会用「四口肉片」「两小碗米饭」「食指长的春卷」描述。换算规则要**有依据 + 可被他复核**：

- 先在他的历史档案里找同单位记录（如 11-04「包菜 2 口 = 30 g」→ 素菜 15 g/口）。
- 不同形态要调（薄肉片 ≠ 肉块：肉块 20 g/口，薄片 12 g/口）。
- 换算表**逐条写进回执**，让他能一眼说「4 口不对，是 5 口」。
- 给保守/主值/宽松三档，并写明「三档差多少、差在哪一项」。

## 交付模板（照这个顺序写回执）

```
【来源】店铺 / 堂食 or 外卖 / 金额（有截图就标）

【逐项】
食材名 克数｜热量｜蛋白｜脂肪｜碳水｜纤维｜钠｜钙｜嘌呤〔来源标签〕
（每项一行，一项不漏）

【合计】总克数｜八项合计
自洽校验：4P+4C+9F vs 热量 → ±X%

【全天】早+午(+加餐+晚)｜对照 profile.md 的剩余额度

【红黄绿】逐项，超线的点名最大来源

【参数备注】改过数的 / 估的 / 缺字段记 0 不是真零 / 两档备用口径

【不确定项】它自己列的，原样转述
```

## 反向检查：他质疑时先看是不是自己漏了

- 他说「没看到回执」→ 复查你是不是发了摘要而非逐项（本文件铁律一）。
- 他说「XX 比例不对」→ 那是你派活时**用「家常做法」推定**而不是问他。立即改成问「肉占几成」，并在档案里留痕「原推定被用户否定，以后不用家常比例推定」。
- 他说「算法别变了」→ 多轮核算**不许中途换条目**；已在用的条目 code 要原样沿用，换条必须有硬理由并写进档案。
