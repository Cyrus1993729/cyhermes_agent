# 主 Hermes → 健康助理 派活规程（2026-11-17 实趟提炼）

> 适用：主 Hermes 收到**饮食/营养/体检指标**类请求时。主 Hermes **不做核算，只派活 + 转述回执**。

## 0. 路由判据（先判再动）

| 请求类型 | 归属 |
|:---|:---|
| 报餐、核算、记账、饮食建议、体检指标解读、食材选型（哪个好/该不该吃） | → 健康助理 |
| 帮规程/流程本身的问题（如「是不是都该交给健康助理」） | → 主 Hermes 直接答 |
| 帖子/视频内容抓取（如小红书食谱） | → 主 Hermes 自己干（这是抓取，不是核算），抽完交给健康助理 |

## 1. 派活命令

```bash
cd ~ && hermes -p health chat -c "Bot Chat" -m deepseek-v4.1-flash -Q \
  --query-file "C:/Users/<user>/AppData/Local/hermes/cache/query_<主题>_<日期>.txt" \
  > "$LOCALAPPDATA/Temp/health_<主题>.txt" 2>&1
```
- **必须 `background=true` + `notify=true`**，否则单次调用可达数分钟。
- 任务书写入**绝对路径的 .txt**，用 `--query-file`，**不要用 `$(cat)` 内联**（长 prompt + 中文会被截/转义）。
- 会话是累积的（`-c "Bot Chat"`），它会记得上一轮——所以任务书里要明写「上一轮/本轮」的先后关系。

## 2. 任务书必含项（模板骨架）

```
【任务：<一句话>】
## 一、日期与档案
  - 今天：YYYY-MM-DD（周X）
  - 当日档案绝对路径 + 字节数 + mtime
  - 档案已有小节列表（## 早餐 / ## 午餐 / ## 加餐 / ## 今日汇总）
  - 本轮要新增的是哪节 / 哪节尚不存在
## 二、用户原话（逐字，未改写）
  > ……（一字不改地搬）
  > 随后补正（以这条为准）：……
## 三、物料/包装信息
  - 图片路径（让它自己走 recognize.py 读，不要用主 Hermes 的识图结果当家）
  - 主 Hermes 只给「定位提示」，不作为数据来源
## 四、口径（最容易被忽略、也最容易出错）
  - 哪些量以用户口述为准（即使与包装标签冲突）
  - 哪些量由它估（调料、单重换算），估的要标〔估算〕
  - 是否分份（吃了一半 / 剩一半）
## 五、禁止项
  - 本轮只核算不落盘（或：只研究不落盘），列出不许改的文件
  - 不写劝诫、不评食谱好坏、不给改进建议（他没问）
  - 不许把「打算吃」的算进合计
## 六、交付格式
  - 结论先行
  - 逐项一行，字段齐（热量/蛋白/脂肪/碳水/纤维/钠/嘌呤）
  - 每行带来源标签〔薄荷·实时〕〔表1-2 †/‡〕〔档案例行〕〔估算〕
  - 单列「数据完整性检查」和「换算过程」
  - 收尾自报「本轮没有写任何文件」+ 回读字节数作证
```

## 3. 两段式铁律（必须遵守）

```
① 派活：只核算、只出稿，不落盘
② 呈报：回执原样贴给用户（不压摘要）
③ 落盘：用户显式说「写」之后，才派第二个任务书让它追加进档案
```
用户没点头写 = 档案字节数必须不变。验收方式：让它回读 `diet/YYYY-MM-DD.md` 的 bytes + mtime 自证。

## 4. 实踩坑（每条都栽过）

### 4.1 不要替健康助理报数据，哪怕你「凭常识」知道
主 Hermes 在任务书里写「橄榄油约 884 卡，差 −0.48 卡」，健康助理查库后纠正：通用条 `ganlanyou` 是 **899**，884 是另一个品牌条。
→ **任务书里只给「要它查什么」，不给「答案应该是多少」。** 主 Hermes 随口报的数会污染它的口径。

### 4.2 用户复述 ≠ 与档案矛盾，先算再说「矛盾」
用户说「我相当于吃了一整个西红柿」，而档案写「2 个 ×164.9 g 可食 ÷ 2 = 165 g」——
**这是同一个数**（一半 = 1 个），不是矛盾。主 Hermes 却在任务书里标成了「矛盾点」，差点让它去多算一份。
→ **发现「看似不一致」时先除一遍/乘一遍**，确认真的分母不同再报。

### 4.3 「打算吃」「一会吃」绝不进统计
用户说「一会儿我还打算再吃一点无糖酸奶拌黑莓」——
→ 只做推演并明标「未计入」，今天合计不变。任务书里要把它写成硬禁止项（最容易违反）。

### 4.4 档位由用户拍板，不由 Agent 推断
「猪肉是纯瘦还是肥瘦相间」这种问题，**只有他能凭肉眼判断**。
- 可以摆两个档位给他选（纯瘦 501 卡 / 肥瘦 +189 卡）
- 他一旦拍板，**下轮任务书必须写「这一条关了，不许再挂备选」**——否则它会每轮都把备选拎出来。

### 4.5 禁止和稀泥结论
问「A 和 B 哪个好」时，写「两个都重要」「换着吃就行」会被直接退回。
→ 任务书要硬性要求：`结论：推荐 X。理由是（1）…（2）…。但如果你更在意 Y，可以选 Z。`

### 4.6 不许把「机制」当「疗效」
→ 任务书要求它对每条机制标证据强度：**「有明确证据」/「有机制但证据一般」/「证据不足」**。

### 4.7 库字段缺失是常态，让它写「无数据」而不是硬填
糖（sugar 字段常空）、维生素 K / 叶酸、花青素 / 多酚、饱和脂肪——库内基本都是空。
→ 任务书要明写「库内无此字段就写『库内无此字段，未取』，不许拿通用均值硬填」。

### 4.8 已入档的餐次不许重估
用户要「今日汇总」时，已入档的三餐要**直接搬运档案里的数**，不许重新估算。怀疑旧数有错→单列一节说明，不得静默修改。

## 5. 回执交付（主 Hermes 这一侧）

- **原样搬，不压摘要**。用户踩过：「午餐回执被摘要，他说没看到回执」。
- **不建 md、不发 MEDIA**。记账回执属于 `task-wrapup` 里「不触发收尾清单」的类型，只在对话里贴正文。
- 有疑虑的项标出来单独问他，但**只问「他凭常识能判断的」**（肉是不是肥的、菜名对不对、份量多少），不问「厨师放了多少糖」「这个换算对不对」。
- 他报份量常用「口 / 个 / 碗 / 半颗」——任务书要让它换成克并**把换算过程写出来给他看**。

## 6. 会话里的真实任务书存放位置

