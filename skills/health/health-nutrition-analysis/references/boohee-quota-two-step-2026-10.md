# 薄荷额度：两步分工 + 语义匹配（2026-10-20 实测落地）

> 代码：`~/health/tools/boohee.py`（`anchor()` / `classification` / `llm_pick()` / `two_step()`）
> 健康 profile 的 `meal-photo-analysis` 已同步写入硬流程。

## 一、起因：一顿早餐烧掉 23 次额度

用户原话：

> **「为什么我只给他发了一个指令，然后薄荷全天的调用次数就被消耗了 23 次？
> 是不是流程当中有可优化的地方？因为这样的话，我全天三顿饭 50 次的调用次数就不够了。」**

**他说得对，而且归因不是他以为的「流程复杂」。**

### 逐次溯源（`cache.json` + `quota.json` 完整证据链）

| 脚本 | 内容 | 记额度 |
|:--|:--|--:|
| `_probe_bf.py` | **10 个搜索词打包循环跑** | 9 |
| `_probe_detail.py` | 8 次详情 | 8 |
| `_probe_units.py` | **6 次详情**（南瓜/菠菜/香菇/黄豆/牛肉/鸡蛋） | 6 |
| — | — | **23** |

**其中 6 次 `_probe_units` 是健康助理自己的「嘌呤字段可信度抽查」，5 次跟用户吃的东西毫无关系。**

### 根因是「盲批探测」，不是选词不准

健康助理自己的认错原话：

> **「搜『甘薯』不是没注意到红薯已经命中，比那更糟——我根本没有机会注意到。
> 我把 10 个词写成一个列表交给脚本循环，脚本跑完才一次性打印结果。
> 所以『甘薯』发出去的时候，『红薯』的结果还没进入我的判断。」**
>
> **「这在本地 `foods.json`（零成本）是合理做法，在有日额度的薄荷上是错的。
> 我沿用了前几天的本地查表习惯，没有为付费接口切换模式。」**

**这一条比别名表重要：别名表能省几次，盲批习惯会每次都犯错。**

### 实测发现的两类浪费

| 浪费 | 实例 |
|:--|:--|
| **同一个东西换词重搜** | 番薯→红薯→甘薯（3次）、牛奶→全脂牛奶→纯牛奶（3次） |
| **为了一条参照值花一次 detail** | 南瓜(栗面)/红薯/牛奶/南瓜 —— **不是他吃的东西**，只是为了对比 |

### 一个可复用的判据：搜俗称时返回的全是制品

```
番薯   → 番薯丸 / 番薯饼 / 番薯蒸包 / 番薯苹果泥      ← 没有红薯本体
甘薯   → 甘薯粉 / 甘薯片 / 甘薯条                    ← 没有甘薯本体
全脂牛奶 → 牧牌 / 太慕 / 乐购 / 纽爵 / 亨氏 全脂牛奶   ← 全是品牌货
```

**对照成功的**：`红薯` → 前两条就是本体；`纯牛奶` → 前三条是基础食材。

## 二、数据一致性实证：两个接口是同一套库

| 食物 | 字段 | 免费 `public_detail` | 付费 `detail` |
|:--|:--|--:|--:|
| 红薯(煮,去皮) | protein / fat / carb / natrium | 1.4 / 0.1 / 17.7 / 27.0 | 1.37 / 0.14 / 17.7 / 27.0 |
| 贝贝南瓜 | 同上 | 1.9 / 0.3 / 20.6 / 1.0 | 1.9 / 0.3 / 20.6 / 1.0 |
| 纯牛奶(全脂) | 同上 | 3.3 / 3.6 / 4.9 / 63.7 | 3.3 / 3.6 / 4.9 / 63.7 |
| 茶叶蛋 | 同上 | 13.7 / 9.1 / 2.2 / 444.0 | 13.7 / 9.1 / 2.2 / 444.0 |

**16/16 字段一致。公开接口 = 同一套库的免费视图，不是「阉割版的另一个库」。**

### 付费 detail 的返回结构（易踩）

`food` 字段里**只有 name/code/图片，没有营养数字**。营养在：

| 字段 | 内容 |
|:--|:--|
| `base_ingredients` | carbohydrate(+sugar, fiber) / protein / fat(+saturated, trans) |
| `mineral` | **calcium** / natrium / kalium / iron / zinc / magnesium / phosphor |
| `other_ingredients` | **purine** / alcohol / gi / gl / lutein |
| `material_section` | 配方（原料克数 + 做法步骤） |

## 三、两步分工（定稿）

```
① anchor(name)   免费锚定 code
   ├─ 别名子串替换（蒸番薯 → 蒸红薯）
   ├─ 做法词**逐级**剥离（清炒菠菜 → 炒菠菜 → 菠菜；水煮鸡蛋 → 煮鸡蛋）
   │    ⚠️ 不是一次剥光 —— 见下方踩坑 6/7
   ├─ public_search 搜，**只有 exact 才提前停**，否则跑满 3 次攒厚候选池
   └─ 挑中 code                                   ← 0 额度
                ↓
② detail(code)   付费抓全套（嘌呤/钙/糖/维生素/配方） ← 1 额度（缓存则 0）
```

**入口就用 `boohee.two_step(name, grams, context="他早上蒸着吃的")`。**

### 为什么这样分工（用户的原话就是答案）

> **「我就完全可以用免费的那个库完成代码的这个锚定的工作，然后确认好代码之后
> 再去那个 API 的库里抓营养素，这样两步走明确分工。」**

我原本想的是「免费拿能拿的、只付费补嘌呤钙」，**被这个分工否掉了，理由站得住**：

> **免费接口有 429 限流。它适合干「失败了大不了重试」的活，不适合干「必须成功」的活。**

| 阶段 | 失败代价 | 该用哪个 |
|:--|:--|:--|
| ① 锚定（试词/筛选） | 再试一次而已 | **免费** |
| ② 抓营养素（出最终数字） | 这顿饭算不出来 | **付费** |

## 四、语义匹配：为什么必须上模型

### 三条字符串规则全失败后才知道的事

薄荷里的名字极其混乱：`红薯` / `红薯(煮,去皮)` / `红薯干` / `蒸红薯` / `安井红薯窝头(红薯)`，
**热量从 60 到 338 kcal/100g**。调了三轮，每修一个就崩一个：

| 轮次 | 判据 | 崩在哪 |
|:--|:--|:--|
| ① | 以 q 开头 + basic | **「红薯干」236kcal** 冒充「红薯」 |
| ② | 以 q 开头 + 非制品后缀 | **「茶叶蛋(蛋白)」29kcal** 冒充「茶叶蛋」141kcal |
| ③ | 只认 exact | 薄荷没精确条目时**直接卡死**（蒸番薯零结果） |
| ④ | exact 或 exact_paren | 搜「纯牛奶」一碰到 `(脱脂)` 就停，池子里没有全脂 |

**用户的判词是对的：「精确同名也会出问题，有时候会匹配不上，你能不能弄成语义理解。」**

### 最终架构：规则做能确定的，模型做拿不准的

| 层 | 何时生效 | 代价 |
|:--|:--|:--|
| **字符串规则** | `quality == exact`，或 `exact_paren` **且同基名唯一** | 0 |
| **`llm_pick()`**（deepseek-v4.1-flash） | 规则拿不准时自动调 | 几分钱 |

**模型判断带理由返回，可事后复核。实测两条：**

> 全脂牛奶：**「用户未指定品牌，候选1是无品牌的全脂纯牛奶本体，最符合『全脂牛奶』。」**
>
> 水煮鸡蛋（候选全是品牌包装）：**「候选均为带品牌的水煮鸡蛋包装品，用户未指定品牌，
> 按规则应排除，不能硬选。」** —— 它主动拒绝硬凑，然后由「剥做法词」兜底命中 `鸡蛋`。

### `quality` 七级分类（返回值里带着，供复核）

| quality | 含义 | 可信 |
|:--|:--|:--|
| `exact` | 一字不差 | ✅ |
| `exact_paren` | 去括号后同名 | ✅ 单一候选时 |
| `prefix` | 带后缀 | ⚠️ 看后缀是做法还是加工 |
| `partial` | 包含关系 | ⚠️ 多是品牌包装品 |
| `product` | 制品（红薯干/番薯丸） | ❌ |
| `part` | 子件（茶叶蛋(蛋白)） | ❌ 热量口径完全不同 |
| `weak` | 关系很弱 | ❌ |

## 五、五个踩坑（都已修）

| # | 坑 | 修法 |
|:--|:--|:--|
| 1 | **`exact_paren` 判据太粗** —— 「茶叶蛋(蛋白)」去括号正好等于「茶叶蛋」→ 40kcal 冒充 141kcal | 括号内容含 `_PART_SUFFIX`（蛋白/蛋黄/皮/骨/壳…）时判为 `part` |
| 2 | **别名只认完整词** —— 「蒸番薯」不在表里，搜「蒸番薯」零结果 | 改**子串替换** |
| 3 | **提前停导致候选池太薄** —— 碰到 `纯牛奶(脱脂)` 就停，模型看不到全脂 | 只有 `exact` 才提前停，否则跑满重试 |
| 4 | **公开接口搜索返回不稳定** —— 同一个词连搜三次：第1次有本体、第2次没有且混 OCR 乱码、第3次又有 | **免费就重试到命中**（本轮 3 次） |
| 5 | **OpenCode Go 网关 403** —— `llm_pick` 少 `User-Agent` + `x-opencode-session` 两个 header | 补齐（与 `recognize.py` 一致）+ `ssl.create_default_context()` |
| 6 | **做法词一次剥光** —— 「清炒菠菜」直接剥成「菠菜」，命中生食材 28kcal（真实「清炒菠菜」42kcal，**差 45%，油和盐全漏**：120g 差 16.8kcal / 152mg 钠） | **逐级剥离**：先只去掉修饰字（清炒→**炒**，薄荷第 1 条就是「清炒菠菜」），再退到裸名 |
| 7 | **说了做法词却匹配到生食材** —— 「菠菜(煮)」带括号、不是裸名，躲过了「裸名降权」，以 `exact_paren` 顶掉 `partial` 的「清炒菠菜」 | ① 候选名**不含做法词**的一律降权（`no_method` 排在排序第一位）② 说了做法词时**强制**走 `llm_pick`，不再看规则置信度 |
| 8 | **`anchor()` limit 太小** —— limit=8 时搜「纯牛奶」经常只捞到「(脱脂)」一条，模型没得选 | limit **8 → 20**，候选池攒厚 |

### 🔴 踩坑 6/7 的元教训：**我自己的测试能过，端到端却挂**

修完逐级剥离后我自己跑了三轮，**全对**（清炒菠菜 → 清炒菠菜 50.4kcal）。
但让健康助理真跑一遍，**它给出的是「菠菜(煮) 27.6kcal」，差 45%**。

**原因：公开搜索返回不稳定。「菠菜(煮)」只要没被那几次请求捞进池子，我的排序就永远遇不到这个 bug。**

> **所以：工具层改完，必须让真实调用方自己跑一遍，并要它报出额度前后差值。
> 自己写的回归测试里，随机性会把 bug 藏起来。**

**验收话术（可直接复用）：**
> 「跑这个，把输出原样贴给我：`two_step('清炒菠菜',120)`。
> 再报出跑前跑后的 `quota.json` 差值。**这个结果对不对？**」

**它的回答质量很高**——不仅指出错了，还自己定位到「是排序不是搜索」，并主动说明
「上午那次手工纠正仍然必要，工具现在还是做不到」。**这种反驳要当真，不要当成它在偷懒。**

### 库里混着 OCR 乱码条目（必须挡）

```
牛奶 → 莲艮 / 柳叶莓 / 二线蛇
番薯 → 唉嗯亩阿企得 / 啤梨(紫)
红薯 → 朹骨草 / 六膜虫 / 红金酿 / 香根牛瘤酒 / 鲎罗果 / 情头翁 / 参虫草
```

**特征：`food_type is None` + 名字跟查询词毫无关系 + 热量离奇（456.24kcal）。**
过滤两条：`food_type is None` 直接丢；名字里一个查询字都没有也丢。

## 七、防 429（用户特别叮嘱「即使免费也要尽量别触发」）

三道闸，全部内置在 `_public_get()`：

1. **全局最小间隔** `PUBLIC_MIN_INTERVAL`（默认 1.2s，环境变量可调）
2. **429/403 指数退避** 1.5s → 3s → 6s …封顶 30s
3. **连续被限 3 次熔断**，本轮停止，不继续糟蹋

⚠️ **被限之后连之前能成功的请求也一起失败** —— 2026-10-19 因此丢过一轮已抓数据。

## 八、虚拟额度以外的真实成本提醒

`llm_pick` 只在规则拿不准时调，一次几分钱；**但一顿 4–6 样里可能有 2–3 样需要调**。
**如果发现每顿都在调，说明别名表/做法词表该补了** —— 模型是兜底，不是主力。
