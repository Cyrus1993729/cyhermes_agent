# 薄荷免费接口能拿全部营养素（含钠）—— 2026-10-29 实测推翻旧流程

## 一句话结论

**`public_detail(code)` 是免费接口，不消耗薄荷开放平台额度，返回体里带 `natrium`（钠）、`protein`、`fat`、`carbohydrate`、`fiber_dietary`、`calory`、`units`、`is_liquid`。**

旧流程「营养素一律走付费 `detail()`，免费只用来查单重」**是错的**，代价是这个错误连续 10 天让钠变成「估算值」。

---

## 字段名坑：是 `natrium`，不是 `sodium`

`public_detail` 返回的键名清单（2026-10-29 实拉 `fddb62ac`）：

```
id, code, brand, name, calory, calory_kj, joule, weight, health_light, is_liquid,
thumb_image_url, large_image_url, uploader, appraise, protein, fat, fiber_dietary,
carbohydrate, natrium, gi, gl, compare, recipe, recipe_type, units, ingredient,
lights, comments_ct
```

🔴 **没有 `sodium` 这个键。** 按 `sodium` 去取会 `KeyError`/拿到 `None`，很容易误判成「薄荷这个字段没填」。
🔴 **`natrium` 的单位是 mg/100g**（与 `calory` 的 kcal/100g 同一口径）。按克重换算时不要再除 1000。

## 🔴 也没有 `calcium` 字段 —— 钙必须另标来源（2026-11-03 实测）

`public_detail` 返回体里**没有钙**。2026-11-03 午餐核算实测 7 个 code
（`piaoerbai` / `kaliniurou` / `duixia` / `shuimianjin` / `lajiao_qing_jian` / `zhurou_shou` / `mifan_zheng`），
`d.get('calcium')` **全部是 `None`**。

但档案里出现了这种写法（错的）：

```
薄荷·免费 `piaoerbai`「上海青」18/1.7/0.2/3.2/纤1.6/Na56.9/Ca59   ← Ca59 不是薄荷给的
```

把成分表/估算来的钙**挂在薄荷 code 后面**，等于给这个数伪造了一个出处。

**✅ 六个都有出处 —— 而且全部是成分表的同名条目**（2026-11-03 复核完毕）：

| 薄荷条目 | Ca | 成分表出处（逐项与薄荷一致） |
|---|---:|---|
| `piaoerbai` 上海青 | 59 | **`045110` 瓢儿白［瓢儿菜］** 18/1.7/0.2/3.2/**Ca59**（piaoerbai＝瓢儿白） |
| `duixia` 对虾 | 62 | **`122106` 对虾** 93/18.6/0.8/2.8/Na165.2/**Ca62** |
| `shuimianjin` 水面筋 | 76 | **`011501` 水面筋** 142/23.5/0.1/12.3/纤0.9/Na15/**Ca76** |
| `lajiao_qing_jian` 青椒 | 11 | **`043123` 辣椒（青、尖）** 22/0.8/0.3/5.2/Na7.0/**Ca11** |
| `zhurou_shou` 猪肉(瘦) | 6 | **`081101x` 猪肉（代表值）** Ca6 |
| `mifan_zheng` 米饭 | 7 | **`012401x` 米饭（蒸，代表值）** Ca7 |

⚠️ **复合菜例外**：`kaliniurou` 咖喱牛肉 Ca38.7 **没出处**——成分表全库无「咖喱牛肉」，
只有 `OFFICIAL-1580` 咖喱粉（Ca540，不能推）；按牛肉 90 g×5 ＋ 土豆 80 g×7 加权只有 ≈10 mg，**差 8 倍**。
→ 这类标 **〔估〕**，并附一句「若改按生食材加权，本餐钙会从 251 降到约 180」的对照，主值不动。

### 🔴 怎么找成分表对应条目：按「能量＋蛋白」双条件数值匹配，别按名字搜

薄荷 code 是拼音（`piaoerbai`＝瓢儿白、`shuimianjin`＝水面筋），**中文名经常字面不同**，
按名字 grep 会得出一堆「对不上」的假阴性。正确做法是全库扫 `foods.json`：

```python
cands = [x for x in foods
         if abs(float(x['energyKCal']) - 18) < 0.6 and abs(float(x['protein']) - 1.7) < 0.06]
```

命中后再比 `fat/CHO/dietaryFiber/Na` —— 四项都吻合才算同源条目，再看它的 `Ca`。
**2026-11-03 我第一版复盘就是只看了名字含「油菜」「对虾」的前 3 条，错判了三项「对不上」，
被他追问后才用数值匹配找回出处。** 复盘中的「对不上」结论，必须先做过一次数值全库匹配：只查名字前几条得出的否定结论，一律不能报给用户。

**规则**：
1. 薄荷条目只能给 `calory/protein/fat/carbohydrate/fiber_dietary/natrium`，**钙一律另起出处**。
2. 钙要么写成分表 code，要么写「—（未收录）」，要么写「〔估〕+ 估算依据」——
   **不许拼接在同一条薄荷来源标签里**。
3. 复核时 `calcium is None` 不代表条目缺数据，是接口根本没这个字段；
   别因为拿到 None 就在档案里填 0。
4. 🔴 **主 Hermes 复核时要核全列**：2026-11-03 那次我只核了 cal/P/F/C/纤/钠，
   把钙列整个跳过去，导致「来源错标」在汇报后才被发现。**验收清单固定为：
   calory / protein / fat / carbohydrate / fiber_dietary / natrium / calcium / units 八项**，
   薄荷返回体里没有的那几项（钙）必须单独交代出处。
5. 薄荷 `public_detail` 的 `ingredient` 字段里可能带 `calcium`，**但口径不一致、不能直接采信**
   （咖喱牛肉就是这种情况），要用成分表同名条目交叉验证后再定。

## 🔴 误判案例：「薄荷所有茶叶蛋条目的钠字段全部返回 —」是错的

2026-10-27 的 diet 档案写过：

> 薄荷所有茶叶蛋条目的钠字段全部返回「—」，一个真实值都没有。已核条目：`fddb62ac`、`fd1b4191 伊势`、`fd13fd57`/`fd4b102f 盒马`、`fd0ee19a 九只` —— 全空。

**这条记录是错的。** 2026-10-29 用免费 `public_detail(fddb62ac)` 直接拿到 `natrium = 444.0`，50g = **222.0 mg**。

后果链：
- 10-20 ~ 10-24 用 **222.0**（对的是按 444×50g 算的）
- 10-27 那次「复核」误判为全空，改成 **250 mg/个 估算**
- 10-28 用 2 个 = **500 mg 估算**
- 2026-10-29 早饭同样按 500 估，实际应为 **444**

→ **「复核后发现字段为空」这种结论必须给出原始返回体的字段名和值，不能只写「查了 5 个条目全空」。** 没有原始字段就无法区分「供应商真的没填」和「我们自己取错了字段名」。

## 根因：免费路径在代码里只被用于取单重

`~/health/tools/boohee.py`：

| 行 | 内容 |
|:--|:--|
| 194 | `def public_detail(code, timeout=30)` —— docstring 明写「不经过开放平台，**不消耗 50 次/天的额度**」 |
| 277 | 唯一调用点，在 `public_units()` 内部，**只取 `units` 单重** |
| 974 / 1057 | `natrium` 只在这两处出现，都在付费的 `Boohee` 类里 |

所以真实流程是：**免费接口 → 单重；付费接口 → 所有营养素。** 营养素明明免费能拿，却全部走了付费。

## 正确的取数顺序（免费优先）

```
① public_search(菜名)         免费  找候选 code
② public_detail(code)         免费  ★ 先看 natrium/protein/fat/carbohydrate/fiber_dietary 有没有值
③ 有值 → 直接用，零额度
④ 无值（真的空）→ 才走付费 detail()
⑤ 付费也拿不到 → 成分表拼算 / 按同类条目中位数，并写明出处
```

🔴 **`public_detail` 有全局限流**（`_public_get` 内置节流 + 429 指数退避 + 熔断）。连着打十几个会变慢（实测一批 8 条约 48s），但**慢不等于失败，也不会花额度**。

**验证是否真的免费**：调完若干次后看 `~/health/fooddb/boohee_api/quota.json` —— 2026-10-29 连打 10 次 `public_detail` 后该文件**一个字没变**（最后一条仍是 `2026-10-27: 13`）。这是唯一的硬判据。

## 🔴 派活时的连带教训

2026-10-29 早饭核算，主 Hermes 在任务书里写了「**尽量走免费接口**（付费额度已用 13 次）」，结果健康助理把整餐 4 样全部按成分表估，**钠 1022.1 里 890 是靠猜的**。

问题不在「省额度」这个方向，而在**把「免费接口」和「不查」划了等号**。正确写法是：

> 「先用免费 `public_detail` 取一遍（不花额度），只有它真的没值才考虑付费或成分表。」

**一次免费接口都没调，就直接降级到估算 —— 这是错的。** 降级之前必须先把免费路径走完，并说明免费路径返回了什么。
