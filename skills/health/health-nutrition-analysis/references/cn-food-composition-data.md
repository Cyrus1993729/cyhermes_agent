# 中国食物成分表：数据源、接口与合并

两套源的覆盖面不同，**必须合并用**。2026-10 实测。

## 源 1：GitHub 开源镜像（主库）

`Sanotsu/china-food-composition-data`，目录 `json_data_v3_20260825_qwen38max_kimi_k3_fixed/`

- **1677 条**，每个分类一个 `merged_<分类名>.json`
- 字段：`foodName / edible / energyKCal / energyKJ / protein / fat / CHO / dietaryFiber /
  cholesterol / ash / vitaminA / carotene / retinol / thiamin / riboflavin / niacin /
  vitaminC / vitaminE* / Ca P K Na Mg Fe Zn Se Cu Mn / remark`
- 全是**裸数字无单位**，能量单位 kcal
- 条目名带「代表值」的是标准参照项（如 `米饭（蒸，代表值）`、`鸡蛋（代表值）`）

🔴 **硬缺口：只有 61 个子分类。整块缺掉 9 个大类**——
糖/糖果/果脯蜜饯/蜂蜜、酱油/醋/酱/腐乳/咸菜/辛香料/盐味精、
饮料类、含酒精饮料、小吃甜饼、速食食品、婴幼儿食品、油脂类。

⚠️ 文件名含中文，用 `raw.githubusercontent.com` 时**必须 URL-encode 路径**，否则 404。

## 源 2：中国疾控中心营养与健康所官方查询平台

`https://nlc.chinanutri.cn/fq/` —— 官方在线版，**覆盖全部 21 个大类**。

### 分类页 URL 可枚举

```
https://nlc.chinanutri.cn/fq/foodlist_0_{cat1}_{cat2}_0_0_1.htm
```

### 真实数据接口（页面是 JS 异步渲染的，直接抓 HTML 只能拿到空骨架）

```
POST https://nlc.chinanutri.cn/fq/FoodInfoQueryAction!queryFoodInfoList.do
Content-Type: application/x-www-form-urlencoded

categoryOne=<大类id>&categoryTwo=0&foodName=&pageNum=<页>&field=&flag=
```

- `categoryTwo=0` 即该大类全部，**不必逐子类抓**
- **每页固定 8 条**，翻到 `page > totalPages` 停
- 返回 `{"currentPage", "totalPages", "list": [[...36 列...], ...]}`
- 需要 `X-Requested-With: XMLHttpRequest` 与 `Referer`，否则可能被拒

**重新定位接口的办法**（结构若变动）：抓一个分类页 HTML，搜内联 JS 里的 `url:` 或 `.ajax(`。

### 36 列定长数组的字段位置

⚠️ **不要按详情页 header 的文字顺序推断**——列表数组多两列，会整体错位。
用详情页 `foodinfo/{id}.html` 的值反查位置才是可靠的。

### 值的格式（**必须转成裸数字才能与主库合并**）

| 列 | 官方格式 | 转换 |
|:--|:--|:--|
| 食部 | `"100%"` | 去 `%` |
| 能量 | `"1698kJ"` | `÷4.184` 得 kcal |
| 蛋白/脂肪/碳水/灰分/纤维 | `"0.1g"` | 去 `g` |
| 矿物质 | `"66mg"`、`"1.40μg"`（硒、碘） | 去单位，**数值口径与主库一致** |
| 空值 | `""` / `"—"` / `"Tr"` | 统一成 `"—"` |
| 脂肪酸 | `"33.3%"` | 是**占比不是克数**，单独存 `SFA_pct`，不要混进主库字段 |

## 合并策略与结果

```
主库 1677 条  ∪  官方独有   →  2393 条
```

- 按**归一化名称**去重（去空格、全半角括号、顿号、逗号、连字符后转小写）
- 实测重名 644 条，官方独有 **712 条**（含 `豆腐（北豆腐）`、`米饭(蒸)(均值)`、
  `心里美萝卜`、`白砂糖`、`酱油(均值)`、`可乐`、`啤酒` 等关键条目）
- 官方条目 `_category` 加后缀「（官方源）」，`_source` 记录出处
- 官方数据更权威的地方**要覆盖手估的自定义条目**：
  白砂糖（手估 400 → 官方 406 kcal）、酱油/食盐/蜂蜜同理，已从 `custom_foods.json` 删除

## 已知仍缺

- **嘌呤** —— 两套源都没有。高尿酸场景要另配食物清单。
- **GI** —— 主库外挂 `json_gi_of_foods`（257 条）。
- **复合菜整菜**（糖醋排骨、宫保鸡丁、鱼香肉丝）—— 两套源都没有。
  官方源只有极少数单品熟食（叉烧肉、烧鹅、猪肉清蒸、卤驴肉）。
  **这是设计而非缺陷：复合菜一律拆解成原料查**，见 `meal-photo-pipeline.md`。
- **预包装食品 SKU**（各品牌零食饮料）—— 薄荷有 160 万条，两套官方源没有。
  但用户以家常菜为主，实测未构成高频缺口。

## 商业方案核实结论（2026-10）

| 方案 | 结论 |
|:--|:--|
| **百度菜品识别** | ❌ **接口层面就不满足**。官方字段表只有 `name` / `calorie`(每100g) / `probability` / `baike_info`；果蔬识别更只有 `name` / `score`。**无蛋白/脂肪/碳水，无份量。** 官网案例页写的"输出三大营养物质"是营销话术——同页示例代码只打印"菜品名称/菜品热量"。 |
| **百度果蔬识别** | ❌ 只返回 `name` + `score`，连热量都没有。 |
| **薄荷开放平台** | 食物数据 API（`fc.boohee.com`，13 接口，160 万条，170+ 字段含 GI/GL/嘌呤）可用，在**个人会员**内；图片识别在企业会员内（价格需联系商务）。用户实测个人会员 **1元/天 ≈ 365元/年**。⚠️ 价格与配额**无法从公开文档核实**，需登录控制台。⚠️ 入参是 `code` 不是名称，要 `search` → `ingredients` 两步。 |
| **天聚数行 TianAPI** | 价格公开（普通会员免费 100次/天；高级 169元/年 1万次/天），字段全。**但只有近 2000 种食物**，覆盖量与官方源同量级，不解痛点。 |
| **聚美智数（阿里云）** | 多菜品 + 预估重量 + GI + 营养成分，一步到位；**价格需登录**。 |

**最终决策：走中国疾控中心官方源（免费、权威、离线可用），薄荷暂不购买。**
薄荷的唯一优势是预包装食品 SKU，实测非高频需求，需要时再买不迟。

### 薄荷补充核实（2026-10，购买决策用）

- **薄荷 App 自带 AI 相机**。官网原话：「160万+ 食物营养数据……也可使用**薄荷 AI 相机，
  一拍餐食，即知重量、热量、营养构成及饮食建议**」。
  → 买会员 = 用户**多装一个 App 自己拍照**，完全绕开本管线。
  但它估重的原理与照片估重相同，**上限一样**，不是更准的方案。
- ✅ **已核实（2026-10 补充）：确有成品菜条目**，且接口不在 `foodie.boohee.com`：

  ```
  GET https://food.boohee.com/fb/v1/foods/search?q=<urlencoded 菜名>
  ```

  **公开可访问，无需登录。** 返回里 `food_type: "recipe"` 的就是成品菜：

  ```
  番茄炒蛋  84 kcal/100g   food_type=recipe
  红烧肉   497 kcal/100g   food_type=recipe
  宫保鸡丁  96 kcal/100g   food_type=recipe
  ```

  ⚠️ 搜索接口**只返回热量 + 碳水**（`calory` / `carbohydrate`），**没有蛋白/脂肪/钠**；
  详情接口 `/fb/v1/foods/{id}` 返回 `{}`（需登录）。
  → **免费能拿到「这道菜多少卡」，拿不到我们真正需要的三大营养素明细。**
- 🔴 **但薄荷的成品菜也是「算的」，不是「实测的」。** 官方自述原话：

  > **菜肴原料计算**：根据菜肴的实际原料组成与用量，**通过标准化算法模型计算获得**营养数据

  基础数据源也写明引用《中国食物成分表》2018/2019 版——**和我们用的是同一份**。
  所以买会员得到的是「另一家公司用更专业的配方库算出来的结果」，**不是「更真实的数字」**。
  它的真价值在**配方库**（每道菜用多少原料），不在数据源。
  **答复用户时必须讲清这个区别，否则他会以为花钱买掉了误差。**
- 📊 薄荷自报的识别准确率（其商业 AI 能力）：单品类中餐 90%、西餐 98%，
  **餐盘多食物 70.3%**——后者才是本管线的场景。
- ⚠️ 开放平台用户协议 4.8.4 写明「不得私自爬取、搬运、**二次拆解**」、
  「不得转租、转售、转授权、拆分二次分发」。**个人自用与商用不同，但批量抓取属灰色地带**
  ——是否采用**由用户决定，不要替他拍板**。
- 🔴 **决策关键未知项**：个人会员 1元/天 给的是**「名称 → 营养素」的 API 调用权**，
  还是仅 App 会员？**必须由用户在控制台自行确认**才能据此开工。
  文档站（`ai.boohee.com/docs`）13 个接口文档里**不含任何价格/配额/会员信息**，
  已确认无法外部获取。
- 操作量对比（答复用户时用）：自建方案多一个「确认」动作，但零成本、可见明细；
