## 一、方案类产出（早餐方案 / 食谱 / 餐单）送用户前必做：硬指标对账

**只核热量和蛋白是不够的。** `profile.md` 第五节「其他硬指标」是**逐日上限/下限**，
方案里每一套都要对得上，否则就是自相矛盾的交付物。

```
蔬菜 ≥500 g/天 ｜ 低脂/脱脂奶 300 mL/天 ｜ 鸡蛋 1 个/天
膳食纤维 25–30 g/天 ｜ 饮水 ≥2000 mL/天
```

🔴 **2026-11-02 实踩**：早餐方案 8 套里有 2 套（S3 紫薯蛋奶碗、S8 黑米小米粥）各用了
**2 个全蛋**，而 profile 写着「鸡蛋 1 个/天」，原稿没有任何一处解释这个冲突。
主 Hermes 验收时抓到，派回去改成「1 个全蛋 + 2 个蛋清」——改完还更好（蛋白 42.6→43.7、
脂肪 9.1→4.9）。**如果不查这一条，用户拿到的就是一份违反他自己体检口径的方案。**

### 胆固醇口径（必须用同一本账，别混）

| 口径 | 1 个鸡蛋（50 g） | 出处 |
|---|---:|---|
| 中国食物成分表 `111101x` 648 mg/100 g | **324 mg** | `foods.json`，**他所有档案同源** |
| USDA 186 mg/枚 | 186 mg | 公开科普常用值 |

**两者差 1.6 倍。** 档案里混用两套会把一天算乱。他 LDL-C 4.37 属高胆固醇血症，
《中国血脂管理指南（2023）》那句「每天膳食胆固醇 <300 mg」是**直接适用**的，不是参考。
按成分表口径 1 个蛋黄就 324 mg（108%），所以「一天 1 个蛋黄封顶，其余蛋白走蛋清/奶/酸奶/豆制品」
是能站住的规则；即使按 USDA 口径，2 个全蛋＝372 mg 仍超 300，**结论不因此改变**。

### 其它要对账的项
扫描方案里出现的：奶当量（两套同天吃会撞）、豆制品量（嘌呤 89 mg/100 g）、
鸡胸等高嘌呤主蛋白（**S7 嘌呤 222，一周最多 1–2 次**）、钠（生抽 6500 mg/100g 折算）、
有没有推荐蛋白粉（**他家里没有蛋白粉，不要推**）、有没有建议脱脂奶（**不许，一律全脂**）。

## 二、核算档案验收：固定八项，缺一不可

```python
# 每个食材 code 都要过一遍（免费，不设上限）
import sys; sys.path.insert(0, r"C:/Users/Administrator/health/tools")
import boohee
r = boohee.public_detail(code)
d = r[0] if isinstance(r, tuple) else r      # 🔴 返回 tuple，直接 .get 会 AttributeError
# 核：calory / protein / fat / carbohydrate / fiber_dietary / natrium / calcium / units
```

1. **八项逐项核**，不是只核热量蛋白。`calcium` 一定是 `None`（接口没这字段）——
   那就去问「档案里那列钙是哪来的」（见 `boohee-free-public-detail-natrium.md`）。
2. **code 存在性**：不在本地 `cache.json` **不等于编造**，但必须能 `public_detail` 通；
   通不了才判假。
3. **合计 = 逐项和**（Python 重算，不手算）；
4. **跑脚本**：`python "<skill>/scripts/verify_diet_tables.py" "<档案绝对路径>"`。
   它报「钙有 1/N 行不是数值」是「—」格被判非数值，**属预期**；判据是它 `重算 [...]`
   那行与合计行逐项一致。
5. **付费额度**：`quota.json` 里**没有今天的键**才是真 0 次（有键且计数增长就是花了）。
6. 同一份档案里若同时有早餐/午餐表，**只看午餐表是否 PASS 不够**，两张表都要看。

## 三、修正轮次的派活模板（短、硬、就地改）

发现「数字对但标签/口径错」时，**不要让子代理重写整份核算**，会推倒重来。
任务书固定四段：

1. **定位**：哪几张表的哪一列，错在哪（附证据，如「薄荷 public_detail 无 calcium 字段，实测 7 个 code 全 None」）。
2. **我给已核准的对应关系表**：主 Hermes 先把映射查好，让子代理**复核并允许顶回来**。
   实测它逐条复核后全部确认，省掉一轮来回。
3. **绝对不许动的**：列出七列名 + 合计行原值逐个写死。
4. **改完必做**：从磁盘读回比对、跑 `verify_diet_tables.py` 贴重算行、
   在表格下方补「口径声明」一节；输出末尾给**可直接转发的完整文本**（用户会要「再发一份」）。

🔴 子代理可能反向发现你任务书里的错（如「`ingredient.calcium` 确实有值但口径不一」）——
**它顶回来时公开认，不要悄悄咽下去**。用户在场时这条尤其重要。

## 四、用户问「复盘工作流程是否符合前期要求」时的答复形态

他要的不是自我评价，是**逐条对账 + 证据**：

- 每条拿固定符号打头：`✅` 合上的 / `⚠️` 不合的，**分开列，不要混谈**。
- 每条后面跟**可验证的证据**，不是形容词：`quota.json 无 2026-11-03 键`、
  `verify 重算 [700.6, 57.59, …] 与合计一致`、`public_detail(code) 逐项一致`。
- **自己的漏项要单独拎出来认**（「我复核只核了六列，钙列跳过去了」），
  不要塞在「做得好的部分」里稀释掉。
- 结论句放最前面（「查了/没查」「合/不合几条」），细节在后。
- 结尾给一个**具体动作 + 代价估计**（「改钙列来源标注，几分钟」），不要开放式提问。
