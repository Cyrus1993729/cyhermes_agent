用户发餐食照片 → 识别 → 查成分表 → 核算。2026-10 搭建并实测通过。

跑法：`cd ~/health/tools && python meal.py <图片> --save`

## 设计原则：两段式，职责分离

```
LLM  →  只输出「是什么 + 多少克 + 置信度 + 依据」
查表  →  数值一律由《中国食物成分表》查得
```

**绝不让模型自己报热量。** 这是阿福类 App 翻车的根因——它们让模型连核算一起做了。
模型只做它擅长的（认东西、目测份量），数字交给确定性查表。

提示词里要**明写**这条禁令，并说明理由（"你算了会重复且会错"），否则模型会主动附赠热量。

## 🔴 第一原则：映射表的目标名必须程序化校验，绝不凭记忆写

这是本会话摔得最狠的坑，**同一个错误犯了两次**：

| 轮次 | 现象 | 规模 |
|:--|:--|:--|
| 首次 | 别名表指向不存在的条目 → 番茄被匹配成「番茄（整个，罐头）」 | **27/83 条失效** |
| 二次 | 加工品纠偏表目标不存在 → 大蒜条目不纠偏 | **4/10 条失效** |

**失效方式是静默的**：目标不存在时 `if target in by_name` 直接为假，
流程照跑、不报错、数字照出——只是错的。肉眼审不出来。

**修法（已落地）**：`FoodDB.__init__` 里对**每一张**映射表做自检——
既要查目标存在，也要查**源条目存在**（源不存在 = 该规则永不触发，同样是静默失效）：

```python
self.broken_aliases = {k: v for k, v in ALIAS.items() if v not in self.by_name}
self.broken_maps = []
for _tn, _tb in (("RAW_TO_COOKED", RAW_TO_COOKED),
                 ("PROCESSED_TO_FRESH", PROCESSED_TO_FRESH)):
    for _k, _v in _tb.items():
        if _v not in self.by_name: self.broken_maps.append(f"{_tn}: {_k} -> {_v}（目标不存在）")
        if _k not in self.by_name: self.broken_maps.append(f"{_tn}: 源条目 {_k} 不存在（永不触发）")
```

责任行、并打到 stderr。`python fooddb.py` 会打印全量解析结果，**目标状态是 0 告警**。

> 这条规则不限于营养场景：**任何「把外部名字映射到参考数据集条目」的代码层**都适用。

## 十一类已实测的错误

### 1. 生 / 熟混淆 —— 差 2-3 倍，最要命

| 盘中形态 | 正确条目 | 错误条目 | 倍数 |
|:--|:--|:--|:--|
| 熟米饭 | 米饭（蒸，代表值）116 kcal | 稻米（代表值）346 | 3.0× |
| 熟面条 | 面条（富强粉，煮）107 | 面条（生，代表值）301 | 2.8× |

实测：一张汤面图因模型写「面条（生）」算出 602 kcal，实际 214。

**双保险**：提示词要求 `state` 字段（熟/生/干/湿）+ 引擎侧 `RAW_TO_COOKED` 表
在 `state=熟` 时自动纠偏并打告警。

⚠️ 库内**没有**「糯米饭（蒸）」——糯米条目**不做纠偏**。宁可不改，也不能换错。

### 2. 加工品名 —— 凭空膨胀几百 kcal

模型会把菜里的新鲜食材叫成**加工制品名**：猪肉→「猪肉脯」、大蒜→「大蒜（脱水）」。
加工品营养密度高得多：

- 猪肉脯含糖 46g/100g → 175g 多出 **81g 碳水 ≈ 326 kcal 幽灵热量**
- 脱水蒜是鲜蒜的 **5 倍**浓缩

实测 06 号图：修复前 碳水 99.6g / 脂肪 35.7g，修复后 **碳水 12.9g / 脂肪 85.6g**。

**总量几乎没变（952→970 kcal），但构成完全反了**——修复前看着"脂肪还行"，
修复后真相是脂肪 86g = 目标 67g 的 **128%，直接超标**。

> ⬆️ 这正是不查表、只用模型报数的危险之处：**错的是构成，不是总量，总量对不上时反而容易发现。**

**双保险**：提示词加命名规范（不用加工品名，给 ❌/✅ 对照表）+ 
引擎侧 `PROCESSED_TO_FRESH`。

🔴 **触发条件用「反向判断」**：只要 `dish` 有值且不像零食/包装语境（不含
零食/小吃/即食/包装/干货/果脯/蜜饯）就纠偏。

> 最初写的是正向判断（dish 含炒/烧/蒸/煮…）——**漏掉了「糖醋咕噜肉」「卤味拼盘」
> 「干煸四季豆」这整类菜**，因为它们的菜名里一个烹饪动词都没有。
> 实测糖醋咕噜肉那张图，「猪肉脯」因此又漏网，又产生 65g 幽灵碳水。
>
> 教训：**给「什么情况下规则该生效」写白名单，必然会漏掉没想到的情况。
> 除非有明确的反例场景，否则用反向判断（什么时候*不*生效）。**

### 3. 可食部（骨/壳/皮/籽）

带骨带壳必须区分 `raw_g`（毛重）与 `edible_g`（可食重），参考区间：

| 食物 | 可食部 |
|:--|:--|
| 带鱼/鲫鱼（整条） | 70-80% |
| 虾（带头带壳） | 55-65% |
| 排骨 | 60-70% |
| 鸡翅（带骨） | ~65% |
| 苹果/梨（带核） | ~85% |
| 西瓜（带皮） | ~60% |
| 蛋（带壳） | ~88% |

库内 `edible` 字段就是可食部百分比，`calc()` 会按它折算。

### 4. 模型 JSON schema 漂移

实测两种：**整个 `confidence` 字段丢失**、`quality_note` 跑到 `photo` 对象外面。

**修法**：`normalize_schema()` 在解析后补齐缺失字段并打标记（`_conf_missing`），
把放错层级的字段搬回去。**模型输出不可信，但不可信不等于要崩。**

提示词侧同时加硬约束："`confidence` 是必填项，items 里每一项都必须有"，
"三个 photo 字段必须在 photo 对象内部"。

### 5. 识别本身会错 —— 但有时是照片的问题

实测一张糊掉的番茄炒蛋被认成「番茄拌鸡丝」（置信 0.50）。
**我用另一个视觉模型独立看，判断成「萝卜丝拌炒鸡蛋」——两个可能都不对。**

那张图糊、斜拍、无参照物。**这种照片谁都判断不了**，不是模型不行。

→ 对策不是换模型，是**让模型诚实标注**：低置信度必须显式列出、
`overall_confidence < 0.5` 时主动问用户确认，不要硬算。

### 6. 🔴 把「菜名」整名丢进库 —— 静默返回错菜（最危险的一类）

`resolve()` 在库里找不到精确条目时，`difflib` 会**猜一个相似的**。实测全错：

```
糖醋排骨  →  酱排骨    366 kcal
红烧肉   →  叉烧肉    196 kcal   ← 完全是另一道菜（红烧肉实际约 470）
番茄炒蛋  →  番茄酱     86 kcal   ← 离谱
可乐鸡翅  →  鸡翅      202 kcal   ← 看着合理，但漏了可乐的糖
宫保鸡丁  →  查不到
```

**它不报错、不空着，直接给一个像模像样的错数字。比「查不到」危险得多**——
查不到会被发现，猜错不会。

**修法**：`calc()` 检测到 `how` 含 `fuzzy` 就强制告警；菜名再含
糖醋/红烧/宫保/鱼香/咕咾/干煸/水煮/回锅/麻辣/椒盐/蒜蓉/清蒸/京酱/酸辣/咖喱
等菜型词时加一条「这是复合菜名，库里没有整菜数据，请拆解」的红牌告警。

**根本原因**：成分表里**根本没有复合菜**。官方源也只有极少数单品熟食
（叉烧肉、烧鹅、猪肉清蒸、卤驴肉）。**复合菜一律拆解，不要指望整菜查表。**

### 7. 🔴 糖醋/红烧类漏糖 —— 系统性少算

第一次跑糖醋类菜，「糖」和「醋」**完全没出现在结果里**。模型自述：
> *「酱汁成分（糖、醋、番茄酱、生抽等）无法从照片确认用量，未单列」*

这个理由看着严谨，实际是系统性少算：**漏 18g 糖 = 少算 73 kcal**，
而糖恰恰是血糖问题用户最该被记录的项。

**根因是提示词写得太绝对**——「宁可不列，不可乱列」被严格执行成了「看不见就不列」。

**修法**：提示词加「**第 3.6 步：菜名自带的调味必须列出来**」，给出菜型→调料的对照表：

| 菜型 | 必须补列 |
|:--|:--|
| **糖醋**X | 白砂糖 15-25g + 醋 + 炸油 |
| **红烧**X | 白砂糖 5-15g + 酱油 10-15g + 油 |
| **鱼香/宫保/京酱**X | 白砂糖 10-18g + 酱油 |
| **可乐**X | 可乐 200-330ml（含糖 25-35g） |
| **拔丝/蜜汁/茄汁**X | 白砂糖 20-30g |
| **卤/酱**X | 酱油 15-20g（钠高，务必单列） |
| **水煮/麻辣**X | 油 25-40g（红油层厚） |

按菜型估一个数 + 标 confidence 0.4-0.5，**比不列好得多**。
⚠️ 要区分：「糖醋」是**菜型名**（补糖），「番茄（糖水罐头）」里的糖水是**加工方式**（不补）。

### 8. 复合菜拆解：调料用量怎么来（菜谱配比法）

复合菜（糖醋排骨、红烧肉）库里没有整菜，必须拆解。附表那一格「调料用量」从哪来？

**联网搜菜谱可以，但搜到的是「绝对克数」不是「配比」——直接抄会翻倍。**

实测 4 家菜谱的糖醋排骨糖用量，归一到 500g 排骨：

```
搜狐        500g排骨 → 冰糖 30g
52hrtt      500g排骨 → 3勺(≈15g/勺) ≈ 45g
Christine's  600g排骨 → 3勺糖 ≈ 45g   → 归一 37.5g
美食天下     500g排骨 → 3汤勺 ≈ 40g
```

→ **中位数 40g / 500g = 糖占排骨重 8%**

红烧排骨同样算：600g 排骨配冰糖 20g、500g 排骨配一小把 15-20g → **约 4%**

| 菜型 | 糖 : 主料（实测菜谱） |
|:--|:--|
| 糖醋X | **8%** |
| 红烧X | **4%** |

**正确用法：取比例，再按照片里的份量缩放。** 照片里 200g 排骨 → 糖醋 16g，
**不是**抄菜谱的 40g。

🔴 **还要过一道生熟换算**：菜谱按**生重**写，照片看到的是**熟重**。
排骨煮后缩水两三成——不换算，糖会少估 25%。

> 照片里熟排骨 200g ≈ 生排骨 250-280g → 糖 20-22g

**缓存设计**：搜一次存进 `dish_recipes.json`，常见家常菜（糖醋排骨、红烧肉、
宫保鸡丁、鱼香肉丝等 ~30 道）可先批量预置。
**别每次都联网——只在遇到生僻菜时才触发，否则每次多几秒延迟。**

> 实测校验：模型自己估的糖醋菜糖量（15-25g）与菜谱推算（200g 排骨 → 16g）**吻合**。
> 所以联网不是雪中送炭，而是**给生僻菜兜底 + 给用户一个可信出处**。别把它当必需品卖。

### 9. 🔴 整碟重量校准：基准用错了层级

用户确认的是「这一碟多重」（**成品整碟毛重** = `dishes.gross_g`），
但 `items` 记的是**原料生重**。两者**天然不等**（烹饪失水、调料计入方式不同）。

**用 `items` 合计当缩放基准 = 反向缩放：**

```
确认卡报：整碟 230g
items 原料合计：344g
用户说：「不止，大概 300g」（比 230 大）
按 items 算 → k = 300/344 = ×0.87  ← 用户说“多”却被缩小了
按 dishes 算 → k = 300/230 = ×1.30  ← 正确
```

**正确做法**：缩放基准一律取 `dishes.gross_g`（用户给了修正就优先用他的），
再等比缩放到该菜所有的 `items` 上。

顺带做一致性检查：原料生重合计 / 成品整碟重 > 1.6 时提示一声——
生重>成品是正常的（失水+调料），但差得太离谱往往意味着识别漏项。

### 10. 🔴 用户回「对」时校准也必须执行

同一段代码里还有个更隐蔽的 bug：该校准最初只在「用户给了修正」的分支里跑。
**用户回「对」时根本不执行**——他确认了 260g，报告却按模型原始的 298g 算，
**确认了个寂寞**。

修法：`apply_corrections()` 无条件调用（无修正时 `fixes={}`），
对每道菜取「用户修正 > `dishes.gross_g`」作为目标值。

> 教训：**凡是「用户确认了一个数、系统据此重算」的流程，
> 都要单独测一遍「用户不改任何东西、直接确认」的路径。**
> 那条路径最容易漏——因为它看起来“不需要做什么”。

### 11. 🔴 模型的菜名不稳定 —— 用精确同名去匹配会静默丢弃修正

同一张图跑两次，菜品名分别给出 **「糖醋咕噜肉」**和 **「咕噜肉」**。
用户照着确认卡回「**糖醋咕噜肉 300g**」，程序拿它去匹配却匹配不上当前这次的名字，
修正被静默丢弃（只留了一条“不在菜品列表中”的提示）：

```
✅「咕噜肉」原料按确认卡上的整碟重量校准 ×0.96
⚠️ 修正里的「糖醋咕噜肉」不在本次识别的菜品列表中，未应用
```

**修法（`match_fix`，三层降级）**：
1. 精确匹配
2. **双向子串匹配**（`fk in dn or dn in fk`）
3. 若只有一道菜且用户只给了一条修正 → **直接认它**

已应用的修正名要记进 `used_names`，末尾把没匹配上的修正在同一行报出来，
不要静默丢。

> 教训：**模型输出的自由文本名不能当内存里的主键。**
> 只要它是 LLM 生成的，就要假设“每次都可能不一样”，匹配一律走模糊+降级。

## 提示词设计要点（外置在 prompt_recognize.txt）

分步推理，每步在 `basis` 字段留痕，**可追溯才能被纠正**：

1. **先找尺度参照物再谈重量** —— 中式盘 20-24cm / 饭碗 11-13cm / 筷子 ~24cm。
   没有参照物就明说，并降低 confidence。要求用户在照片里放筷子/勺是最有效的提升手段。
2. **拆到食材级** —— 番茄炒蛋 → 番茄 / 鸡蛋 / 植物油（成分表里没有"番茄炒蛋"这个条目）。
   盐/酱油/葱姜蒜用量极小时不必单列。
3. **两个重量** —— raw_g 与 edible_g 分开给。
3.5. **命名指向新鲜食材**，不用加工品名（见错误 2）。
4. **生/熟说清楚**，`state` 字段（见错误 1）。
5. **烹饪油单列**，confidence 一律 ≤0.4（一盘炒青菜的油 5-25g，差 180 kcal）。
6. **自评置信度**，看不清宁可不写也不要编。

输出要求：只给一个 JSON 代码块，前后无文字；不要营养数；不要建议。

## 数据源（已扩容）

主库来自 GitHub 开源镜像，**只覆盖 61 个子分类**，原本整块缺掉 9 个大类
（糖/调味品/饮料/糕点/酒/速食/婴幼儿食品）。

**2026-10 已从中国疾控中心营养与健康所官方平台 `nlc.chinanutri.cn` 补全 712 条，
库从 1677 → 2393 条。** 接口、字段位置、合并策略见 `cn-food-composition-data.md`，
抓取脚本 `scripts/crawl_official_fooddb.py`（可重跑）。

⚠️ 官方源到位后，**要用手估的自定义条目被官方值覆盖**：
白砂糖（手估 400 → 官方 406 kcal）、酱油、食盐、蜂蜜已从 `custom_foods.json` 删除。
仅剩 4 条成分表本身就没有的：贝贝南瓜、乳清蛋白粉、无糖希腊酸奶、蚝油。

**仍然缺**：嘌呤（两套源都没有，高尿酸场景另配清单）、GI（外挂 `json_gi_of_foods` 257 条）。

## 精度诚实边界

- **份量误差约 ±30%**。人类专家看照片估重误差 41-53%（多篇 benchmark），AI ±15-25%。
  不要把数字说成精确值。
- 学术前沿供参考：DietAI24（Nature 2025，GPT-4 Turbo Vision）识别 98.9% / 份量 84.2%。
- 商业/外部方案的核实结论（含百度官方字段表、薄荷定价、天聚、聚美）见
  `cn-food-composition-data.md` 的「商业方案核实结论」节。
  一句话：**百度只有热量没有三大营养素且无份量；薄荷够全但要 365元/年且非必要；
  最终走免费的中国疾控中心官方源。**

满分 8/8：deepseek-v4.1-flash, minimax-m3, qwen3.8-max, qwen3.8-flash,
          kimi-k3, glm-5.3-flash, mimo-v2.6-flash, qwen3.7-plus

## 12. 🔴🔴 `max_tokens` 太小 —— 「结果每次都不一样」的头号真因

**这是本会话最有价值的一条，因为它伪装成了别的问题。**

症状：同一张图连跑三次，菜品名分别是「凉拌生菜」「炒生菜」「生菜」，
做法跟着在「凉拌 3g / 家常炒 10g」之间跳，油量差 3 倍。

第一反应会归因成「模型采样随机」或「视觉模型判断不稳」——**全错**。
`temperature` 本来就设的 0。真因在 verbose 日志里：

```
[minimax-m3]          返回了内容但解析不到 JSON（10341 字符）
[deepseek-v4.1-flash] 返回了内容但解析不到 JSON（2175 字符）
```

**`max_tokens` 设成了 3000。** minimax-m3 会先输出一大段 ` thinking` 推理，
光这个就上万个字符，**JSON 还没写完就撞上限被砍断** → 解析失败 →
降级到链上下一个模型 → **下一个模型看得不一样** → 结果每次都不同。

于是「你指定的模型一次都没真正生效过」，而系统一声不吭。

### 修法（两条都要）

1. **`max_tokens` 提到 8000**（`recognize.py` 的 `call_model`）
2. **加截断修复** `_repair_json()`：从后往前砍掉不完整的尾巴、去掉残缺的键值、
   按已有的 `[` `{` 计数补齐括号，再 `json.loads`

### 结果对比

```
修前  第1次 [deepseek-v4.1-flash]  菜名=[香菜小炒牛肉, 生菜（生食/配菜）, 杂粮饭]
      第2次 [deepseek-v4.1-flash]  菜名=[香菜炒牛肉, 生菜沙拉, 杂粮饭]
      第3次 [deepseek-v4.1-flash]  菜名=[香菜小炒牛肉, 生菜（凉拌/沙拉）, 杂粮饭]

修后  第1次 [minimax-m3]  菜名=[凉拌牛肉, 生菜, 杂粮饭]  做法=[凉拌,凉拌,清蒸]  修补=无
      第2次 [minimax-m3]  菜名=[凉拌牛肉, 生菜, 杂粮饭]  做法=[凉拌,凉拌,清蒸]  修补=无
      第3次 [minimax-m3]  菜名=[凉拌牛肉, 生菜, 紫米饭]  做法=[凉拌,凉拌,清蒸]  修补=无
```

**修复后不仅稳了，还直接认出「凉拌牛肉」**——和用户的原话一字不差。
之前认成「香菜炒牛肉」也是截断的次生灾害，不是模型看不懂。

> **教训（跨场景通用）：当「LLM 输出每次都不一样」时，先查输出是否被 `max_tokens` 截断，
> 再怀疑采样随机性。** 推理型模型（会先吐 think 的）尤其容易撞这个坑——
> 它的思考过程本身就消耗大量 token，留给结构化输出的额度被挤没了。
> 而失败的方式是「静默降级」，日志里只有一行不起眼的字，很容易被当成模型能力问题。

## 13. 🔴 油量：不能看照片估，要按「做法」查表 + 用户校准

用户实测：**凉拌牛肉他只放了 3g 油。模型从照片估了 12g（豆油 8 + 辣椒油 4）——高估 4 倍。**

### 根因是方法论错，不是参数不准

```
凉拌菜：淋 3g 油     → 表面很亮，油光明显
炒菜：  下锅 15g 油  → 大部分留在锅里，菜上反而看不到多少
```

**油光和用油量基本无关，甚至反向。** 原来的提示词就是一张「油光程度 → 克数」的
对照表，从设计上就错了；而且那张表里**根本没有「凉拌」这一档**，
模型看到「有油光」只能往「家常炒 10-15g」上靠。

### 联网查菜谱也救不了

实测各版本菜谱的油量：

```
百度百科（老式宴席）  香油 50g
Instagram 家常版      花椒油 1/4 茶匙 ≈ 1g
Threads 家常版        腌肉用油 + 热油呛香 + 香油若干
```

**同一道菜差 50 倍。** 权威锚点同样说明问题：《中国居民膳食指南》推荐每天烹调油
25-30g，而我国居民**实际人均摄入 43.2g/天**。查菜谱拿到的是「人群平均的某种做法」，
和用户家锅里放了多少无关。

### 修法：模型只判做法 → 程序查表 → 用户实测覆盖

`~/health/fooddb/oil_profile.json`：

| 做法 | 基准 | 范围 |
|:--|--:|:--|
| 凉拌 | 3 g | 2-5 |
| 清蒸白灼水煮 | 2 g | 1-3 |
| 煮汤炖 | 3 g | 1-5 |
| 少油快炒 | 6 g | 4-8 |
| 家常炒 | 10 g | 8-15 |
| 红烧糖醋 | 18 g | 12-25 |
| 干煸油炸 | 30 g | 20-45 |
| 水煮麻辣 | 35 g | 25-50 |

优先级：**用户本次实测 > 用户历史校准 > 做法基准**。
用户报一次 3g，`apply_oil_profile()` 就写进 `用户校准`，以后同类做法直接用它：

```json
"用户校准": { "凉拌": { "g": 3.0, "依据": "2026-10-19 用户实测", "菜例": "凉拌牛肉" } }
```

**他只说一次，不是每次都说。** 报告里仍把油单列标「估算」——给他「看」，不是要他「核」。

### 配套：一道菜只准列一项油

模型同时给了「豆油 8g」和「辣椒油 4g」——**那是同一份油被拆成两项，重复计**。
提示词改成「一道菜只列一项油，两种油合并在 note 里说明」，
程序侧再把同菜的多项油合并成一项。

## 14. 🔴 油克数填 0 → 除以 0 → 整条记录营养归零

做法查表后有个隐蔽 bug：程序按「新目标 ÷ 原克数」算比例，
而**新提示词恰恰要求模型把油的 `raw_g` 填 0 或省略**（因为克数由程序定）。
于是 `k=0`，`kcal/fat/protein/carb/fiber` 全被设成 0：

```
| 豆油 | 炒生菜 | 9g | 9g | 0 | 0.0 | 0.0 | 0.0 |   ← 9g 油显示 0 kcal 0 脂肪
```

**修法：油的营养不按比例缩放，直接按克数重算。**

```python
old_kcal = float(keep.get("kcal") or 0)
per_g = old_kcal / float(cur_total) if (old_kcal > 0 and cur_total > 0) else 8.99
keep["kcal"] = round(per_g * target, 1)
keep["fat"]  = round(target * 1.0, 1)     # 食用油 ≈ 100% 脂肪
keep["protein"] = keep["carb"] = keep["fiber"] = 0.0
```

> 教训：**改动某一项的输入契约（这里是「模型不用给油克数了」）时，
> 要顺着数据流检查每一处拿它做除数的代码。** 除以 0 在这里不报错，只是静默归零。

## 15. 🔴 从菜名推做法：强信号覆盖、弱信号兜底

做法决定油量，而做法从哪来？最初只用模型的 `method` 字段，但模型把
「凉拌牛肉」认成「香菜炒牛肉」时，做法跟着变成「家常炒」→ 油 10g，而实际凉拌只有 3g。

**改为从菜名推，因为菜名是用户看得到、能纠正的，`method` 字段他看不见。**

但第一版把「炒」也当成了覆盖信号，结果把「**炒生菜**」判成「家常炒」→ 油 10g，
**反而覆盖掉了模型本来标对的「少油快炒 6g」**。

**修法：分强弱两档。**

```python
STRONG = [  # 这些字眼算数，覆盖模型标注
    (("凉拌","拌","沙拉"), "凉拌"),
    (("红烧","糖醋","卤","焖"), "红烧糖醋"),
    (("干煸","油炸","炸","酥"), "干煸油炸"),
    (("水煮","麻辣","沸腾"), "水煮麻辣"),
    (("清蒸","蒸","白灼","焯"), "清蒸白灼水煮"),
    (("汤","羹","炖","煲","粥"), "煮汤炖"),
]
WEAK = [    # 模型没标时才用。「炒」太宽泛——炒青菜少油、炒肉才家常
    (("少油","清炒","蒜蓉","炝"), "少油快炒"),
    (("炒","爆","煸","煎"), "家常炒"),
]
```

> 教训：**覆盖模型判断的关键词表，只放「字面就锁定语义」的词。**
> 「炒」这种一个词覆盖十种油量档位的，只能当兜底不能当覆盖。

## 16. 主食类同义兜底 —— 用户报的和模型叫的对不上

用户看了确认卡说「**杂粮饭 90g**」，而模型给那道菜起名「**紫米饭**」，
字面上没有任何子串关系 → 修正在末尾被静默丢弃：

```
⚠️ 修正里的「杂粮饭」不在本次识别的菜品列表中，未应用
```

**修法**：`match_fix` 加一层「主食类同义」兜底——用户说的和菜名**都含**
饭/面/粥/粉 之一时认它。

```python
STAPLE = ("饭", "面", "粥", "粉")
if any(s in fk for s in STAPLE) and any(s in dn for s in STAPLE):
    return fk, float(fv)
```

> 配套：库里**没有「紫米」**，但有「紫红糯米［血糯米］」= 紫米；
> 而模型一度把「紫米饭」匹配到「**糯米饭团**」（333 kcal / 脂肪 17.6g，
> 加油加馅的加工品，比白米饭高 2.9 倍）。
> 已加别名：杂粮饭/紫米饭/黑米饭/糙米饭/二米饭/藜麦饭 → 米饭（蒸，代表值），
> 并把「糯米饭团」加进 `PROCESSED_TO_FRESH`。
> 熟紫米混白米实际约 120-130 kcal/100g，用 116 的蒸饭口径误差 <10%，
> 比错到 333 好得多。
