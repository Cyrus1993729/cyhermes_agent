# 薄荷（Boohee）食物数据：免费接口 vs 开放平台

> 2026-10-19 实测。上文 `cn-food-composition-data.md` 里薄荷只占了
> ”商业方案核实”一小段，本文件是完整调研。
> 挖取手法（Next.js 空壳站怎么逆出接口）见 skill `web-api-discovery`。

## 一句话结论

薄荷有**两条完全不同的路**，不是一件事：

| | App 会员 | 开放平台 API |
|:--|:--|:--|
| 形态 | 手机 App 手工查 | 程序调用 |
| 价格 | App 会员年卡（用户报 365 元；报道称另有 88/128 档） | **免费 ￥0 / 个人 ￥365 年 / 企业联系商务**（三档表见第三节） |
| 沉淀 | 得手工抄 | 自动落库 |
| 数据 | App 展示什么就能看什么 | 结构化完整营养素 |
| 合规 | 个人使用 | 会员套餐 + 企业认证 |

**两条路都不买也能先验**——开放平台「注册可用」有免费额度。

## 一、免费公开接口（无需登录，但被阉割）

```
GET https://food.boohee.com/fb/v1/foods/search?q=番茄炒蛋
    UA: 浏览器 UA 必带；Referer: https://food.boohee.com/
```

**返回字段（实测只有这几个）**：

```json
{"foods":[{"id":14400, "code":"fanqiechaodan", "name":"番茄炒蛋",
            "food_type":"recipe", "calory":"84", "carbohydrate":3.52,
            "weight":"100", "health_light":2}]}
```

🔴 **只有热量 + 碳水，没有蛋白/脂肪/钠。**这是商业分层，不是 bug。

**有用的副产品**：
- `food_type` = `recipe` 就是**复合菜**（番茄炒蛋 84 / 红烧肉 497 / 宫保鸡丁 96 kcal/100g）
- `code` 字段是后面调完整接口要用的主键（如 `fanqiechaodan`）

⚠️ 老的食物库页面（`www.boohee.com/food/`、`food.boohee.com/`）已改成需登录的 SPA，
所有路由返回同一个 1505 字节空壳，**不能再靠爬网页拿数据**。

## 二、开放平台（薄荷科学 AI）：完整 API 清单

**文档接口无需登录，直接拿全部内容**：

```bash
curl -s -A "$UA" -H "Referer: https://ai.boohee.com/" \
  "https://api.boohee.com/open-interface/v1/panel/docs-index" -o docs.json
# → 56 KB JSON，含 13 篇文档的 markdown 全文
```

**13 个接口**（域名 `fc.boohee.com`，图片识别接口除外）：

| 接口 | 地址 | 说明 |
|:--|:--|:--|
| 获取访问令牌 | `POST /api/v2/access_tokens` | app_id + sign 签名 |
| 食物搜索（关键词） | `GET /api/v1/foods/search` | **支持 `food_type`：基础食材0/包装食物1/菜肴2** |
| 食物搜索（条码） | `GET /api/v1/foods/barcode` | |
| **食物详情** | `GET /api/v3/foods/:code` | 官方示例就是 `fanqiechaodan` |
| **食物营养信息** | `POST /api/v2/foods/ingredients` | **核心接口，见下** |
| 食物估重图 | `GET /api/v2/foods/:code/food_weight` | 8000+ 食物重量对比图 |
| 食物单位 | `GET /api/v2/foods/:code/units` | |
| 食物分类 | `GET /api/v1/categories` | kind = group/brand/cooking/season |
| 食物列表 | `GET /api/v1/foods` | |
| 食物排行榜 | `GET /api/v2/food_rankings` | |
| 图片识别 | `POST /open-interface/v1/kamela/food_recognition` | 域名 `api.boohee.com` |

### `食物营养信息` —— 和我们的管线直接对应

```json
POST /api/v2/foods/ingredients
{ "foods": [ {"code":"fanqiechaodan", "weight": 175}, ... ] }
// 单次最多 100 个
```

**注意：参数是 `{code, weight}`——就是我们平时说的「菜名 + 用户确认的份量」。**
它把「识别→拆解→查表」整段都包了。

**返回**：总热量（Kcal/Kj）+ 蛋白/脂肪/碳水各自的热量占比，以及

- 碳水（细分：**糖**、膳食纤维）
- 蛋白（细分：优质蛋白）
- 脂肪（细分：饱和 / 反式 / 单不饱和 / 多不饱和 / **胆固醇**）
- **15 种维生素**（A/E/B1/B2/B6/B12/C/D/K/烟酸/叶酸/泛酸/生物素/胆碱/胡萝卜素）
- 矿物质：**钠**、磷、钾、铁……

### 意外收获：业务标记字段

食物详情接口额外返回：

```json
"lights":   ["低饱和脂肪", "低嘌呤"],
"warnings": ["高胆固醇"]
```

**「低嘌呤 / 高胆固醇」这两个维度我们自建的成分表没有**——而这个用户尿酸 454↑、
LDL-C 4.37↑，正好对口。

## 三、计费与条款（从控制台 JS + 用户协议挖出）

**控制台原文**（登录后可见）：


### 三档权益表（2026-10-19 用户截图确认，这一节取代之前的"待定"）

| 接口功能 | 免费会员 ￥0.00 | 个人会员 ￥365/年 | 企业会员（联系商务） |
|:--|:--|:--|:--|
| **API 限制** | **50 次/天** | **200 次/天** | 无限制/天 |
| 食物搜索（关键词） | ✓ | ✓ | ✓ |
| 食物搜索（条码） | ✓ | ✓ | ✓ |
| 食物列表 | ✓ | ✓ | ✓ |
| **食物详情** | **✓** | ✓ | ✓ |
| 食物营养信息 | ✗ | ✓ | ✓ |
| 食物分类 / 单位 / 估重图 | ✗ | ✓ | ✓ |
| 食物排行榜 | ✗ | ✗ | ✓ |
| **食物图片识别** | ✗ | ✗ | **✓** |
| 定制接口 | ✗ | ✗ | ✓ |

🔴 **这张表里最关键的一条：「食物详情」在免费档就有，而它返回的同样是完整营养素**
（每 100g 口径，见上面「食物详情」一节的返回示例）。

**「食物营养信息」与「食物详情」数据同源，差别只是算法位置：**

| | 食物详情（**免费**） | 食物营养信息（个人会员） |
|:--|:--|:--|
| 粒度 | 一次一个食物 | 批量，单次 ≤100 个 |
| 份量 | 返回**每 100g**，自己乘 | **把克数传进去**，返回算好的值 |

→ **用免费档的「食物详情」+ 自己乘克数，功能上可替代个人会员的核心能力。
不要一上来就建议买 365。**

**调用量测算（免费档 50 次/天 够不够）**：

```
一顿饭 4 道菜 → 1 次搜索 + 4 次详情 = 5 次
一天 3 顿     → 15 次
免费额度 50 次/天 → 还剩 35 次
```

且**吃过一次的菜缓存进本地库后不再调用**，用量随时间下降。

🔴 **图片识别只在企业会员里** → **识图必须自建**（我们已经跑通 minimax-m3 那条路），
这不是缺陷，反而是自建管线里唯一不可替代的部分。

## 三·B、免费档拿不到的三个接口——实测封闭情况（2026-10-19）

用户问过：「薄荷的食物详情是不是也有以个数或者 ml 为单位的？」
**有，而且比我们自己猜的权威得多。**

🔴🔴 **后记（2026-10-19 同日晚些时候）——本节原来的结论「免费档拿不到」是错的，已证伪。**
付费的 `/units` 确实报「权限不足」，但**同一份数据在公开接口 `GET food.boohee.com/fb/v1/foods/<code>`
上免费拿得到**（零额度、无需鉴权）。完整做法见 `boohee-pieces-and-units.md`。
**本节保留作为「付费接口封闭情况」的记录，但结论已由那篇取代。**

> 教训：一个接口「要会员」不等于「这个数据要会员」。
> **先找同数据的公开入口，再决定要不要掏钱。**

### `食物单位` 接口：薄荷自带「1 个 = 210g」

```
GET /api/v2/foods/:code/units

{"success": 1, "food": {
   "name": "小麦", "calory": "338.0",
   "units": [{
      "unit_id": 14,
      "amount":  "1.0",
      "unit":     "个(中)",     ← 还分 个(大)/个(小)
      "weight":   "210.0",      ← 一个多重
      "eat_weight": "159.6",    ← 可食部（去核/去皮/去壳后）
      "calory":   "86.2"
   }],
   "food_weigh_url": "https://food.boohee.com/food_weight"
}}
```

🔴 **它连「可食部」都分好了** —— 这正是自建管线里一直要靠查表或猜的东西
（苹果带核、鸡蛋带壳）。**如果要用，它能一次性替掉我们的单品重量表。**

### 实测：权限不足，且**不是** 1024 错误码

```json
HTTP 200  {"success": false, "message": "权限不足！"}
```

`api.boohee.com` 与 `fc.boohee.com` **两个域名返回完全一致**（都试过）。

⚠️ **注意形态**：文档里的错误码表写着 `1024 未获授权的接口`，但实测会员接口未授权时
返回的是 **`success:false` + 中文文案**，**不是** 1024。
→ **判断接口有没有权限，只能看 `success` 字段和 `message`，不能靠错误码表。**

🔴 **更要紧的一点：它返回「权限不足」而不是「当天接口调用次数超过限制」** ——
说明**权限检查排在额度检查之前**。**买额度解不开权限问题，必须升档。**
（这一条决定了「先买 50 次试试」这条路走不通。）

### `食物估重图`：对校准视觉估重有理论价值

```
GET /api/v2/foods/:code/food_weight
→ {"success":1, "url":"http://s.boohee.cn/house/food_weight/big20101428.jpg"}
→ 不存在时: {"success":0, "message":"暂无食物估重图"}
```

薄荷对每样食物拍了**标准份量的实拍图**（「一个中等苹果长什么样」）。
理论上能校准模型对「一个」的视觉判断——**而这正是管线最弱的一环**
（蒸南瓜高估 2.5 倍就是这类问题，见 `portion-calibration-2026-10.md`）。

⚠️ **但它返回的是一张图**，管线要走 vision 转译，链路变长、每次多一次模型调用。
**实际收益未经实测，不要仅凭推测建议买。**

### 结论：365 元买不买（← 本节结论已被 `boohee-pieces-and-units.md` 推翻，保留供对照）

| 想要的能力 | 免费档 | 实际替代方案 |
|:--|:--|:--|
| 按「个」的食物换算单重 | ~~✗~~ **✅ 公开接口免费给** | 已建成 72 条 `piece_weight.json` |
| 液体按 ml | ✗ | 瓶标上写着；程序按 1ml≈1g（牛奶 1.03，误差 3%） |
| 校准视觉估重 | ✗ | 让他**拍照时放筷子/勺子**，零成本且效果已被验证 |
| 每日额度 | 50 次 | **把确认卡预览改走公开接口后，一天约 10 次**，够了 |

→ **单位接口和估重图都不是「没有就不行」的能力。**
真正值得掏钱的理由只有「确实需要新功能」或「调用次数不够」，
**不是「数据不够权威」**。

⚠️ **但要区分两种「公开接口」**：`/fb/v1/foods/search` 确实只给热量+碳水（被阉割），
而 `/fb/v1/foods/<code>` **给完整营养素 + units + is_liquid**——
**别因为搜到一篇写着「公开接口被阉割」就以为所有公开接口都那样。**

有独立的 `/enterprise-certification/` 页面与接口 → 部分能力可能要企业认证。

## 四、数据源本身的性质（别误判）

薄荷官方自述（`ai.boohee.com/solution/diet`）：

> **菜肴原料计算**：根据菜肴的实际原料组成与用量，**通过标准化算法模型计算获得**营养数据

基础数据源引用的是《中国食物成分表》（2018/2019 版）、USDA、日本/英国/法国/韩国成分表。

🔴 **所以薄荷的复合菜也是「用算法从原料算出来的」，和我们做的事是同一件**，
不是「实测数据」。买它得到的是**另一家更专业的配方库**，不是「更真实的数字」。
**根因是配方库，不是数据源**——这样说才准确。

薄荷自己公布的分项准确率：

```
单品类西餐 98% │ 单品类中餐 90% │ 单品类食品 88% │ 单品类包装食品 83%
购物单 80% │ 餐盘多食物 70.3%   ← 多菜同盘才是我们的场景
```

```json
   "major_materials":  [{"name":"鸡蛋","weight":100}, {"name":"番茄","weight":200}],
```

```json
 {"name":"升糖指数","value":0},
 {"name":"血糖负荷","value":0},
 {"name":"酒精度"}, {"name":"叶黄素+玉米黄素"}, {"name":"甜菜碱"}]
```

第一件事就是把真实返回 dump 一遍，别只按文档写解析。**

## 六、管线已落地（2026-10-19）

```
照片 → 多模态模型（minimax-m3，见 SKILL.md 「视觉模型 JSON 稳定性」）
     → 确认卡发用户（菜名 + 整碟克数 + **薄荷匹配预览**）
     → 薄荷搜索菜名 → code → 食物详情 → 每100g 营养 × 克数/100
     → 合计（薄荷查不到的菜降级到自建成分表，**单独列表不混算**）
```

**实现落点**：`~/health/tools/boohee.py`（客户端）+ `meal_boohee.py`（对接层），
`meal.py --confirm` 默认走薄荷，`--legacy` 回退旧路径。

### 客户端设计的四个要点（都是额度/稳定性逼出来的）

| 要点 | 做法 | 为什么 |
|:--|:--|:--|
| **token 缓存** | 存 `token.json`，1 个月有效期，过期前自动续 | 有效期 1 个月，不缓存等于每次多一次调用 |
| **时钟偏移缓存** | 取一次服务器 `now` 算出本机偏移量存住，报 1014 时自动重新校正重试 | 每次调用都去拿服务器时间太浪费 |
| **详情永久缓存** | `cache.json` 按 code 存完整返回 | 营养值不会变；缓存过的菜二次使用**不消耗额度** |
| **搜索也缓存** | 按 `query\|food_type` 存结果 | ⚠️ **不缓存的话确认卡预览搜一次、出报告又搜一次 = 双倍消耗** |
| **每日额度计数** | `quota.json` 本地计数，用到 80% 告警 | 免费档 50 次/天，测试时很容易烧完 |

### 搜索匹配的三个坑

1. 🔴 **必须先剥掉括号后缀**。模型会输出「香菜炒牛肉（带花生米）」，
   直接拿去搜**一条都搜不到**，而库里明明有「香菜炒牛肉」。
2. **「凉拌X」和「拌X」在薄荷是两种写法**，要都试。
   实测他说「凉拌生菜」，库里只有「拌生菜」（才对）和「凉拌生菜鸡胸肉」。
3. **候选排序要自己打分**（精确 > 去括号相同 > 前缀 > 包含 > 反向包含 > 字重合），
   分数 < 92 的标「⚠️近似匹配」并列候选让用户指认。

### 薄荷的配方是「买来的生料重量」

实测：红烧排骨 = 猪小排 **500g（生）** + 水 + 调料；糖醋排骨 = 猪小排 400g 生。
→ 和用户报的「这一碟多重」口径基本一致，**但含骨/含壳的菜差距大时要提醒他偏粗**。

### 配方里的油量可以拿来对账

`material_section` 里油是单列的（凉拌牛肉 = 芝麻油 10g）。
**用户报过实测油量时，从薄荷结果里把差值扣掉**（`--oil "凉拌牛肉=3"` 扣 7g×9=63 kcal）。
「把你实测的油填进去」这个能力，换成薄荷后依然保留。

### 🔴 薄荷返回的是「成品每 100g」，不是「原料每 100g」

用户会问：薄荷给的配方是 500g，我实际才吃 180g，你折算了吗？**答案是折了：**

```
薄荷「凉拌牛肉」= 114 kcal/100g（成品口径）
  180g → 205.2 kcal  (114 × 1.8) ✓
  500g → 570.0 kcal  (114 × 5.0) ✓
```

**那个 653g 的配方只是薄荷推导每100g 值的中间产物，与用户实际吃多少克无关。**
→ 用户报 180g，算的就是 `180 × 114/100`，**不要拿他报的克数去和配方总量比**。
（这类验证走缓存，不消耗额度，随时可以重跑给他看。）

**换掉的是「拆解 + 查表」，不是「识别 + 确认」。份量依旧要用户确认，
薄荷的图片识别也在企业版里，不解决份量这个最大误差源。**

## 鉴权实战：从「有凭证」到「调得通」（2026-10-19 实测踩坑）

### 凭证是两个字段，不是一个

控制台「API Key 管理」里是：

```
App ID       ← 明文显示，旁边有「复制」按钮
App Secret   ← 提示语「首次注册后仅完整展示一次，重置...」
```

⚠️ 用户只发来一个 32 位随机串时，**那是 App Secret**（符合"只展示一次"的特征），
必须再补要 **App ID**。只有一个值的话无论怎么试都是 `1002 无效的 app_id 或 app_key`。

### 签名算法

```python
sign = md5(app_key + "".join(f"{k}{v}" for k in sorted(params)) + app_key)
# 参与签名的 = 请求参数（含 app_id、timestamp）按 key 正序拼成 k+v 串
# app_key 不参与拼接，只是被包在整个串的前后；结果取 32 位小写 md5
```

🔴 **文档给的样例值是错的。** 文档称 `sign(app_id=boohee, timestamp=1470042310,
app_key=12345) = 27f61732856d133758e7f8927a3abed1`。
实测把 8 种拼接变体（等号 / 冒号 / `&` / 只前置 / 只后置 / 不包 / 加 `app_key` 字段…）
全算了一遍，**没有一个能对上**。
→ **按文字描述实现，不要试图复现文档样例**，否则会一直以为自己写错了。

🔴 **`1014 非法请求时间戳` 的真正原因：必须用服务器时间。**

本机 epoch 与薄荷服务器差 **2–3 分钟**就报 1014。试过 ±8h、秒 / 毫秒、
字符串 / 数字 —— **全部失败**。取服务器时间的办法：

```bash
# 任意一个 api.boohee.com 的公开响应里都带 now 字段
curl -s "https://api.boohee.com/open-interface/v1/panel/access-apis"
# → {"code":1010,"message":"缺少 AccessToken","now":1792373917}
```

**改用该 `now` 值当 timestamp，错误立刻从 1014 变成 1002** —— 这一步同时证明
时间戳过关、签名格式没写错。

### 错误码的检查是有先后顺序的（这才是诊断线索）

```
1014 非法请求时间戳        ← 最先检查，不通过就不会验 app_id/app_key/sign
1001 缺少 app_id 或 app_key
1002 无效的 app_id 或 app_key
1003 非法 sign 值
1010 缺少 AccessToken / 1011 已过期 / 1012 无效
1013 缺少参数或参数不规范
1021 找不到该食物 / 1024 未获授权的接口
```

→ **看到 1014 别去改签名，先修时间戳；看到 1002 才说明前两关都过了。**

✅ **请求体格式不是坑**：JSON body / form-urlencoded / query string 三种都能走到
签名校验、报同样的错。**不用在这上面花时间。**

⚠️ 调 `fc.boohee.com` 要挂代理（`HTTPS_PROXY=http://127.0.0.1:10808`）
且 `User-Agent: curl/8.0.0`（默认 urllib UA 被 Cloudflare 拦）。
