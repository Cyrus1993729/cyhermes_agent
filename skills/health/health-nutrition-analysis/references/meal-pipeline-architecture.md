# 餐食管线：架构与「确定性」设计

工程实现层（哪行代码会错）见 `meal-photo-pipeline.md`。
**本文件是设计层**——为什么这么搭、以及用户对「流程要确定」的诉求怎么落地。

## 用户的原始诉求

> **「我希望可以有一个相对固定的程序，让大模型知道第一步怎么做、第2步怎么做、
> 第3步怎么做，这样的话就是误差可能还是会有，但是起码流程是相对确定的。」**

起因是他担心：**大模型常识里没有的菜，识别不了只能瞎猜。**

## 先纠正目标函数

不要追「每餐算准」——人类专家看照片估份量误差 41-53%，物理上做不到。该追的是四条：

| 目标 | 为什么 |
|:--|:--|
| **无系统偏差** | 随机误差长期抵消；系统偏差会累积 |
| **永不崩溃** | 任何菜都要有输出路径 |
| **不确定可见** | 用户知道哪个数能信 |
| **可复现** | 同样的菜给同样的结果 |

🔴 **「无系统偏差」最关键，不是「把 ±40% 压到 ±20%」。**
总高估 80 kcal × 3 餐 = **240 kcal/天**，会让他误以为自己在缺口里，而其实没有。
随机误差一周下来自己就抵消了，系统偏差不会。

## 洞察 1：拆解不需要图片

实测：把提示词 + 菜名纯文本喂给模型（**不给图**），它能正常拆解。模型原话：

> *"no image was provided... 但我能基于菜名拆解"*

因为拆解做的是**「菜名 → 原料」的知识检索**，不是看图。

**所以拆解应该从识图里独立出来**，变成一次可缓存的查询：

- 同一道菜永远给同样的配方（**可复现**）
- 可单独修正配方而不影响识别
- 可用便宜的文本模型
- 可预置常见菜

而现状是「识图时顺便拆」——每识别一次就重拆一次，**这才是菜名/配方飘的根源**。

## 洞察 2：人是重复性动物

一个人一周吃的菜就 **30-50 种**。**所以「模型不认识的菜」是会自然衰减的问题，不是长期问题。**

```
第一周    命中率低，模型拆得多
第二周    开始重复，库里有了
一个月后  80-90% 走配方库，模型几乎不出场
```

**这直接回答了「不认识的菜怎么办」**：不是让模型什么都认识（做不到），
而是建一个**会成长的本地库**——今天不认识，明天认识，后天就记住了。

> 答复用户时的关键句：**你不需要一个无所不知的模型，你需要一个记得住你吃什么的系统。**

## 洞察 3：「固定程序」= 让模型做选择题，不是写数字

提示词里写「第 1 步 / 第 2 步」只是**表面形式**。真正让流程确定的是
**每一步的输出是有限集合里的一个值**：

```
❌ 不固定  "这道凉拌菜大概放 8g 油"    自由生成，不可复现、不可检查
✅ 固定    "这道菜的做法是【凉拌】"     9 选 1，可复现 → 油量由程序查表给
```

**模型从「生成器」退化成「分类器」——输出空间越小，越可复现、越可审计、越可修正。**

## 四层降级框架

```
第 0 层 配方库（零模型参与）
  菜名 → 规范化 → 命中 → 固定配方 → 查表
  ⭐ 用户确认过的菜永远走这里 = 完全可复现

第 1 层 槽位化拆解（受约束的生成）
  未命中 → 模型按固定 6 槽位填：
  ①主料(必填1-3) ②配菜(0-4) ③碳水(0-1) ④油脂(留空，程序按做法查表)
  ⑤调味(按第3.6步菜型表补) ⑥勾芡/挂糊(0-1)
  ⭐ 每样必须能在成分表里查到，查不到就报错，不静默替换

第 2 层 菜型兜底（只做选择题，不生成）
  拆不动 → 只判「做法 × 主料」两个枚举值
  9 种做法 × 12 类主料 = 108 格，总能落一格 → 永不崩溃

第 3 层 诚实降级
  全不行 → 给粗估 + 明确标「这是猜的」
  ⭐ 拒绝服务比给粗结果更糟——用户要的是记录，不是精确
```

⚠️ **第 2 层有个未解决的短板**：中式菜「菜型 × 主料」的配比数据源**没找到**。
如果找不到，这一层就是我拍脑袋定的先验，**不可信，不要在答复用户时把它说成可靠方案**。

## 提示词「第 0 步」：先判断认不认识

在拆解之前先让模型回答这个问题，并写进 `dishes`：

| 情况 | 标记 | 之后怎么办 |
|:--|:--|:--|
| 确定认识（宫保鸡丁 = 川菜） | `known: "certain"` | 按标准做法拆 |
| 认识但做法有分歧（红烧肉各地糖量差很多） | `known: "variant"` | 拆标准版，basis 写明按哪派 |
| 只认得菜系 | `known: "guess"` | 必须写 `guess_basis`，**confidence ≤ 0.3** |
| 完全不认识 | `known: "unknown"` | **不要编**，按字面拆 + `guess_basis: "仅凭菜名"`，confidence 0.2 |

**铁律：不确定就必须说「不确定」。** 编一个像模像样的配方，比老实说「我不认识」危害大得多——
**用户看到一份精确到克的报告，会以为它是准的。**

### 实测：冷门菜的覆盖度比预期高

纯文本给菜名让模型拆：

```
宫保鸡丁        ✅ 川菜，标准做法
擂椒皮蛋        ✅ 湘菜：皮蛋 + 烧椒 + 蒜 + 酱油 + 醋 + 油
秃黄油拌饭      ✅ 苏州菜：蟹黄蟹膏 + 猪油
撒撇            ✅ 云南傣族，还能分出「苦撒用牛胆汁 / 柠檬撒」两支
凤凰盏          ⚠️ "could refer to a few things... I cannot accurately determine"
轻食鸡胸肉沙拉  ✅
```

**覆盖度远超预期，且不认识时它倾向说「不确定」而非硬编。**
这降低了「崩」的风险等级——**回答用户之前先测，别凭直觉说「模型肯定不认识」。**

## 报告应该标注每个数字的来源

现在报告是一堆精确到小数点的数字，**用精确的外表掩盖了内部的不确定性**。

```
牛肉 175g   蛋白 35.0g    ← 用户确认的份量 × 查表    [可信]
豆油   3g   脂肪  3.0g    ← 用户实测值               [可信]
花生  25g   脂肪  8.6g    ← 模型估，置信 0.55        [猜]
```

**让他一眼看出哪个数该信、哪个数该一笑而过。** 这是「不确定可见」的落地方式。

## 校准信号只能收「用户判断得了的」

| 信号 | 能收吗 |
|:--|:--|
| 菜名 | ✅ 他看得见 |
| 份量 | ✅ 他手上有实物 |
| 配方 / 调料克数 | ❌ 「我又不是厨师，我哪知道厨师放了多少颗糖」 |
| **烹饪习惯倾向** | ✅ **跨菜生效**——"我凉拌菜都少油" → 整个凉拌档降下来 |

**第 4 行是关键设计**：配方层永远只能靠菜型先验，但用户能通过
**跨菜累积的倾向**间接校准（`oil_profile.json` 的 `用户校准` 就是这一条的最小实现）。

## 副产物：粗糙启发式造成的误报

为抓「生/熟混淆」曾写了一条模糊启发式：
`state=熟` 且标准名含「干」「生」「粉」之一就告警。结果：

```
⚠️「花生（炒）」看起来是生/干制品，但盘中是熟食
```

**「花\*生\*」的「生」字被当成了生制品标记。「生菜」同理。**

**修法**：删掉模糊启发式，换成**精确白名单**（只列真正会混淆的生粉/面粉条目）。

> 教训（跨场景通用）：**误报比漏报更伤信任。**
> 用户看到几次假警报就不信这个提示了，之后**真警报也会被忽略**。
> 宁可少报，不可乱报——这与「宁可错杀不可放过」的直觉相反，但在给人看的告警里是对的。

## 未验证项（答复用户时不要当成结论）

1. **配方库命中率**能到多高？推断「一个月后 >85%」，**这是推测，没有数据**。
2. **「菜名规范化」是隐藏难点**：用户说「杂粮饭」、模型说「紫米饭」，
   对不上就命中不了。同义词收敛问题未解。
3. **预置配方会不会污染**？预置的「红烧肉」和用户家做的可能不一样。
   判断影响有限（只影响看不见的调料），但是判断不是验证。
