# 餐食口述 vs 识图冲突的裁决流程（2026-11-17 午餐实证）

## 教训一：主 Hermes 第一动作是加载本 skill，不是 vision_analyze
2026-11-17 我又先调了 `vision_analyze` 认菜，才想起 skill 里写着禁止。
顺序必须是：**收到餐食照片 → 先 skill_view 健康域 skill → 再写任务书让健康助理用 recognize.py**。
主 Hermes 的识图结论一个字都不许进任务书。

## 教训二：用户说「一切都以我说的为准」= 直接落盘，不许再问第二轮
流程：识图结果与口述冲突 → 出纯文本确认卡 → 用户裁决。
- 他说「以我说的为准」时，处理的是**菜名冲突**（面条≠米粉、素鸡≠圆饼、酸菜牛肉≠梅干菜扣肉）
- **他不会再报克数**。此时不要二次追问档位，直接：
  - 他报过的克数照用，标 `〔他说〕`
  - 他没报的（「一碗」「一大块」）由我按照片碗型/尺寸落一个估算档位，标 `〔估算·大碗档〕`／`〔估算·尺寸推算〕`
  - 汤不喝就不计；他没提的配菜不单列（酸菜 0）
- 回执里用「不同档位带来的差异」单列一行给他看差异，**但不要请他重选**。

## 教训三：健康助理会自己编「截至 HH:MM」
2026-11-17 16:07 写入的档案，正文写成「截至 11:25」。这是它自己填的时间戳，不是他报的。
**落盘后必须核对档案里的时间戳与真实时间**，不符就在回执里单独点出来问，别让它躺在档案里。

## 教训四：落盘要复核，别信它自报
它自报「已写入 diet/xxx.md，7,338 bytes，ALL PASS」后，仍要：
```
ls -l ~/health/diet/2026-11-17.md
grep -n "759\|合计" ~/health/diet/2026-11-17.md | head
```
确认文件大小、表内合计行与正文数一致。

## 教训五：轮询姿势
派活用 `background=true, notify=true`，别在前台 `sleep`。
前台 sleep 段 **≤200 s**（280 s 那次直接 timeout 报错）。
用 `wc -c 输出文件` 判断是否跑完：几十字节=仍在跑，几 KB=完事。

## 教训六：汇总类请求的口径
用户要「今天截止目前的汇总」时，只有午餐报过。要求健康助理：
未报餐次一律写「未报」，**不许推算、不许填 0、不许算赤字**；
给出占 TDEE 比例时必须同时说明「分子只是午餐、分母是全天」。
