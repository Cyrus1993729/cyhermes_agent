# 调健康助理做联网核查 + 复核它自报的数

> 2026-11-16 实战沉淀（打球前加餐二选一：Tafe 苏打饼干 vs 史蜜斯高蛋白黑猪肉肠）。
> 适用场景：用户不在本会话直接核算，而是要「让健康助理联网搜一下 / 记一下」。

---

## 一、调用姿势（踩过的时间坑）

```bash
hermes -p health chat -c "Bot Chat" -m deepseek-v4.1-flash -Q --query-file <路径>
```

- 会话保留（会 Resumed session），它读 `profiles/health/` 下的 skills 与 `~/health/profile.md`。
- 长 prompt 一律写文件走 `--query-file`，不要 `$(cat f)`（引号/反引号会被 shell 吃掉）。
- 🔴 **前台必超时**：一次完整联网核查约 **9–10 分钟**，`terminal` 前台 420s 就断（本次断过一次，白等 7 分钟）。
  正确姿势：
  ```bash
  # terminal background=true, notify=true
  hermes -p health chat -c "Bot Chat" -m deepseek-v4.1-flash -Q \
    --query-file "C:/Users/.../query.txt" > "$LOCALAPPDATA/Temp/health_out.txt" 2>&1
  ```
  然后 `process_manage(action='poll')` 看状态，**不要连续 wait**（wait 上限 180s，连着等纯浪费）。
- 🔴 **落盘类任务别等 stdout**：它先把内容写进 `~/health/diet/YYYY-MM-DD.md`，再慢慢憋文字回执。
  判断「有没有落地」看目标文件的 **md5/mtime 变化**，不看进程输出。
  本次：md5 `6cdaf87…`（14:58 基线）→ `d050967…`（新增「加餐（打球前·已摄入）」一节）。

## 二、它的数据分三级，回执必须带级

| 级别 | 含义 | 能不能进档案 |
|---|---|---|
| **标签值** | 实物包装背面 / 官方详情页原始数 | 直接写，标来源 URL |
| **同款推定** | 薄荷库、fatsecret 上别的品牌的条目 | 可以写，但必须标「同款推定，非本品标签」 |
| **估算** | 它自己按品类取的区间中值 | 必须标「估算」，且在合计里单独说明占比 |

## 三、🔴 必做：复核它报的每一个数

用户明确要求「自报验证必复核」。本次实测它犯了两类错：

**错误 1｜把查得到的标签值当成「查不到」。**
它对 Tafe 苏打饼干写「没有任何一页列出每 100 g 营养表」，实际 fatsecret「山姆 黑松露火腿苏打饼干」
＋什么值得买横评双双给得出完整标签值。**它说查不到 ≠ 真查不到，自己再搜一轮。**

**错误 2｜串档取值不标注。**
它写香蕉嘌呤 24 mg/100 g，实际约 **3 mg/100 g**（差 8 倍）。凡它给的单点值，只要没有来源链接，一律当可疑。

### 复核手法三条（都很便宜）

#### ① 热量自洽校验 ← 判断「这是不是真标签」

```
蛋白×4 ＋ 碳水×4 ＋ 脂肪×9 ≈ 标称能量 ？
```

- Tafe 饼干 529：`8.6×4 ＋ 60.5×4 ＋ 28.1×9 ＝ 529.3` ✔ → 判为真标签
- 史蜜斯肉肠 215：`16.0×4 ＋ 4.2×4 ＋ 15.0×9 ＝ 215.8` ✔ → 判为真标签

**过不了自洽的，基本是二手推定或抄错，降级处理。** 这条比翻十个页面都快。

#### ② 双源交叉

同一个产品名在两个**独立**站点给出同一组数才敢当标签用。
本次饼干：fatsecret（529/8.6/28.1/60.5）＋ 值得买横评（脂肪 28.1、钠 692）→ 脂肪两位数完全对上。
只有单源的 → 降级「同款推定」。

#### ③ 按渠道反查规格（克重从箱规推，别在商品页里找）

会员店商品常多平台在卖同款，`箱规 ÷ 小包数` 就能反推单片/单根克重：

- Tafe 饼干 1.16 kg ÷ 40 包 ＝ **29 g/包**；用户说一袋 3 片 → 9.7 g/片
- 史蜜斯肉肠 840 g ÷ 26 根 ≈ 32.3 g/根；山姆 79.9 元 28 个 ≈ 30 g/个；京东分装 28 g/包 → 取 30 g

搜法：`品牌 + 规格 + 箱/包/根`，比在详情页翻参数快得多（HKTVmall / 什么值得买 / 海外代购站经常把箱规写成「1.16kg (40包)」）。

## 四、包装照片识别：别死磕，也别跟用户争

- 🔴 **裁切坐标估错时，`vision_analyze` 会给出高度确信但完全无关的结果**——本次一张裁错的 crop 回「高露丸」，
  另一张回「一根拇指 + 一张卡片」。**裁切前先用整图确认构图**，别在同一张图上连试多个 crop。
- 大字也会读错：本次把「黑猪肉肠」读成「午餐肉」，而且**两次独立读取自洽地重复同一个错**（自洽 ≠ 正确）。
- 📌 **包装品名以用户口述为准。** 他纠正就立刻照改，并回一句「是我读错了」，不要拿 vision 结果跟他辩。
  （本次记录里就写成「〔标签值，用户提供并指定采用〕」，保留口径来源。）
- 小字（净含量 / 营养表）读不清就**摆出来让他拍背面**——这正好落在他的确认边界内（菜名/份量他判断得了）。

## 五、落盘后的验证清单

- [ ] 记目标文件 md5/mtime 基线 → 跑完再取 → **变了才算落地**
- [ ] `grep` 把那两行原样贴回给他（他要完整回执，**禁压成摘要句**）
- [ ] 三级对账：逐项相加 ＝ 本餐合计 ＝ 今日累计增量
- [ ] 估算项在合计里单独标出占比（本次：钠 440.68 里 240 是估算，占 54.5%）
- [ ] 明确说「本节只到 X 餐，不是收盘数」——他会追问落点

## 六、写任务书时的模板骨架

```
【任务：<一句话目标>】
一、先纠正上一轮的错误（别沿用）      ← 有旧错误时必写这节
二、这两样他已经吃了（不是计划）      ← 已发生/未发生要写死，他不会重复说
三、已核实好的数据（直接用，别重搜）  ← 把自洽校验结论、来源、估算项一次给全
四、合计
五、要做的事：落盘位置 / 回读验证 / 回执格式 / 当日累计新落点
六、注意：估算必须标估算 / 不改历史档案 / 中文直接不客套
```

**关键：把「已经核好的数 + 哪些是估算」直接喂进去，比让它自己去搜准得多。**
它的联网能力不如你，但档案口径、嘌呤档、当日累计这些只有它会算——分工要分清。
