# 核算脚本化与历史回归测试（2026-11-13 实做）

用户问「把核算固化成脚本，会不会降低回复质量」时用。
**答案已实测：核算部分脚本化是数学上的完全等价，不降质量；口径判断部分不能脚本化。**

---

## 一、先分清「可脚本化」和「不可脚本化」的边界

历史脚本（如 `~/health/tools/_lu1112_calc.py`，209 行）里其实是两种东西混在一起：

- **1–113 行**：每 100g 营养 × 克数 → 逐项表 / 合计 / 算术自检 → ✅ **完全可通用**
- **114–209 行**：口径说明散文、假设清单、备份替换、哈希校验 → ❌ 每餐不同，继续手写

→ 所以「脚本化」指的是把前一半做成引擎，**后一半一字不动**。

---

## 二、引擎：`~/health/tools/nutri_calc.py`

- `Item(name, source, grams, per100, purine, purine_mark, raw_grams, ratio, warn)`
  —— 常规行，走「每 100g × 克数」。`raw_grams + ratio` 用于展示折算链（`25.00 × 55% = 13.75`）。
- `DirectItem(name, source, values, purine)`
  —— 直接给值的行，典型是食堂菜的**调味钠差额**（`含盐率 × 总重 × 400 − 食材自带钠`）。
- `render(meal, show_source=True)` —— 输出 markdown 表 + 合计 + 算术自检（蛋白×4 + 碳水×4 + 脂肪×9 vs 热量列）
- `compare_to(recorded, meal)` —— 与档案已记录数字逐项比对，返回 `(是否全等, 差异列表)`
- `split_by_ratio(total, ratios, ndigits=1)` —— 按比例拆分并保证合计精确

---

## 三、🔴 两个口径陷阱（都会让「算法变了」）

### ① 沙拉/拼盘按比例拆分的小数位

档案口径是**保留 0.1 g**：170 g → 78.5 / 27.2 / 39.3 / 20.1 / 4.9（合计正好 170.0）。
若按 0.01 g 拆：78.54 / 27.20 / 39.27 / 20.06 / 4.93 → **热量差 0.01、钠差 0.07**。
→ 必须用 `split_by_ratio(total, ratios, ndigits=1)`（最大余数法补舍入误差），不能直接 `round(x, 2)`。

### ② 调味钠差额是「直接给值的行」，不是「每 100g 的行」

食堂菜走含盐率法：`总钠 = 菜量 × 1.2% × 400`，再减去本行食材自带钠 = **差额行**。
若把它塞进 `Item` 当克数 0、每 100g 巨值，会污染「克数合计」。用 `DirectItem`。

### ③ 薄荷缓存里的多位原始值 ≠ 薄荷公布的 1 位小数

`boohee_api/cache.json` 存的是原始值（蛋白 1.18 / 脂肪 0.08 / 纤维 2.25），
而档案历史口径用的是薄荷**公布精度**（1.2 / 0.1 / 2.2）。

直接拿原始值算，分项与历史档案差 0.01~0.08（2026-11-13 实测：蛋白 16.94 vs 16.97、
纤维 3.38 vs 3.30、钠 290.56 vs 290.48）——**总量对得上、分项对不上，用户会当成「算法变了」**。

→ 用 `norm1(kcal=65, P=1.18, F=0.08, C=15.09, fi=2.25, Na=41.25, Ca=22.5)` 归一到 1 位小数。
口径决定：**取整**（保历史一致性），已写进引擎。

## 四、🔴 回归测试：用历史档案证明「没改算法」

**这是回答「会不会降质量」的唯一硬证据**——不是讲道理，是逐行对账。

做法：拿引擎重算历史某一餐 → 从 `diet/YYYY-MM-DD.md` 原文提取该餐表格 → 逐行逐项比对。

### 提取档案表格的三个坑（全踩过）

1. **`'食材' not in l` 会把「调味钠差额」行误杀**——它的来源文字里有「**食材**自带 26.79」。
   改成精确匹配首列：`c[0] in ('食材','---')`。
2. **`'---' not in l` 挡不住口径说明里的对照表**（可食率 60%/65%/68% 那张）。
   必须先 `split('### 逐项营养')[1].split('### 算术自检')[0]` 把范围卡死。
3. **对齐错位**：档案行末 9 列含克数，引擎 8 值不含 → 用 `av[1:]` 对 `ev`，否则全行报差异。

```python
t = open(r'C:/Users/<u>/health/diet/2026-11-12.md', encoding='utf-8').read()
seg = t.split('## 晚餐')[1].split('### 算术自检')[0]
seg = seg.split('### 逐项营养')[1]
rows = []
for l in seg.split('\n'):
    if not l.startswith('|'): continue
    c = [x.strip() for x in l.strip('|').split('|')]
    if not c or c[0] in ('食材', '---') or c[0].startswith('---'): continue
    rows.append(l)
```

### 实测结果（2026-11-12，两餐）

- **晚餐**：11 数据行 + 合计，逐项不一致 **0 / 12**。
  合计 = 800.25 g / 876.33 卡 / 70.23 蛋白 / 42.37 脂肪 / 56.73 碳水 / 5.31 纤维 / 959.14 钠 / 105.49 钙 / 617.73 嘌呤
- **午餐**：10 数据行 + 合计，逐项不一致 **0 / 11**。
  合计 = 434.75 g / 529.80 卡 / 41.72 蛋白 / 23.21 脂肪 / 40.26 碳水 / 4.74 纤维 / 1344.41 钠 / 121.56 钙 / 254.08 嘌呤

算术自检也复现：晚餐 889.17 vs 876.33 偏差 +1.47%；午餐 536.81 vs 529.80 偏差 +1.32%。

**保留 `_exp_1112_dn_replay.py` / `_exp_1112_lu_replay.py` 当回归测试**——以后改引擎就重跑，
能复现历史数字才算没改算法。

## 五、脚本化省的是「调试循环」，不是「判断」

旧流程算一餐：12 次 terminal（逐步试算/改错/重跑）+ 5 次 write_file + 5 次 patch = **22 次工具调用**。
新流程：1 次 write_file（写 spec）+ 1 次 terminal（跑引擎）= **2 次**。

**但引擎替代不了**：
- 看图确认商品标签参数（`vision_analyze`，不可合并——每张图不同）
- 口径判断（生抽入口 85%、酱汁附着 55%、沙拉按哪次构成缩放）
- 口径说明散文、假设清单

### 🔴 必须对用户说清的风险

**引擎只消除算术错误，不消除取数错误。** 若查错了食物条目（如把「紫甘蓝(加盐煮)」当成生的），
引擎会忠实地把错误放大到合计。→ **`source` 来源标签这一栏永远不能省。**

另外 `render()` 会把 `per100` 里缺的字段按 0 计并显式列 ⚠️，**不编数**——
这跟用户「查不到就照实说查不到」的要求一致。

## 七、上线推广的实测结论（2026-11-13，5 次真跑验证）

引擎建好 ≠ 健康助理会用。canonical `Bot Chat` 会话（400+ 条上下文）**不会主动读新 skill 或 `profile.md`**，
实测该会话 `skill_view` 调用次数为 **0**。

| 规则放在哪 | 老会话会不会用 |
|:--|:--|
| skill 正文（`health-analysis` / `meal-photo-analysis`） | ❌ 照旧写一次性临时脚本 |
| `profile.md`（它活跃窗口里碰过 12 次的文件） | ❌ 那次它连 `profile.md` 都没读 |
| skill 的 `description`（进系统提示） | ⏳ 系统提示冻结，要等压缩重建才生效 |
| **任务书末尾的固定尾注** | ✅ **立即命中** |

**所以：主实例每次派活都在任务书末尾带一句**（对用户零操作）：

```
---
【流程要求】核算的算术部分一律走 `C:/Users/<u>/health/tools/nutri_calc.py`：
写 spec → `cd C:/Users/<u>/health/tools && python <spec>.py`。不要写一次性临时脚本。
```

⚠️ 三个副作用要提前知道：

1. **`python -c` 在 `-Q` 单查询模式下被安全策略拦掉**（`BLOCKED: script execution via -e/-c flag`）。
   一律写成 `.py` 文件再 `python file.py`。这条要写进任务书尾注和 skill。
2. **新建临时会话验证新流程时，它会丢口径**——实测新会话把「鸡蛋可食 52.8 g」丢了，
   合计从 333.39 变成 336.0。**别拿新会话的结果当「新流程质量」**，它反映的是上下文缺失。
   只做「有没有调用引擎」这种结构性验证；要验数值必须用 canonical 会话 + 任务书尾注。
3. **验证看工具调用记录，不看自述**——它会说「已按流程」然后照旧写临时脚本。
   查 `messages.tool_calls` 里有没有出现引擎路径。

## 八、脚本目录归置（2026-11-13 实做）

`~/health/tools/` 长到 **400+ 个文件 12MB**，绝大多数是 `_bf1105_probe2.py` 这种一次性探查脚本，
污染 `ls` 和 `search_files`。

做法：顶层只留**正式工具**（无下划线前缀：`boohee.py` / `meal_boohee.py` / `fooddb.py` /
`meal.py` / `recognize.py` / `build_piece_weight.py` / `nutri_calc.py`）+ 回归测试 + `specs/`，
其余全部移进 `_scratch/`：

- 只移动**不删除**，写 `_scratch/_MANIFEST.json` 记录 moved / kept 清单，随时可移回
- 移完必须重跑回归测试 + `import` 冒烟（`boohee` / `meal_boohee` / `fooddb` / `meal` / `recognize` / `nutri_calc`）
- 文档里引用的历史脚本（`_lu1112_calc.py` / `_cake_verify.py` / `_ph1108_verify.py` 等）
  路径要同步改成 `_scratch/<名>`，否则以后按旧路径找不到文件
- 新 spec 统一写进 `tools/specs/`，不要散落在 tools/ 顶层
- 结果：顶层从 400+ 项降到 12 项
