# 饮食营养分析与体检指标结合

## 触发条件

- 用户问"减脂增肌每天三大营养素吃多少"、"我这样吃对不对"
- 用户报当天/某餐吃了什么，要核算
- **用户直接发餐食照片**（常一句话都不带），或问"这顿怎么样""帮我算一下"
- 用户发体检报告或指标，问饮食怎么改
- 用户发营养 App 的截图，问"这算得对不对"

> 用户个人基线（体重/体脂/体检原始值/运动习惯/目标）见 `references/user-health-baseline.md`。
> 每次分析前先读它，不要凭印象。

## 铁律

1. **算术一律用 execute_code/terminal 算，绝不心算**。用户会核对。
2. **只讲数值 = 归属档位，不用 App 给的标签**（用户明确纠正过："糖尿病前期等都是 App 给我的判断，你只要关注具体指标就好了"）。要引就引指南原文的切点和参考范围。
3. **参考值必须标出处**（哪本指南、哪张表），不写"一般认为"。
4. **自己说错要当场纠正**，不要含糊过去（本会话曾把 475g 西瓜说成"脂肪肝头号推手"，实际指南把西瓜列为"含果糖较少的水果"，真正要避免的是含糖饮料——已纠正）。
5. **不替代医生**：用药时机、风险分层、诊断归类一律写明"以医生为准"。
6. **🔴 引用阈值前先分清「指南原文」还是「临床惯例」**（2026-10 被用户当面纠正，见下节）。
7. **🔴 判断「血糖友不友好」看 GL，不看「糖 X 克」**。他说「我觉得从数据上不会有那么大影响吧」的时候，往往是他对——
   实测我拿「糖 ~20g」判「果糖+乳糖叠加、对餐后血糖不友好」，被他质疑；查 USDA 后发现 **GL 只有 10.2**，
   纤维/蛋白/脂肪一起压平曲线，**判词撤回**。
   → 要看的：**GL**、**同餐有没有纤维/蛋白/脂肪**、**糖的构成拆开**（果糖/葡萄糖/乳糖各占几成）。
   → 不要看的：单纯的糖克数。**「成分的名称」不等于「它的生理效应」。**
   详见 `references/macro-priority-and-glucose-gl-2026-10-25.md`。

## 🔴🔴 阈值口径：别把临床惯例说成指南，也别对无症状人群用痛风标准

**2026-10 用户原话（他认为我过度严苛，而且他是对的）：**

> **「我觉得它对于我的年龄和身体状况而言，没有那么可怕。我现在应该还没有到要控制钠和嘌呤到那么夸张的地步。」**

复查结论：**他完全正确，我把标准套错了档。**

### 三个被我用错的数

| 数字 | 我一直当成 | 实际是 |
|:--|:--|:--|
| **嘌呤 300mg/天** | 「指南红线，超了就危险」 | ❌ **《食养指南2024》全文没有任何 mg/天 数字**。这是**临床惯例**，不是指南条文 |
| **钠 2000mg/天** | 「每日预算，吃掉 xx% 额度」 | ❌ 原文是「**推荐**每天食盐摄入量不超过 5g」——**推荐上限，不是悬崖** |
| **人群档位** | 一律按痛风控制期 | ❌ 他是**无症状高尿酸血症期**（无发作史），有独立的、更宽的档 |

### 指南实际给的是什么

《成人高尿酸血症与痛风食养指南（2024 年版）》**按食物分类，不按每日配额**：

> 「第一类：含嘌呤高，每100g 含150～1000mg。第二类：含嘌呤较高，每100g 含75～150mg。
> 第三类：含嘌呤较低，每100g 含30～75mg。第四类：含嘌呤低，每100g 含＜30mg。」

原则部分只有一句：「以低嘌呤膳食为主，**严格控制膳食中嘌呤含量**。」

**分档是明确写了的**：无症状高尿酸血症期 / 急性痛风性关节炎期 / 痛风间歇期 / 慢性痛风性关节炎期。
附录 3 的食谱能量也分档：无症状期 1600–1800 kcal，急性/慢性期 1420–1550 kcal。

### 正确用法（写进每次输出）

1. **说「超线 xx mg」时，必须标明那是临床惯例口径，不是指南**。
2. **不要再对他用「占额度 xx%」这种预算式语言** —— 那会把人群目标变成个人红线，过度医疗化。
3. **判断落点换成「食物分类 + 全天模式 + 长期趋势」**，不是每顿饭的小数点。
   该盯的是**每 3 个月尿酸 + 体重 + 腰围**。
4. **瘦牛肉在指南里属「瘦肉适量食用」，不在「不宜」栏** ——
   不宜的是肥肉/内脏/加工肉/鱼籽蟹黄鱿鱼牡蛎蛤蜊，**别把瘦牛肉也扫进去**。

### 🔴 但有两件事**不能**因为「放宽」而丢掉

**① 离药物门槛的距离要算，这是硬事实**

《中国高尿酸血症与痛风诊疗指南（2019）》原文：
> 无症状高尿酸血症患者，血尿酸 **≥540 μmol/L** 起始药物；
> 或 **≥480 μmol/L 且伴合并症之一**：高血压、脂代谢异常、糖尿病、肥胖、脑卒中、
> 冠心病、心功能不全、尿酸性肾石病、肾功能损害。

用户 454，**离 480 差 26**，且已符合「脂代谢异常（TG/LDL/TC 全高）+ 超重（BMI 25.59）」两项合并症。
→ **措辞：「你没有富余量」，不是「你很危险」。** 单顿不是事件，但同样模式天天重复就是在磨这 26 的余量。

**② 减重期尿酸会被动抬高**
酮体与尿酸竞争肾排泄。**这个阶段的嘌呤负荷比体重稳定期更值得在意**——但仍是阶段性的，不是永久禁令。

### 🔴 长期做减法的副作用：蛋白被压垮

那次连追五轮，每轮都在「占额度 xx%」的框架里做减法，结果是**蛋白一路被压到 1.1g/kg**。
用户自己察觉到了（「我的蛋白质吃的不太够」）。

**对一个正在减脂保肌的人，蛋白不足的代价比 100mg 嘌呤大。**
→ 多轮追问时，**每一轮都要检查蛋白有没有被前面几轮的减法挤掉**。

**完整复盘（指南原文引用、为什么分档、药物门槛原文、以及我每一轮错在哪）见
`references/threshold-calibration-2026-10.md`。**

## 计算流程（固定顺序）

**第 1 步 定能量** —— 用去脂体重算 BMR（Katch-McArdle，**不依赖身高**，用户不给身高也能算）：

```
LBM = 体重 × (1 - 体脂率)
BMR = 370 + 21.6 × LBM
TDEE = BMR × 活动系数   (1.2 久坐 / 1.375 轻 / 1.55 中 / 1.725 高)
```

健康干预场景的能量还要对照《高尿酸血症与痛风患者膳食指导》(WS/T 560-2017)：
超重/肥胖者 **轻体力 20-25 kcal/kg**、中体力 30 kcal/kg。

⚠️ **但他的体脂率是自估的（22–23%，非体检数据）**——Katch-McArdle 的精度建立在体脂准的前提上，
自估时它反而**把误差引进来**。**给他算 BMR 时首选 Mifflin-St Jeor**（只用实测的身高/体重/年龄），
实测对照（体脂 22%→1731、25%→1679，同一个 Mifflin 一点不飘）见「热量赤字核算」节。

**第 2 步 钉死蛋白** → **第 3 步 定脂肪下限** → **第 4 步 碳水 = 剩余热量 ÷ 4**。
顺序不能反：反了就会变成"砍主食连脂肪蛋白一起砍"，掉的全是肌肉。

## 三大营养素标准（按目标，g/kg 体重）

| 目标 | 蛋白质 | 脂肪 | 碳水 |
|:--|:--|:--|:--|
| 通用健康/维持 | 1.2-1.6 | 0.8-1.0 | 剩余热量 |
| 增肌 | 1.6-2.2 | 0.8-1.0 | 剩余热量 |
| **减脂增肌/刷脂** | **2.0-2.4** | **0.8-1.0（下限）** | 剩余热量，3-5 g/kg |
| 高尿酸/痛风人群 | **1.0 保底，实操 1.2-1.8** | 0.8-1.0 | 50-60% 热量，全低 GI |

- 蛋白要**分餐**：每餐 0.5-0.6 g/kg 或 ≥30-40g
- 脂肪**低于 0.6 g/kg 是红线**（激素/脂溶性维生素）；但高尿酸人群要控嘌呤来源而非砍总量
- 里程碑证据：Longland 2016（AJCN）——热量赤字下 2.4 g/kg 蛋白 + 抗阻训练，4 周减脂 4.5kg 同时增肌 1.2kg

## 🔴🔴 营养素优先级：热量 → 蛋白 → 脂肪 → 碳水（2026-10-25 定型）

他会直接要这套逻辑：**「我想跟你确认一下逻辑，这样的话我自己去制定方案也行」**。
所以答案必须是**能自己套用的判断顺序**，不能四平八稳地说「都很重要」。

| 排位 | 项目 | 性质 |
|:--:|:--|:--|
| ① | **总热量缺口** | 硬前提，≤20–25% TDEE（临床惯例） |
| ② | **蛋白质** | **硬下限，不是「目标」**；1.6 g/kg 是赤字下保肌线，1.6–2.4 区间（运动营养学惯例） |
| ③ | **脂肪** | **有下限**：0.6 g/kg ≈ 48g，低于影响激素与脂溶性维生素（临床惯例） |
| ④ | **碳水** | **唯一可以有缺口的一项** |

**碳水没有硬下限。** 指南的 50–65% 供能比是**一般人群参考区间**，不是减脂期下限；
唯一的生理底线是 **IOM 碳水 RDA 130 g/天**——那是「避免生酮、供脑和红细胞」的线，**不是「最优」线**。
他每周做抗阻：**碳水长期低于 130–150 g 掉的是训练重量和组数**（机制推测）。

**判据：热量缺口已经存在时，「碳水有缺口」不是问题**——热量缺口才是脂肪减少的原因，碳水缺口只是手段之一。

### 四步决策流（交付时原样给他这句口诀）

```
1. 先看总热量 —— 2000 ±150 内随便。超了就减主食，不减蛋白
2. 再看蛋白到没到 129g —— 三顿各一掌肉/鱼/蛋 + 一份奶，自然落在 120–130。
   没到 → 加一份奶或茶叶蛋；到了 → 停，别追 157
3. 再看脂肪到没到 48g —— 2–3 勺油 + 一把坚果。这项只看下限，不看上限
4. 剩下的热量全给碳水 —— 剩多少吃多少。不够也不用补：不饿、训练不掉重量就够了
```

**唯一例外**：抗阻日重量明显掉 → 当天主食加一拳（约 50g 生米），**热量从脂肪里挪，不从总量里加**。

> 一句话：**蛋白是任务，脂肪是底线，碳水是零钱。**

⚠️ 顺带澄清过两条：**蛋白吃到 157 g 没有坏处**（1.95 仍在 1.6–2.4 内，代价只在蛋白来源带的嘌呤和钠）；
**热量缺口不是越大越好**（超 25% 会肌肉流失、代谢适应、抬高尿酸、依从性崩）。

## 减重速度：有硬性上限

| 人群 | 安全速度 | 出处 |
|:--|:--|:--|
| 一般 | ≤ 体重 1%/周 | 通用 |
| **高尿酸血症/痛风（🔴 推荐给他用这条）** | **每月 1.5-3.0 kg（≈0.35-0.70 kg/周）** | 中国高尿酸血症相关疾病诊疗多学科专家共识(2023) |
| 高尿酸血症/痛风（食养指南口径，更宽） | **每周 0.5～1.0 kg** | 《食养指南2024》原文「避免过度节食和减重速度过快，以每周减低 0.5～1.0kg 为宜」 |

🔴 **两条口径并存，推荐用保守那条（0.35–0.70）**，另一条作为出处说明一并给出——
别只报一个数让他以为只有一种说法。

体脂换算（回答「这个赤字对应多少」时用）：**1 kg 体脂 ≈ 7700 kcal**

| 周减 | 每日赤字 |
|---|---:|
| 0.35 kg | 385 kcal |
| 0.50 kg | 550 kcal |
| 0.70 kg | 770 kcal |
| 1.00 kg | 1100 kcal |

🔴 **快速减重会升高血尿酸**——酮体与尿酸竞争肾排泄，是诱发痛风急性发作的经典场景；低脂+快速减重还增加胆结石风险。给高尿酸用户定方案时必须先算速度再定热量。

## 🔴 他问「怎么才能把尿酸降下来」时（2026-10-21 实战定型）

核算跑顺之后他必然会转到**策略层**，而且**自己带方案来让你评估**，不是来听禁令：
「我不吃牛肉也不吃肋排就可以控制下来，但太难了，我不能真的不吃肉呀」
「我换一个思路，每天多喝水＋把有氧强度提上来，是不是有助于控制尿酸？」

**他要的是「一条能长期走的路」。** 回答里必须同时有：**肯定对的部分 + 指出反的部分 + 一个「不用戒肉」的答案。**

### ① 最常被提错的一条：**提高有氧强度 ≠ 降尿酸**

指南原文：「运动强度以**低、中强度**的有氧运动为主……**避免过量运动**。有氧运动以每周 4～5 次、每次 30～60 分钟为宜……运动期间或运动后，应及时补充水分。」

**判据：减重的杠杆是能量缺口，不是强度。** 他已经在打 1h20 双打，单次量顶满；
乳酸竞争肾排泄 + 出汗脱水是负分项（⚠️ 机制推论，指南只写「避免过量运动」，引用必须标明）。
要加就加**频率**和 **NEAT**（走路/爬楼/站办公）——不脱水、不需坚持。

### ② 饮水是唯一有指南背书的对冲动作

「每天建议 2000～3000mL。尽量维持每天尿量大于 2000mL。」（前提：心、肾功能正常）
**别让他记毫升数**——判据给「**尿色浅黄到接近透明就够，深黄就去倒一杯**」，符合他零记录的底线。

### ③ 「是不是得戒肉」→ 用**每克蛋白的嘌呤成本**回答，不讲情怀

| 食物 | 嘌呤 mg/100g | 蛋白 g/100g | **mg 嘌呤/每克蛋白** |
|---|---:|---:|---:|
| 鸡蛋(熟) | 1 | 13.1 | **0.1** |
| **牛肉(瘦)** | 105 | 20.0 | **5.2** |
| 鲜对虾 | 102 | 18.6 | 5.5 |
| 猪里脊 | 138 | 17.7 | 7.8 |
| 草鱼 | 134 | 16.6 | 8.1 |
| 猪小排 | 138 | 16.8 | 8.2 |
| **鸡胸肉** | 208 | 19.4 | **10.7** |
| 猪肝 | 275 | 19.3 | 14.2 |

**反直觉但真实：瘦牛肉是所有肉里单位蛋白嘌呤最低的之一，比鸡胸低一半。**
「不吃牛肉改吃鸡胸」是把账算反了。该砍的是**内脏（12.7–19.1）、蟹黄 182、浓汤**。

**再加一条「戒肉也到不了 300」的算式**（实测那天 757）：牛肉 157.5 ＋ 肋排 178.8 = 336.3，
全戒掉仍剩 **420.7mg** —— 剩下的是口蘑/菜心/杂粮饭这些他本来就该吃的。
→ 同时证明：**300 对他不现实；不该用戒肉去够它。**

#### 🔴 「300 好难」时：杠杆排序里膳食嘌呤不是第一位（2026-10-25 他原话）

> **「如果嘌呤想控制到每天 300 以下，好难啊，我一顿牛肉就快吃超了。」**

**先分清两件事：「防痛风发作」和「降血尿酸」不是一回事。** 他无症状、无发作史，要解决的是后者。

指南把 **限制嘌呤 / 限制果糖 / 限制饮酒 / 健康体重** 列为**四条并列原则**（第一、二、三、五条），
**没有排序，也没说嘌呤第一**：

| 因素 | 作用位置 |
|:--|:--|
| **酒精** | **生成端 + 排泄端双向**（指南原文：促尿酸生成 ＋ 血清乳酸升高减少排泄） |
| **果糖** | 生成端（诱发胰岛素抵抗） |
| **膳食嘌呤** | **只动生成端的一部分** |

→ **膳食嘌呤不是第一大杠杆，不要为了「少吃肉」的框架给它排序。**

**真要收，只收一处：动物内脏。** 指南全文唯一用「**应尽量避免选择**」的类别就是「肝、肾、心」。
不碰肉、不碰主食、不改吃饭方式——这是唯一符合他「我不能真的不吃肉」的收法。

### ④ 他不接受「蛋奶撑一天」

原话：「我全靠蛋和奶撑起一天的这个蛋白质摄入，这太困难了……坚持不下去的」。
→ **蛋白来源按他的接受度排，不按数据好看排。蛋奶是补充，不是替代肉。**

### ⑤ 他会把一天的账归因到单一食物，**别附和**

原话：「我知道了所有所有的过错都是中午那两根炸肋排带来的。」
正确回答是**拆两半**：脂肪 50.7%、热量 25.8% —— 对；**嘌呤只占 23.6%（晚餐牛肉只比它少 21mg）** —— 不对。
→ 一句「**你说对了一半**」比「是的」有用，附上具体百分比。

### ⑥ 他那句「一时尿酸上上去无所谓」要分开回

**日常波动 → 对**（看的是三个月复查值）；

### 铁律 8：他问「这个能不能当加餐」时，**先看碳水，不是先看热量**（2026-10-21）

**运动日的「加餐」分两种，判据完全不同：**

| 时机 | 要什么 | 为什么 |
|:--|:--|:--|
| **运动前 1–2h** | **碳水** | 蛋白/脂肪胃排空慢，临上场吃会顶着；蛋白质不能供能 |
| **运动后 30–60min** | **蛋白** | 修肌肉；这时仍是低脂优先 |

**实测**：蛋皇鹌鹑蛋一包 3 颗 = **25g、59 kcal、蛋白 3.9、脂肪 4.6、碳水 0.6**。
热量上完全放得下（当天还剩 675 kcal），**但碳水几乎为零——它顶不了打球前那一口**。
→ 答案不是「能吃 / 不能吃」，而是「**能吃，但要配一根香蕉**」。

**交付形态（照这个给，他不用再追问）**：
1. 这包本身多少（六项齐：热量/蛋白/脂肪/碳水/钠/嘌呤）
2. **一句话定性它适不适合这个用途**（「垫肚子可以，当打球前的加餐不够」）
3. 具体补什么、多少克（香蕉 88.5g = 82 kcal、碳水 19.5g）
4. 时间点（运动前 1–1.5h 吃完，别临上场）
5. 运动后补蛋白、且当天脂肪已超时点明「别再上油锅」

**顺带一条：蛋类不是嘌呤问题项**——表1-2 鸡蛋(熟) 1、鹅蛋(熟) 1、鹌鹑蛋(熟) **7**、松花蛋(熟) 1 mg/100g。

| 指标 | 合适 | 边缘升高 | 升高 |
|:--|:--|:--|:--|

**尿酸**：男性正常上限 420 μmol/L；高尿酸血症诊断=非同日 2 次空腹 >420；

**454 这种值 = 高于正常上限但未达药物起始阈值**，这个区分对用户很重要。

家庭自测方案=连续 5-7 天早晚各 1 次、每次 2-3 遍、取全部读数平均。
诊室高而家庭正常 = 白大衣性高血压。

⚠️ **但中国指南判"糖代谢状态"依据的是空腹血糖 + OGTT 2h 血糖，不是 HbA1c**。

### 🔴 肉汤的长期原则（2026-10 他直接问过「以后是不是尽量少喝」）

**不是「少喝汤」这个笼统说法，是三条具体的：**

| 类别 | 怎么吃 |
|:--|:--|
| 火锅汤、老火浓汤（熬 4 小时以上） | **不喝**。想喝就两三口尝味道 |
| 普通肉汤 | **一周 1–2 碗，每次不超过 200ml（大半碗）** |
| 清汤（汆过就取、没久熬） | 可略多，但也就是一碗 |

**🔴 关键不是「少喝」，是「喝汤那顿的肉要减半」——汤和肉抢的是同一份额度。**

**排序（从重到轻）**：火锅汤/老火汤 > 鱼汤（鲫鱼 154、草鱼 134，鱼汤总嘌呤高于畜肉汤）
> 鸡汤（整鸡带皮，鸡胸 208 是表里最高一档）> 排骨汤/猪骨汤 > 牛肉汤 > 蛋花汤/纯蔬菜汤（可忽略）。

**判据：看汤里煮过多少肉，不是看汤白不白。** 白浓汤主要是脂肪乳化，不是嘌呤。

**⚠️ 反直觉但重要：家里炖的汤比食堂例汤更该防。**
食堂例汤熬得短、水多肉少；家里炖汤 1–3 小时、肉多水少，**浓度反而更高**。
（例外：食堂有「老火靓汤/瓦罐汤」窗口，那和最浓的家常炖汤同级。）

**量级**：一碗 275ml ≈ 150–190mg 嘌呤 ≈ **临床惯例口径「控制期日上限」（~300mg）的 50–64%**。
它比同重量的肉更贵——**肉只吃一次，汤能喝一整碗水**。
⚠️ **~300mg 是临床惯例，不是《食养指南》原文**（指南全文无 mg/天 数字）——见上方「阈值口径」节。
讲给他听时用「这一碗相当于把一天的量吃掉一大半」，**不要用「占额度 56%」这种预算式语言**。

**「营养都在汤里」是错的**：同重量瓦罐鸡汤的蛋白只有肉的 **1/16**（1.3g vs 20.9g /100g）。
90% 以上的蛋白还在肉里，**砍汤不会缺蛋白**。真正该留的是**冬瓜、海带、萝卜这些料**
（低嘌呤、高钾、有纤维）。省下的蛋白额度换成蛋/奶/豆腐，**不是「不补了」**。

### 🔴 火锅锅底怎么选（前提：汤一口不喝）2026-10-24 实测

**判据：不喝汤时，锅底差异不体现在「汤里有多少」，而体现在「涮出来的东西吸走多少」。**
他问「辣锅 vs 番茄锅对我摄入影响大吗（都是底料不是自己熬的）」时按这张表答：

| 每涮 100g 食材多带走 | 辣锅（牛油/清油） | 番茄锅 |
|---|---:|---:|
| 脂肪 | 2–5 g（冻豆腐/油豆皮 8–15 g） | 0.5–2 g |
| 钠 | 50–150 mg | 30–100 mg |
| **糖** | 0.3–1 g | **1–3 g** |

→ 他添加糖只剩十几克余量时选辣锅；要保住的正是唯一还没超标的那一项。

**最有效的一条不是换锅，是下锅顺序**：**冻豆腐、油豆皮、宽粉、方便面最后下**（吸油是绿叶菜的 3–5 倍），
配「涮完锅边沥 3 秒」和「开锅撇一次浮油」。

## 🔴 调味品按「实际品牌标签」算，不是按品类均值

2026-10 核算一份炒饭时，我用「普通生抽 6390mg/100g」估钠，用户直接补了一句：
**「我用的生抽是薄盐生抽哎，蚝油也是薄盐蚝油。品牌都是李锦记。」**

**教训：他报菜时不会主动说调料品牌，但他手上有实物。问一句就能把误差从 ±30% 降到 ±5%。**

### 实战：实测出来的三个数

| 产品 | 标注 | 钠 | 糖 |
|:--|:--|--:|--:|
| **李锦记薄盐生抽（新版）** | 每 10g | **427mg**（4270mg/100g） | **1.8g**（碳水 1.9g 里 95% 是糖） |
| **李锦记薄盐蚝油** | 每 15g | **503mg**（3353mg/100g） | **2.6g**（碳水 3.4g 里 76%） |
| 对照：普通生抽 | — | 629–708mg/10ml | — |
| 对照：普通蚝油 | — | 均 3658mg/100g | — |

### 🔴 「薄盐」是用糖换的盐

上面两个产品，**糖占碳水的 95% 和 76%**。按生抽 8g + 蚝油 8g 计，
**累计带来 2.83g 糖**。

**量级判断（实测口径）**：2.83g 糖 ≈ 13 kcal，是全糖奶茶（~50g）的 1/15，
占添加糖建议量（<25g）的 13%——**单顿无所谓，不用为它改方案**。
但要说一句：**酱料糖是隐形糖，三餐都用会攒到 10g 左右**，到那个量级再管。
**推高糖化的从来不是这 3 克，是全天精制碳水总量。**

### 查标签的两条实操

1. **官方产品页常常只有配料表、没有营养成分表**（李锦记官网就是如此）——
   营养成分表在**电商详情页/包装实拍**上。找不到就让用户直接拍照
2. **⚠️ 新旧包装并存且数据不同**：李锦记薄盐生抽旧版标「每份 18g / 钠 761mg」，
   新版标「每份 10g / 钠 427mg」。**直接按数值比会得出「新版钠降了 44%」的错误结论** ——
   得先统一到每 100g。**看到「包装升级/随机发货」字样，必须问或看用户发的那版**

### 反直觉结论：换橄榄油没有意义

用户问「把油换成橄榄油会不会好」时，两个事实要同时给：

- **所有食用油热量和脂肪完全一样**：橄榄油/豆油/花生油/菜籽油都是 899 kcal/100g、99.9g 脂肪
- **饱和脂肪占比橄榄油并不最低**：橄榄油 14.1%，而**菜籽油 7.3%、茶籽油 7.0%、葵花籽油 10.0% 都更低**

→ 10g 用量下，橄榄油比菜籽油**反而多 0.68g 饱和脂肪**。对饱和脂肪上限（~22g）的影响 <3%。
**别把它当改进项推荐。**

⚠️ 但有一个真实的使用问题：**特级初榨橄榄油烟点约 190℃，花生油 225℃、玉米油 232℃**。
炒饭要高温出锅气，190℃ 的油容易冒烟。

## 食物核算：生重 → 熟可食部（常被忽略的一步）

用户报的是**原料生重**（如"白灼虾生重350g"）时，必须折算成实际吃进去的部分：

```
熟可食部 = 生重 × 可食率(去壳去头) × (1 - 熟制失水率)
```
参考区间：虾类可食率 55-65%、水煮失水 8-15% → 折算系数约 **0.53**
（350g 生虾 ≈ 185g 熟虾仁）

🔴 **营养总量按"生可食部"折算，不按熟重**——烹饪只失水，蛋白脂肪不流失。
用熟重 × 熟品成分表会重复计算失水。

🔴 **`--reply` 只适合短句，多菜+带解释的长句会被静默错解**（2026-10-26 实踩）：

他回的那句是「红烧肉改成红烧鸡块，可食用部分100g左右；第一道菜是炖白菜没问题，只是加了一点肉丝炖的不是加的粉丝，分量也大概150g，蒸山药大概100g，炒青菜大概120g」——
`--reply` **把整句当成了「红烧肉」的新菜名**，生成了一道叫「红烧鸡块，可食用部分100g左右；……」的菜，
**红烧那道菜直接消失**，而它 **exit=0 不报错**（与文档说的「解析不出来会 exit 2」不符）。

**判据：只要他一句话里改了两道以上，或带了「不是…是…」这类解释，就不要用 `--reply`，改用逐个 `--confirm --rename` / `--set`。**
`--set` 是**整碟毛重（gross_g）等比缩放**；他说的「可食部 100g」不能直接当 gross 用——
**凡他给的是「可食用部分」，先换算回整碟口径再 set，或直接改 `edible_g`。**

🔴 **健康助理会在「回答衍生问题」时凭空编造当天事实**（2026-10-26 实踩）：
让它解释「今天赤字为什么这么大」时，它写「今天能到 746 是因为**早餐没吃**（省 350 卡）」——
而当天早餐 350.1 卡早就存档在案。**存档小节本身没错，错的是回答里的叙事**，所以 grep 查不出来。
→ 转述前必须拿档案逐条核对话里的「事实性断言」（吃没吃、哪一餐、有没有运动），
对不上就在回复里公开纠正，别原话转发。

🔴 **`--reply/--set` 给的克数优先级最高**，覆盖模型估计值和 `edible_g`。
**他亲口给的数永远优先，不要再拿模型的值去质疑他。**

**几个开关的语义（别记混）**：

| 开关 | 作用于 | 备注 |
|:--|:--|:--|
| `--set "<菜名>=<g>"` | **整碟级** | 按 `dishes.gross_g` 等比缩放全菜 |
| `--set "<原料名>=<g>"` | **原料级** | 只改那一项，并跳过该菜的整碟缩放（`touched_dishes`） |
| `--oil "<菜名>=<g>"` | 该菜的油 | 他实测的油量；**只有一道菜有油时可直接写 `--oil 3`**。会写进 `oil_profile.json` 的「用户校准」 |
| `--rename "<旧>=<新>"` | 菜名 | 改名后会**用新菜名重判做法**→ 油量跟着变（「炒生菜→凉拌生菜」= 10g→3g） |

🔴 **`--confirm` 不重新识别**（读 `.pending_meal.json`，实测 0.27 秒）——所以**确认过的菜名/份量不会被覆写**。
但改提示词/改 `fooddb.py` 规则后，旧中间态**不会自动重算**，需要重新跑 `--card`。

⚠️ **菜名对不上时会静默落空**：用户说「杂粮饭」，模型那道菜叫「紫米饭」→
`--set "杂粮饭=90"` 命中不到，只会在输出里给一行警告。已加主食类同义兜底（饭/面/粥/粉 互通），
但遇到其他类别的别名对不上时，用 `--rename` 先统一名字。

```
① 照片 → 多模态模型（minimax-m3）→ 「菜名 + 整碟重量 + 做法」
        ↓
② 确认卡发他 → 他只看「菜名对不对 + 这一碟多重」
        ↓
③ 薄荷开放平台（主路径）→ 菜名查 code → 食物详情 → 每100g 营养 × 克数/100
   ↓ 薄荷查不到的菜，降级到自建《中国食物成分表》拆解（单独列表，不混算）
④ 合计 + 逐项标来源
```

🔴 **绝不让模型自己报热量。** 阿福那类 App 翻车的根因就是让模型连核算一起做了。

### 为什么改成薄荷为主（2026-10 落地）

《中国食物成分表》**没有复合菜**（宫保鸡丁/红烧肉/糖醋排骨全查不到），必须让模型拆原料；
**拆出来的调料克数全靠猜**——而这是整条链最大的不确定源。

薄荷有**专业人员维护的复合菜条目**，直接给「这道菜每 100g 多少营养」，
**把整层拆解难题省掉了**，调料克数是他们配好的。而且多给一列**嘌呤**
（用户尿酸 454，这是自建成分子表给不了的）。

**两个数据源的关系**：薄荷**主路径**，自建成分表**降级路径**（薄荷查不到时才用）。
两者口径不同，**在报告里必须分开列表，不能直接相加。**

### 🔴🔴 优先级：薄荷**完整菜品条 > 菜品组合 > 拆原料**（2026-10-22 用户当面定下）

用户原话：
> **「优先用薄荷库里的完整菜品或者库里菜品的组合，这样比较准，比如土豆丝炒肉丝，
> 如果没有的话，用炒土豆丝+少量肉丝叠加」**

**为什么会错**：拆原料只能查到生料自带的那点钠，**烹调盐/酱油全部丢失**——
实测同一道「青菜炒豆皮」：薄荷菜肴条 **钠 372mg/100g**，而拆原料（小白菜132+千张21+油0）只有 **154mg/100g**。
**差的那 218mg 就是盐和酱油。** 一顿三道菜这么拆，全天钠能少算 1000mg 以上。

**正确顺序：**

| 顺序 | 做法 | 例 |
|:--:|:--|:--|
| ① | **薄荷有同名菜肴条 → 直接用** | 「青菜炒豆皮」`fdc012fe`、「清蒸鲈鱼」`fd58c510` |
| ② | **没同名条 → 菜品组合叠加** | 「土豆丝炒肉丝」= 醋熘土豆丝 120g + 猪里脊 30g；「鸡蛋韭菜饼」= 韭菜炒蛋 |
| ③ | **只能拆原料时**：**必须在报告里标「本项不含烹调盐」**，并把盐单独列一行（表4.7：食盐 1g = 钠 400mg） | — |

**⚠️ 但组合时要防重复计油**：肉丝用**生料**（猪里脊）不要用「清炒肉丝」那道菜，
否则菜条里的油会和平底锅里的油重复算。
**同理防重复计盐**：菜条已含盐，别再叠加盐。

**第二次实测（同一天同一顿）三种口径的差别**：

| 口径 | 午餐热量 | 午餐脂肪 | 全天脂肪 | 全天钠 |
|:--|--:|--:|--:|--:|
| 全拆原料 | 1146.1 | 59.5 | 71.3（106%❌） | 1356（68%） |
| 部分用菜条 | — | — | — | — |
| **菜条优先（定稿）** | **1059.9** | **51.8** | **63.9（95%✅）** | **1878（94%）** |

→ **口径一换，脂肪从「超」变成「没超」，钠从「偏低」变成「接近上限」。同一顿饭，结论相反。**
所以遇到用户质疑数字时，**先回去核「这道菜用的是菜条还是拆的原料」，比调任何参数都关键**。

### 🔴 薄荷给的配方要不要按实际重量折算？——要，而且已经折了

用户会问这个问题（他看到的配方是 500g，实际只吃了 180g）。**答案：**

**薄荷返回的是「成品每 100g」口径，不是「原料每 100g」。** 它内部那个配方
（如凉拌牛肉 = 牛肉500g + 调料，原料合计653g）只是**它推导每100g 值的中间产物**，
与用户实际吃了多少克**无关**。

```
实测验证（线性）：
  薄荷「凉拌牛肉」= 114 kcal/100g
  180g → 205.2 kcal  (114 × 1.8) ✓
  500g → 570.0 kcal  (114 × 5.0) ✓
```

→ 用户报「这碟 180g」，算的就是 `180 × 114/100`。**不要把他报的克数去和配方总量比。**
（这类验证走缓存，不消耗额度，可以随时重跑给他看。）

### 🚦 确认卡是两道闸，不是一道

```
- 杂粮饭   → 杂粮饭   ✅
```

薄荷库里只有「拌生菜」（才对）和「凉拌生菜鸡胸肉」（错）；说「生菜沙拉」，

### 🔴🔴 薄荷的错误是「HTTP 200 + `success:false`」——曾把「额度用完」误报成「食物不存在」

**2026-10 实际翻车**：用户早餐的**茶叶蛋、牛奶**，确认卡上写成「❌ 薄荷库里没有」，
**但薄荷明明有**（一查：茶叶蛋 30 条、牛奶 30 条）。

真凶：额度用尽时薄荷返回的是

```json
HTTP 200  {"success": false, "message": "当天接口调用次数超过限制！"}
```

旧代码**只看 JSON 能不能解析**，能解析就当正常返回 → 找不到 `foods` 字段 → 返回空列表
→ 被写成「库里没有这道菜」。**它把「额度用完」伪装成了「食物不存在」。**

**判据（写进任何对接薄荷的代码）**：
1. **状态码永远是 200，成败要看响应体的 `success` 字段**
2. `success:false` 时把 `message` 当错误**向上抛**，不许降级成「空结果」
3. 额度类错误要**单独标记 + 短路**（当天后续请求必然失败，省得空转）
4. 上层文案必须区分「**接口报错**」「**额度用完**」「**库里真的没有**」三种情况

**推广**：凡是「错误伪装成空结果」的第三方接口，都会把基础设施问题变成数据问题，
让用户以为是数据源不行。**对接外部 API 时先问一句：它的错误长什么样？**

### 🔴🔴 付费 `detail()` 把「未收录」写成 `0.0`，比免费接口的空串更危险（2026-10-24 实测）

同一批食物（糯玉米 `fd1a186b`、全脂奶 `fdf1e8ef`、茶叶蛋 `fddb62ac`）免费 `public_detail` 与付费 `detail` 逐字段对撞：
**热量/蛋白/脂肪/碳水/纤维/钙 一个数都不差**；差别只有三处，且都是付费侧更差：

| 字段 | 免费 | 付费 | 真相 |
|:--|:--|:--|:--|
| 嘌呤 | 空串（未收录） | **`0.0`** | 三样全 0 = 全未收录，不是真零。表1-2 才对 |
| 糖 | 无此字段 | 牛奶 **0** | 牛奶碳水 4.9g/100g 几乎全是乳糖 → 实约 10.1g/206g |
| 胆固醇 | 无此字段 | 茶叶蛋 **0** | 1 枚蛋约 290mg，全餐实约 325mg |

**判据：付费接口返回 `0` 时，先按「未收录」处理，换源核过再入账。**
付费真正新增且可用的只有**饱和脂肪**（牛奶 2.1 / 茶叶蛋 3.1 g/100g，属正常值）。
→ **别为了拿嘌呤/糖/胆固醇去花额度**：嘌呤永远走表1-2，糖与胆固醇薄荷这两项填法不可靠。
→ 反过来说，免费 `public_detail` + 缓存足以支撑一次完整核算，0 次付费不是「没查库」。

### 🔴 额度纪律：写任务书给健康助理时必须带上这三条

一顿早餐曾烧掉 **23 次**（全天三餐必撞 50 次上限）。把下面三条写进 query-file：

| 规则 | 内容 |
|:--|:--|
| **R0 禁止盲批探测** | 不许写一个查询列表丢给脚本循环跑完再一起看结果。**每发一次搜索先看结果再决定下一次** —— 这是 23 次浪费的主因 |
| **R1 参照值不走 detail** | 需要对比某条嘌呤/热量时，用 search 结果里的 `calory`，或直接说「薄荷对该条未收录」并标注来源 |
| **R2 一顿的付费上限 = 样数** | 4 样最多 4 次付费。超过就停下来问，别硬跑 |

**并明确要求它走 `boohee.two_step(name, grams, context="...")`** ——
免费锚定 + 付费抓营养素，不要自己去拼调用。

### 🔴🔴 工具层改完，必须让真实调用方跑一遍验收（2026-10-20 教训）

「菠菜(煮)」只要没被那几次请求捞进候选池，bug 就永远不显现。

|:--:|:--|:--|

| 2 | **报出 `quota.json` 跑前跑后的差值** | 只有它自己报，才知道规则有没有真被遵守 |

**它的反驳要认真对待。** 本次它回的是：「匹配到 `菠菜(煮)` 27.6kcal，正确是 50.4kcal，
差 22.8kcal（−45%），油完全没算进去……**是排序不是搜索**」——

### 🔴 匹配不准时，别自己调字符串规则，上模型

本次实测：字符串匹配判据调了**四轮全崩**（「红薯干」冒充「红薯」、「茶叶蛋(蛋白)」冒充「茶叶蛋」、
「纯牛奶(脱脂)」冒充「全脂」）。**用户当时的判断是对的：**

> **「精确同名也会出问题，有时候会匹配不上，你能不能弄成语义理解？」**
> **「我希望尽量自动化且保证准确率。」**

**判据：同一类规则修正超过 2 轮还在相互打架，就停手改用语义模型。**
`two_step()` 已内置两层（规则优先、拿不准自动调 deepseek-v4.1-flash），
返回值带 `confident` / `by_llm` / `llm_reason`。

🔴 **`confident=False` 时必须在报告里标注，不能当准数用**——这是同一条原则的另一面。

#### 🔴 `confident=True` 只保证「名字对得上」，不保证「是同一道菜」

**已修但原则要留：** 他说「清炒菠菜」，薄荷里「菠菜」(28kcal) 会以 `exact` 胜出，
而他要的是放油炒过的「清炒菠菜」(42kcal)——**差 45%，油和盐全漏**。
（120g 差 16.8kcal / 152mg 钠）

**工具层已修三处**：① 做法词**逐级**剥离（清炒→炒→裸名，不是一次剥光）
② 说了做法词时，候选名不含做法词的一律降权 ③ 说了做法词时**强制走大模型复核**

**⚠️ 但仍要人工核一眼**：看到 `food_type=basic` 而他说的是道菜（带做法/带配料），
说明很可能回退到了生食材。**工具能兜大多数情况，兜不住全部。**

### 报告里要念给他听的「配方」

薄荷详情接口额外返回 `material_section`（**文档没写**），内含主料/辅料/调味
的完整克数 + 做法步骤。**他质疑数字时把配方念给他听**，比说「数据库里就是这样」有用得多。

#### 🔴 「这个盐合理吗」——用配方反推**含盐率**，一次算完（2026-10-22）

他问「这个盐你判断下是不是合理的」时，**不要凭感觉答**。做法：

```
含盐率 = 配方里的食盐克数 ÷ 成品总克数（主料+辅料+调味之和）
```

实测薄荷「青菜炒豆皮」：豆皮 150 + 油菜 300 + 花生油 20 + **食盐 4** + 大蒜 10 = **484g**
→ 含盐率 **0.83%**，成品约 3 人份、每人 1.33g 盐；他吃 150g（31%）= **1.24g 盐 / 496mg 钠**，
占每日 5g 限额 **25%**。
**判据：家常炒菜落在 0.8–1.2% 是正常水平，>1.5% 才算咸。**（⚠️ 这个区间是经验值，不是指南条文）

验证方法：把配方自算的钠（盐 4g×400 + 油菜 73.7×3 + 豆皮 20.6×1.5 ≈ 1647mg）
除成品重，得 **371.7mg/100g**，与薄荷标的 372.36 一分不差 —— **能对上就说明这条菜是该用的**。

#### 🔴 虾类/带骨肉：**只数不重要，总重 × 出肉率才是账**（2026-10-22／10-23）

电商写「罗氏沼虾 400g（16–24 只）」，薄荷单位却写「一只 80g」。**两者不矛盾，别纠结。**

| 口径 | 算法 |
|:--|:--|
| 薄荷单位 | 一只毛重 80g → `eat_weight` **30.4g**（出肉率 38%） |
| 电商包装 | 400g ÷ 16–24 只 = 每只 **17–25g** |
| **实际核算** | **按总毛重 400g × 38% = 可食 152g**，与只数无关 |

→ **他报「买了一份 X g」时，永远用总重 × 出肉率**，不要去数只数、也不要用薄荷的「一只 80g」去乘。
→ 呓类嘌呤：表1-2 **罗氏虾没条目**，用淡水虾类比（青虾 180 / 江虾生 231）与海虾（鲜对虾 101.5）夹区间，
**并明说是推算不是查表**。实测一只虾肉约 30g ≈ **55mg 嘌呤**，这是最容易被他低估的一项。

#### 🔴 比价也要折到可食部：**只有同平台同形态才可比**（2026-10-24）

他发两张**同一平台、同为鲜活**的商品页问「黑虎虾是不是更划算」。
**带壳/带骨商品比价，必须折成「元/斤可食肉」**，只看牌子上的单价会得出反向结论：

| | 黑虎虾 | 罗氏虾 |
|---|---:|---:|
| 页面 | 300g / 8-12只 / ¥38.61 | 350g / 10-17只 / ¥39.90 |
| 折毛重 | 64.35 元/斤 | **57.00 元/斤（更便宜）** |
| 出肉率 | 55%（薄荷 `units` 33÷60）／59%（成分表斑节对虾） | 38%（30.4÷80）／40% |
| **折虾肉** | **109–117 元/斤** | **142–150 元/斤** |

→ **毛重上黑虎贵 12.9%，吃到嘴里反而便宜 22–23.5%。** 多出来的 50g 毛重抵不过少掉的 32g 虾肉。

🔴 **跨渠道的价不能直接比。** 上一轮拿「塘口批发罗氏 33 元/斤」对「进口冻品黑虎 49 元/斤」，
得出「折成虾肉两虾持平」；用户一换同平台两张图，**结论直接翻转成黑虎便宜 22%**。
**比较前先确认三件事：同一平台？同为鲜活/冷冻？规格相近？** 三个都一致才允许下结论，否则明写「不可比」。

**顺带一条口感问题的正确答法**：他问「是不是错觉」时，先用可查指标定性——
水分 黑虎 73.6% vs 罗氏 78.0%（**低 4.4 个点，这就是「更实」的直接解释**）；
但**蛋白反而是罗氏高（20.6 vs 18.6）**，且两条数据碳水口径不一致，**这一项要明说不能拿来下结论**；
「海水虾含水量低、肌节长」属于**机制推测，不是查表**——三者必须分开标。

#### 🔴 带骨肉（羊蝎子 / 排骨 / 带骨锅）：**薄荷的「一块 X g 可食」经常不能用**（2026-10-23）

实测一顿食堂**羊蝎子锅 7 块**。薄荷 `basic`「羊蝎子」`fdfe349d` = **203 kcal/100g、蛋白 19.0、脂肪 14.1、钠 81** ——
**这组数其实是「羊肉(肥瘦)」的纯肉值，不是带骨块的值。** 它的 `units` 写「块 **70g** / `eat_weight` 70g」，
**照它乘 7 块 = 490g 可食 —— 7 块骨头出近一斤肉，明显不合理。**

**判据：`basic` 条目的营养值是「每 100g 可食肉」，`units` 里的块重也是纯肉折算，不是带骨块重。
带骨菜一律走「**总毛重 × 出肉率**」。** 羊脊骨每块毛重约 100g、出肉率 **25–35%**（他吃过，说「可食用部分挺少的」）。

**怎么让他确认出肉率 —— 别问「出肉率多少」**（他答不了），换成**他能凭手感判断的三档**：

> 「7 块加起来，平均每块能剔出的肉大概是小半颗鸡蛋（25g）／大半个鸡蛋（35g）／还是一整颗鸡蛋（50g）？」

他当场答**「出肉 35% 我觉得比较合适」**，口径立即锁定。**这比给一串百分比有效得多。**

**三档必须一起给，因为最高档会翻转晚饭的结论**：

| 每块出肉 | 7 块合计 | 午餐热量 | 午餐脂肪 | 早+午脂肪占比 |
|---|---:|---:|---:|---:|
| 25g | 175g | 582 | 28.0 | **60%** |
| **35g（他选的）** | **245g** | **724** | **37.8** | **75%** |
| 50g | 350g | 938 | 52.6 | **97% ❌** |

→ 最高档时**当天脂肪已经吃到 97%**，晚饭基本没有油脂空间；最低档还剩 27g。**这个差距直接决定晚饭怎么吃，所以必须让他看见。**

**他会补一张「筷子夹着那块肉」的照片**做尺寸参照（2026-10-23 实测，一句话都不带）。
处理姿势：`vision_analyze` 加 `region` 裁到那块肉，以**塑料勺勺头 ≈4cm、普通筷子 ≈22cm** 作标尺问
「长/宽/厚各多少厘米」，测得 **9×7×2.5cm**。
⚠️ **但照片只能看到一面**：vision 会报「骨头只占 5–10%、附着肉约 90%」，那与带骨脊骨的真实情况矛盾。
**照片只用来定块头，不用来定出肉率；出肉率以他说的为准。**

**炖煮类（羊蝎子/火锅/汤锅）的嘌呤**：表1-2 用对应肉类条目（羊肉(生) **109**、牛肉 105、猪肉 138），
并注明「炖过的嘌呤部分溶进汤里，**只要不喝汤，实际不高于这个数**」——这是这条判断偏保守的方向。

**汤汁口径**：他说「没喝汤、没用汤泡饭，只是吃的时候挂一点汁」→ **汤按 0 计**（同 2026-10-22 酸汤肥牛那条），
报告里写明「汤汁未计入」即可，别再追问他挂了多少毫升。

| **模型菜名不稳定** | 「--set」修正被静默丢弃 | 双向子串 + 主食谱义 + 单菜直认；**但根因往往是 max_tokens 截断** |
| 照片糊、无参照物 | **认错菜**（实测有） | 无——只能靠低置信度提示用户确认 |

⚠️ **加工品名的危险在于错的是「构成」不是「总量」**：
实测一图修复前 952 kcal / 碳水 99.6g，修复后 970 kcal / 碳水 12.9g。
总量几乎没变，但"脂肪还行"的假象被戳破——真实脂肪 86g = 目标 67g 的 **128%**。
**只看总量对不上时才发现，是最容易漏的一类错。**

#### 🔴 喷雾式油：**入口率改 90%，不套 65%**（2026-10-25）

他把油换成喷雾式橄榄油后，历史「下锅 10g × 65% = 6.5g」整套作废。

| 喷雾量 | 入口油（×90%） | 热量 | 脂肪 |
|---:|---:|---:|---:|
| 1 g | 0.9 g | 9.0 | 0.90 |
| **2 g（主值）** | **1.8 g** | **18.0** | **1.80** |
| 3 g | 2.7 g | 27.0 | 2.70 |

- 档位是**估算**：市售油喷雾常见标注「每 1/3 秒 ≈ 0.25g」，26–28cm 锅铺一层薄膜需连续喷 4–12 秒 → 1–3g；品牌间喷出量可差 2–3 倍，但三档极差只有 16.2 kcal
- **入口率 65% → 90%**：65% 是给「下锅 10g、盘底会积油倒掉」用的；**总量只有 1–3g 时形不成能倒掉的积油层**，绝大部分被食材带走
- 🔴 **先确认是不是纯油罐**：纯油（压缩空气/氮气推进，不产热）→ 899–900 kcal/100g；**油水乳化型可低至 200–400 kcal/100g**。他没说品牌时按纯油计，并点明「看一眼配料表能定死"
- 相较历史 6.5g：**−4.70g 脂肪、−42.2 kcal**——这是换喷雾的全部收益，别夸大成「饮食改善」

**让用户在照片里放双筷子或勺子**是最有效的精度提升手段——主动提一句。

### 🧭 架构原则：让模型「做选择题」，不要「写数字」

用户 2026-10 的诉求原话：

> **「我希望可以有一个相对固定的程序，让大模型知道第一步怎么做、第2步怎么做、
> 第3步怎么做，这样的话就是误差可能还是会有，但是起码流程是相对确定的。」**

起因是他担心「大模型常识里没有的菜就只能瞎猜」。**三条结论：**

1. **模型对冷门菜的覆盖度远超预期**——实测「撒撇」（云南傣族）、「秃黄油拌饭」（苏州）、
   「擂椒皮蛋」（湘菜）**全部认识**；不认识的（「凤凰盏」）会主动说
   *"could refer to a few things... I cannot accurately determine"*，**不硬编**。
   → 提示词加「**第 0 步：先判断认不认识**」（`known: certain/variant/guess/unknown`），
   把不确定性显式化，`unknown` 时明写"不要编" + confidence 压到 0.2。
2. **拆解不需要图片**——模型原话 *"no image was provided... 但我能基于菜名拆解"*。
   它做的是「菜名 → 原料」的知识检索。**所以拆解应独立于识图，可缓存、可复现、可单独修正。**
3. **「固定」的本质是输出空间有限**——步骤分得再细，只要每步还在自由生成数字，流程就不确定。
   要的是「模型输出枚举值（做法 9 选 1）→ 程序查表给数字」。**模型从生成器退化成分类器。**

**目标函数也要换**：不追「每餐算准」（人类专家看照片估份量误差 41-53%，做不到），
改追 **无系统偏差 / 永不崩溃 / 不确定可见 / 可复现**。其中**无系统偏差最关键**
——总高估 80 kcal × 3 餐 = **240 kcal/天**，会让他误以为自己在缺口里。

完整框架（四层降级、6 槽位、逐数字标来源、误报比漏报更伤信任）见
`references/meal-pipeline-architecture.md`。

## 🔴 视觉模型 JSON 稳定性（2026-10 实测定型，别再调回去）

**症状**：同一张照片，每次识别给出的菜名都不一样；偶发「返回了内容但解析不到 JSON」。
**根因不是采样随机，是 `max_tokens` 太小。** 实测 minimax-m3 三次调用的用量：

```
reasoning_tokens   1244 / 5499 / 3572     ← 思考量波动极大
completion_tokens  2604 / 6633 / 4753     ← 曾用满 6633
```

原来设 8000，**某次已用掉 6633，只剩 1300 余量** → 思考多一点，JSON 没写完就被砍断。

**四条已落地的修法（缺一不可，别单独回退任何一条）：**

| 项 | 值 | 为什么 |
|:--|:--|:--|
| `max_tokens` | **32000** | 消除截断（思考最高用过 5499） |
| 超时 | **400s** | 思考长时耗时长（实测最长 90s，网络慢会更久） |
| JSON 提取 | **优先取含 `items` 的那份** | 模型会在 `think` 里试写草稿 JSON，原来取第一个代码块会**抓到草稿** |
| 提示词 | 明写「推理结束后只给**唯一一份**最终 JSON，不要打草稿」 | 减少多版本 |

**验证结果**：连续 5 次 → **5/5 成功、零重试、主菜菜名 5/5 全对、做法 5/5 全一致**
（改造前是 5 次给出 5 个不同菜名）。

### 🔴 禁止降级到其它模型——失败就重试同一个（用户明确要求）

用户原话方向：**「既然只有 minimax-m3 是准的，那就只允许用 minimax-m3 识图，不要降级」**。

**理由（用户是对的）**：同一张图，降级模型给出的菜名和 minimax-m3 **不一样**——
把「凉拌牛肉」认成「香菜炒牛肉」，还**凭空编出照片里没有的「花生米」**。
**「给出看起来正常但其实是错的答案」比「给不出答案」危险得多。**

**实现**：`recognize.py` 的 `FALLBACK_MODELS` 默认不启用；失败时**重试同一个模型**
（`RETRY_SAME = 3`），三次都不行就**明确报错**让用户重发，绝不换模型顶上。
应急才显式传 `allow_fallback=True`，那时报告会打 `⚠️ 本次识别用的是 xxx（非 minimax-m3）`。

**这条原则可以推广**：凡是「结果会被用户当成事实依据」的模型调用，
**降级换模型 = 引入静默的错误**，宁可失败重试。

（本次会话把此策略同步写进了健康 profile 的 `meal-photo-analysis` skill。）

#### 🔴 模型连挂 3 次之后：**别让他重发照片，改成「他报菜名 + 你估克数」**（2026-10-22 实测）

实测 minimax-m3 连挂三次（`HTTP500` + 两次 `TimeoutError`）。按规矩不降级是对的，
**但「三次全挂 → 让用户重发照片」不是唯一出路**——这时他的口述往往已经把菜名说全了：

> 「蒸鱼没问题，杂粮饭没问题，青菜炒豆皮没问题，另外是鸡蛋韭菜饼（没什么面粉就是鸡蛋+韭菜），
> 酸汤肥牛（我只吃了肥牛 150g 左右，沾少量汤汁），另外一个是土豆丝炒肉丝（肉丝少量）」

**判据：菜名齐了、只缺克数 → 直接走口述路径，手写一张确认卡让他改数字。**

```
1 蒸鱼 220g
2 杂粮饭 180g
3 青菜炒豆皮 150g
4 鸡蛋韭菜饼 120g
5 酸汤肥牛（只算肥牛）150g
6 土豆丝炒肉丝 150g

（改数字或菜名后整段发回；对就回「对」）
```

→ **「模型挂了」不是死路，「他还没报菜名」才是死路。** 先问菜名，再谈重发。

**多菜场景两条实测规律：**

1. **一桌 5–6 道菜时，模型的错集中在「主语」不是「有没有」**——把酸汤肥牛认成「肉片汤」、
   把鸡蛋韭菜饼认成「蔬菜煎饼」、把土豆丝认成「笋丝/豆皮丝」。**数量对了、名字错了。**
   → 确认卡要**一次列全六行**让他逐行改，不要一次只问一道。
2. **他报菜名时带的括号限定词，才是这道菜真正的口径**：
   「没什么面粉就是鸡蛋+韭菜」→ 从「面饼」改判「蛋＋菜」，**碳水差一个量级**；
   「只吃了肥牛 150g，沾少量汤汁」→ **汤不计入**（同 `edible_g` 规则）。
   核算完回头对一遍：**他括号里写的每一个词，进账了吗？**

## 🔴🔴 多轮追问：一顿饭被连续追问时的正确姿势（2026-10 实战定型）

他会就**同一顿饭连追四五轮**：原方案 → 改方案 → 补一个新信息 → 补一张照片。
每轮都在问「这样行不行」。**这是本项目最高频的交互形态，比单次核算更常见。**

### 铁律 1：**他没提的餐 ≠ 他没吃**（我被明确纠正过）

我把「午餐完全空白」当成最坏假设、说全天账建立在「你没吃午餐」上。**他纠正：**

> **「不是呀，午饭我没跟你讲吃了什么不代表我没吃午饭呀。」**

**所以**：
- **没提到 = 数据未知，不是数据为零。** 说「午餐未知」，不要说「假设你没吃午餐」
- 全天账里**单独列一行「未知」**，不要用 0 填进去再算总计
- 缺的那餐**主动要一次**（「午餐吃了什么？」），他给了就补算，**不要自己填假设**
- ⚠️ 这条适用于一切「用户没主动说」的场景：漏报的药、漏报的加餐、漏报的运动

### 🔴 铁律 1b：**他提到要吃的餐 ≠ 已经吃了**（2026-10-24 被当面纠正）

这是铁律 1 的反向版本，同一天内就踩了。他说「如果下午吃了这个 1/4 块蛋糕，晚上再吃一顿放纵餐」——
**这是计划，不是已发生。** 我却把它算进「全天累计」并标成「已摄入」，他直接纠正：

> **「我的蛋糕还没吃呢，蛋糕你要去掉的蛋糕跟晚饭都没吃呢。」**

**判据：只要他没说「吃完了 / 刚吃了 / 正在吃」，一律按「计划」处理——**
- 单独列一行「**计划中（未发生）**」，**不进「已摄入」合计**
- **不写进 `diet/` 的累计行**，也不参与「还剩多少」的扣减
- 他要的是「假如吃了会怎样」时，明确写成「**假如吃了**」版，和已摄入分两栏

⚠️ 两个方向都要防：**没说 ≠ 没吃**（铁律 1）／**说了要吃 ≠ 已经吃了**（本条）。

#### 🔴 计划 → 实吃的转换：**必须按实物整块重算，不能沿用计划版**（2026-10-26）

他晚上说「**我回来吃加餐了**」并直接报克数时，**计划那一版作废**。实测两版差得非常远：

```
计划版：酸奶100g ＋ 蓝莓80g ＋ 茶叶蛋1个        = 179.2 卡 / 18.4 蛋 / 338.8 钠
实吃版：酸奶300g ＋ 蓝莓125g ＋ 蜂蜜10g（没有蛋） = 291.0 卡 / 33.9 蛋 / 115.7 钠
```

**三处变化同时发生，每一处都足以推翻计划价**：① 份量变 3 倍 ② **计划里有的东西没吃**（茶叶蛋）
③ **计划里没有的东西出现了**（蜂蜜 10g）。

**判据：**
- 他报实测克数时，**以他这次说的为准，计划版明写作废**，不要两者混用、不要取平均
- 「少了的那一样」要在报告里点一句「原计划的 X 本次未食用，不计入」——**他记得计划里有，不点他会以为漏算**
- **计划里没出现的新成分**（蜂蜜/果酱/坚果碎）等于新条目，去查它的值，**别拿酸奶的碳水去顶**

🔴 **赤字这时才能定稿**（他此前明确说过「等加餐结束之后才能记赤字」）。顺序固定：
**加餐实物核算 → 全天合计 → 赤字 → 他确认 → 才存档**。

🔴 **存档时不是「追加一节」，是把「## 加餐（计划中·未食用·不计入合计）」整节改成已食用**，
并同步改全天合计、汇总节标题、以及「若再加这套」那类假设性备注。**否则文件里会同时存在计划版和实吃版两套加餐账。**

**包装宣称可以交叉验证克数**：君岛/Larmilk 酸奶标「**每杯 33g 蛋白**」、表上 11.0g/100g →
33 ÷ 11.0 × 100 = **300g 正好是一杯**，与他报的 300g 互证。
→ 凡包装上写了「每杯/每份 X 蛋白」这类宣称，**拿它反推份量、与用户报的数对一遍**，是最便宜的核验。

**蜂蜜口径**（这次差点用错）：**304 卡/100g、碳水 82.4g/100g**（USDA FoodData Central）。
我一度用了 75.9（把糖当成了全部碳水）——**10g 差 0.65g 碳水**，量级小但方向是系统性低估，**别再用那个数**。

### 铁律 2：**判断维度由他指定，别自作主张换维度**

> **「蛋白的这个缺口你暂时不用把它当成主要的判断依据，你主要帮我判断一下嘌呤和脂肪就好了。」**

他指定维度后：
- **不要在推荐理由里夹带他不想要的维度**（我曾用「蛋白多 12g」论证方案 K，被点名否掉）
- 该维度如果确实还很重要，**一句话带过或直接不提**，不要展开论证
- 但**数据可以照算照列**——他要的是「结论按哪个维度给」，不是「别的数不许出现」

### 铁律 3：**多轮之间口径必须完全一致**，否则两个数没法比

改方案时最容易犯的错是每轮重新选口径（换了数据源、换了假设、换了熟重生重），
**结果「429 → 277」这种对比根本不可信**。

每轮开头明确写一句：「口径与上一轮一致（凉拌油 8g、杂粮饭按熟重、嘌呤查表1-2）」。
**沿用上一轮的假设并说明，别换口径。**

#### 🔴 但「沿用上一轮口径」= **整表照抄**，不能只抄合计行（2026-10-23 我自己踩的）

实测：新建 10-23 记录时，早餐三样「与 10-22 完全一致」。我**只把合计行（295.6 / 15.30 / 12.14 / 32.43 / 385.6 / 14.9）照抄**，
**行值却按另一套 mg/100g 重算**（红薯 28.8、牛奶 5.0）→ **三行相加 34.3，合计行 14.9，对不上**。

**判据：凡写「沿用上一轮口径」，行值和合计必须整块 copy，不许一半旧一半新。**
单项差异看着小（十几毫克），但**行和 ≠ 合计**会被他一眼抓出来，而且他没法判断哪个是对的。

**健康助理这次主动报了这个矛盾、并拒绝替它抹平**（「我按任务书原样写入，并在表下加了说明，没有擅自改成一致」）
——**这是它做得对的一次，不要因为「它没修」就批评它；该修的是我的任务书。**

**收尾必做**：把每张子表的行和与合计行各算一遍，对不上**就地改**，
不要留「⚠️ 本表存在行和与合计的差异，已如实记录不修正」——他只要一个数，不要两套。

### 铁律 4：他改方案时，要算「**净变化账**」，不能只说「改善了」

他问「我改成 X 会不会改善」时，**默认答案是「会改善」**——因为他在往好的方向改。
真正有价值的是**省下的和加回的相抵之后还剩多少**：

```
虾 300g毛重（可食177g）  257mg → 0        ⇒ 省 −257mg
牛肉 120g → 220g         126mg → 231mg    ⇒ 增 +105mg
─────────────────────────────────────
净变化 −152mg（吃回去 105/257 = 41%，净存 59%）
```

**结论措辞**：「不是白减，回收四成、净赚六成」——比笼统说「改善了」有用得多。
**同时必须指出他在别的维度上付出了什么代价**（那次是脂肪 +7.3g、蛋白 −13g）。

### 铁律 5：换食材先算「**蛋白/脂肪效率比**」

判断「用 A 换 B 补蛋白值不值」，一句话就能定性：

| 食材 | 蛋白 | 脂肪 | 蛋白/脂肪 |
|---|---:|---:|---:|
| 虾 300g毛重（可食177g） | 32.9g | **1.4g** | **23.2** |
| 脱脂奶 300ml | 10.5g | 0.9g | 11.7 |
| 牛肉 120g | 24.0g | 10.4g | 2.3 |
| 牛肉 220g | 44.0g | 19.1g | 2.3 |
| 豆腐 150g | 9.9g | 8.0g | 1.2 |

**虾每克脂肪能换 23g 蛋白，牛肉只有 2.3g，差 10 倍。**
→ 「虾换牛肉补蛋白」必然**同时付脂肪和嘌呤两笔代价**，这不是他算错，是食材属性。
→ 真正低脂高蛋白的替代是**脱脂奶、乳清蛋白、蛋清、低嘌呤白肉鱼**，**不是红肉**。

⚠️ 顺带一条反直觉的：**鸡胸的嘌呤（208mg/100g）比鲜对虾还高**，不能当「低嘌呤蛋白」推荐。

### 铁律 6：**食材部位不同，成分表的「代表值」会估高**

用户报的部位越具体，越要警惕。实测「牛吊龙」（牛背脊长肌、瘦肉部位）按
「牛肉代表值 8.7g 脂肪/100g」算，但「牛里脊」只有 0.9g/100g——**差近 10 倍**。

**做法**：给结论时**明说这个数可能偏保守**，并给出两端（「真实值大概在两者之间、更靠近瘦肉那端」），
**不要拿一个代表值当铁律**。他会揪这种归因问题。

### 铁律 7：食堂/外卖场景，**炒菜油是脂肪主因，且照片读不出来**

实测一顿食堂套餐：三道菜的炒制油 **33g，占午餐脂肪的 62%**。
照片只能看出「菜面油亮/盘底是否积油」，**克数读不出来**。

**对策：按低/中/高三档各算一遍，主表取中值，敏感性单独列一节。**
实测那顿三档分别是 44 / 53 / 78g 脂肪——**跨度 1.8 倍，比任何食材克数的误差都大**。

**要对他讲清的结论**：一天脂肪超标的主因往往**不是他晚餐吃的那块肉**，
而是**午餐食堂的油 + 下午那杯全脂奶**（两项合计 59%）。
**「今晚能做的只有不要再往上加，没法拉回来」**——这种话要直说，别给虚假的希望。

### 🔴🔴 铁律 8：食堂/家常菜核算有**三个系统性高估**，每个都可能差 10g 以上

2026-10 他一句「**怎么会有 53g 的脂肪啊？你具体的给我拆解一下**」，
查出来午餐脂肪 **53.2g → 27.5g，虚高 25.7g（94%）**。**他的直觉是对的，三项错叠在一起。**

| # | 错在哪 | 影响 | 判据 |
|:--|:--|--:|:--|
| ① | **把「一道菜的重量」当成「纯肉重量」** | −3.9g | 炒菜里有辣椒/蒜苗/姜丝/配菜。湘菜小炒肉占比约 **70–80%** |
| ② | **部位密度用了「代表值」** | −9.3g | 见铁律 6。食堂不会用里脊，常规是后腿/牛霖，**2.0–4.2 才是合理区间** |
| ③ | **下锅油当成吃进去的油** | **−14.4g** | **最大的一个**。盘底积油筷子夹不走 |

**③ 的算法**（这是最容易漏、影响最大的一条）：

```
下锅油 × 入口比例 = 入口油
  盘底不积油（菜面油亮但盘干）  65%
  盘底有积油                   45%
  油亮无积油                  55%
```

实测那顿：33g 下锅 → **18.6g 入口**。旁证——卫健委数据，我国居民人均每天烹调油
**摄入** 43.2g（入口口径），这顿 18.6g 占 43%，**是正常食堂水平**。

⚠️ **入口比例本身是假设，没有食堂实测数据，误差 ±8.5g**——报告里必须标出来。

#### 🔴 元错误：**写进描述了，却没用到计算里**

最隐蔽的一类：他已经写下「茭白盘底有浅黄积油」，**但算的时候还是按 33g 全算入口**。
**照片描述里的每一个限定词（积油/带壳/带骨/没吃完）都必须在算式里落地**，
否则观察等于白做。**核算完回头对一遍：我观察到的每一件事，进账了吗？**

### 🔴 铁律 9：**餐次要标清楚，别把上一餐的账算进下一餐的建议**

实测翻车：午餐的冬瓜排骨汤，被当成「**今晚**汤别喝完」的建议给出去——
**可午餐他早就吃完了。** 这类错一旦发生，整条建议链全废。

**做法**：每条建议后面跟一句限定（「**午餐那碗**」/「**今晚这顿**」）；
出全天账时**每一行都带餐次标签**（早餐/午餐/下午/晚餐），不要混成一片。

### 🔴 铁律 10：**误差比决策空间还大时，停手别抠了**

实测：那碗汤的嘌呤误差 **91mg**（55–146），而「牛肉吃 0g 还是 60g」的
整个决策空间只有 **63mg**。**为 63mg 争论，却对 91mg 没底——精度已经超过数据本身了。**

**判据**：算出「某项的误差区间」和「你要做的选择的差距」，**前者更大就直接说**：
> 「继续抠这个克数没有意义，真正值钱的是把 X 的实测值补上。」

**能说这话是加分项**——他要的是知道**哪个数值得信、哪个不值**，
不是每一次都给一个精确到克的假答案。

## 🔴 外部食谱评估（小红书/教程视频）：**博主给的热量几乎总是偏低**

他会发一个减脂食谱链接问「**按这个做，三大营养素是什么情况？健不健康？适不适合我？**」
2026-10 实测一条「瘦子炒饭｜只有346大卡」。**这类任务有自己的坑，和核自己的餐完全不同。**

### 铁律 1：博主贴的营养卡**不含油和调料**

那次的营养卡（App 截图，视频第 2 帧）写得很完整：

```
总热量 346 kcal ｜ 蛋白 34.4g ｜ 脂肪 4.3g ｜ 碳水 44.6g
食材：菜心 168g / 牛肉(精瘦) 115g / 米饭 133g / 白蘑菇 49.7g —— 共 465.7g
```

**看着无懈可击，但它只列了 4 样食材，橄榄油和所有调料都不在卡里。**
而视频里明明在倒橄榄油、用生抽/老抽/蚝油/鸡精。

**所以必须给两套数**：

| 口径 | 说明 |
|:--|:--|
| **博主口径** | 复现他卡片上的数，用来判断「他算得对不对」 |
| **实际口径** | **加上油和调料**，这才是他照着做会吃进去的 |

实测那次的差额：「少许」橄榄油按 5–10g 就是 **+45~90 kcal、+5~10g 脂肪**，
**346 → 400–450 kcal，脂肪 4.3 → 9–14g（翻倍还多）**。

**判据**：食谱类帖子报的「只有 XXX 大卡」，**默认是漏了油和调料的**。
一个 346 kcal 的炒饭，实物做出来 400+ 才是常态。**不要直接引用博主的数字下结论。**

### 铁律 2：调料用量博主经常**根本没说** —— 那就直说没说

他会专门要求「**包括他调料加了多少**」。2026-10 那条视频里，口播和字幕全文只有：

```
「用生抽老抽黑胡椒蚝油腌制一下」   ← 四种调料，零克数
「锅里加少许的橄榄油」              ← "少许"
「少许的盐和鸡精调味」              ← "少许"
```

19 帧逐帧核对过，**没有任何数字，营养卡里也没有**。

**正确做法：明写「这不是我没找到，是博主没给」**，然后给出你的估算区间并标明是估算。
**绝不要为了让报告完整而编一个看起来合理的克数。** 他会核对，编了就是失信。

### 铁律 3：食谱里的份量要判**生重/净重/带壳**

- 肉写「115g」→ 大概率是**生重**
- 虾写「300g」→ 可能是**鲜活带壳重**（可食率 59% → 177g）
- 饭写「130g/133g」→ 要判**生米还是熟饭**（差 2.8–3 倍）

**博主的口播和卡片可能不一致**（那次口播「120克牛肉」、卡片「115克」；
口播「130克藜麦饭」、卡片「133克」）。**以卡片为准**——卡片是称过的。

### 铁律 4：评估落脚到「**作为某一餐**」和「**跟他自己昨天那顿比**」

干巴巴的三大营养素百分比没有决策价值。要给：
- 这碗饭**当晚饭量够不够**
- 跟中午那顿食堂套餐（高油高嘌呤）比，**是好还是差**
- 结合他的尿酸/血脂/糖化，**这个食谱落在他身上要不要改、改多少**

✅ 值得推荐的（那次实测）：藜麦饭替白米饭、菜心 168g+口蘑 49.7g 的蔬菜量、牛肉选精瘦部位。
⚠️ 要提醒的：**蚝油含糖**、生抽老抽带钠（他舒张压压线）、油没算进卡里。

## 🔴 包装食品/商品页：**「减油减盐」这类宣称号要逐项验，一项改善常掩盖另一项恶化**

### 🔴 他发包装背面的营养成分表时 —— **它是权威值，不许去库里找同名条目**（2026-10-25）

他把酸奶包装的营养成分表拍过来了，那就直接用它，不要去薄荷找同名条目估：

```
BASIC 系列希腊酸奶（发酵乳，100g/盒）
每 100g：能量 264 kJ ｜ 蛋白 11.0 g ｜ 脂肪 0 g ｜ 碳水 4.5 g ｜ 乳糖 0 g ｜ 钠 38 mg ｜ 钙 120 mg
→ 264 kJ ÷ 4.184 = 63.10 kcal/100g；他吃了 200g = 两盒 = 126.2 kcal
```

**四条判据：**

1. **优先读营养成分表**，不要拿成分表或其他牌子的酸奶条目去估
2. **kJ → kcal 一律写出换算系数**（÷ 4.184），不要直接套其他酸奶的热量
3. 🔴 **先看净含量** —— 这款是 **100g/盒**，不是常见的 200g 杯。他说「吃了 200 克」时要确认是两盒还是一个 200g 装
4. **「乳糖 0」不等于「无碳水」** —— 碳水 4.5g/100g 仍在（乳糖被分解成葡萄糖+半乳糖）；标「糖」时按碳水全当糖计是**偏保守**的方向，要写明

⚠️ 同类产品（全脂无糖酸奶 / 希腊酸奶 / 普通发酵乳）**蛋白密度差 3 倍以上**，认错品类会整段作废。

他会发电商商品页（酸奶/辣条/零食）问「我可以吃吗」，并常自带直觉判断。
**他的直觉往往方向对、但理由错——而理由那半才是他真正要的。**

### 铁律 1：宣称要**逐项**对照品类基准，不要整体买账

实测一款辣条号称「减油减盐」，数字是脂肪 42.5g、钠 625mg /100g：

| 宣称 | 对照常规辣条 | 判定 |
|:--|:--|:--|
| **减盐** | 625 vs 2000–2560（**低 70–76%**） | ✅ 站得住 |
| **减油** | 42.5 vs 20–30（**高 42–113%**） | ❌ **比普通辣条还油** |

> **典型的「健康光环」营销：用盐这一项的改善，掩盖油那一项的恶化。**
> 他说「感觉好像不可以」——**方向对，但真正扣分的是脂肪不是钠**。

**做完这个对照后必须明确告诉他：你该盯的是哪一项。** 他以为自己在担心钠，实际上钠是最优秀的那个指标。

### 铁律 2：蛋白质高不等于好——算**蛋白/脂肪效率比**

| | 蛋白 | 脂肪 | 蛋白/脂肪 |
|:--|--:|--:|--:|
| 辣条 100g | 20.2 | 42.5 | **0.48** |
| 瘦牛肉 100g | 20.2 | 2.3 | **8.8** |

**同样吃到 20.2g 蛋白，它带的脂肪是瘦牛肉的 18 倍。** 「高蛋白」在零食上往往是脂肪的副产品。

### 铁律 3：多产品对比用**「蛋白密度」和「每杯实际摄入」两个口径

用户发多个商品对比时，**不要比「每100g」，要比「每杯」**——因为规格不一样（70g vs 120g）。

```
蛋白密度 = 吃 10g 蛋白需要多少克产品   （越小越好）
每杯摄入 = 标注值 × 每杯克数 ÷ 100      （贴着实际行为）
```

实测三款酸奶：蛋白密度 91g（希腊过滤型）/ 200g / 294g，**差 3.2 倍**。
只看「每100g」会得出相反的结论。

### 铁律 4：益生菌宣传看**菌株号 + CFU**，不看菌种数量

| 能验证的 | 不能验证的 |
|:--|:--|
| 标了菌株号（如 **B420**）+ 标了活菌数（≥1×10⁸ CFU/100g） | 只写菌种名、写「13 种菌」 |

**菌株号是唯一能把「这袋菌」对应到具体研究的信息；CFU 是剂量，没有剂量等于没说。**
多种菌里前两种是所有酸奶都有的发酵剂，**不算卖点**。

### 铁律 5：零脂/零糖的加分，**要看它相对什么而言**

实测：零脂酸奶比 200ml 全脂奶省 7g 脂肪，占他日目标 67g 的 **10%**。

> **但他真正的脂肪大头是食堂那三道菜的 33g 炒菜油。**
> **选零脂酸奶是顺手占到的便宜，不是关键改善。别把注意力放错地方。**

**换奶制品前先算「钙」这一项**：酸奶替牛奶，钙往往从 208mg 掉到 150mg 甚至 84mg。**这笔账经常是亏的。**

### 铁律 6：数据缺失时先声明，不要拿假设当事实

实测那两款商品页：**辣条没标净含量、配料表被截断；酸奶没标品牌/规格**。

**必须做的事**：
- 明确写「净含量未知，下面按 30/50/100g 三档算」
- **说明「这不影响排序」**——B 款脂肪最高蛋白最低，怎么算都垫底
- **配料表截断时**：高油产品（脂肪 42.5%、保质期 28 天）**必然加了抗氧化剂**，
  这条不用看配料表也能推出来——**但要说清这是推论**
- **「短保 ≠ 更安全」**：28 天保质期可能只是少加防腐剂，
  也可能只是高油高盐本身就是抑菌环境。**别把短保当健康证明。**

**完整数据与逐项结论见 `references/packaged-food-label-evaluation.md`。**

## 第三方营养 App 数字核验（高频刚需）

用户用「蚂蚁阿福」这类 App 记账，**该 App 反复出现算术错误**。核验套路：

1. **交叉验算**：`蛋白×4 + 碳水×4 + 脂肪×9` 是否等于它报的总热量
   （实测遇过报 98/210/24g 却写"910 kcal"，实际 1448 kcal，差 538）
2. **反解可疑值**：用它对的那几项 + 总热量，反推可疑项应该是多少
   （同上例：910 kcal 反推出碳水只能 ~76g，而 App 自己说碳水大头=西瓜36g+米饭44g=80g → **错的是碳水那个数**）
3. **按食物清单逐项重算**，用中国食物成分表
4. **给出区间而非单点**：模糊量（"两小根""两顿"）按上下限各算一遍
5. 最后**核对它的结论句**——实测 App 把"蛋白只有目标 57%、脂肪 43%"评价成"都吃到位了"，结论比对数字错得更危险

## 输出规范（用户偏好）

- 中文；**先给结论，再给推导**，用户重视推导过程
- 用**代码块**给数字，别写成段落（**但是：多列表格在手机上会折行，见下方硬规则**）
- 每个数值都标**达成率/差额**（`实际 / 目标 = xx%`）
- 说"少了"必须同时说"补什么、补多少克"
- 调整顺序永远写明：**先补脂肪和蛋白 → 再补碳水**
- 不堆形容词，不用"很棒""加油"这类鼓励语

### 🔴🔴🔴 手机端宽度硬规则：一行一项 · 不折行（2026-10-25 原话）

> **「现在这种呈现形式，他在手机上预览他会换行，所以我看得很不清楚，我希望这个表里所有的信息都不要丢，但是弄一个更好让我读取的呈现形式，这样不然我每次都得换行读很麻烦。」**

**问题根源**：7–9 列的多列表格（项/克数/热量/蛋白/脂肪/碳水/钠/嘌呤/code）在手机窄屏上每行折成 2–3 行，列对不上，**信息没丢但完全没法读**。

**硬规则**：

1. **禁止**在聊天正文里输出 **≥5 列**的表格。
2. **默认格式：一行一项，项与数值之间用 `｜` 分隔**，指标用单字缩写 + 数字，不带空格：

```
涮牛肉110g｜167卡 21.9蛋 7.9脂 2.2碳 71钠 116嘌
牛肉卷110g｜305卡 21.0蛋 23.9脂 0碳 71钠 116嘌
```

3. **缩写固定**：`卡`=热量 `蛋`=蛋白 `脂`=脂肪 `碳`=碳水 `钠`=钠 `嘌`=嘌呤 `纤`=纤维 `钙`=钙。**表头只写一次**（放在代码块第一行或紧邻的一行说明），不要在每行重复中文长标签。
4. **小数位**：正文取 **1 位小数**，整数不补 `.0`；需要精确值（如钙、糖）时另起一行给。
5. **长度自检**：每行 **不超过约 60 个半角宽度单位**（≈30 个中文字 + 30 个数字/字母）。超了就**拆成两行**：第一行「项 + 克数」，第二行缩进给数值——**不要靠折行，主动断行**。
6. **合计行**放最后，用 `合计｜` 开头，与明细同格式。
7. **`code`（薄荷条目 ID）、数据来源、误差区间、推算依据——一律不进正文**，进 `diet/` 存档文件；他追问出处时再单独发一小块。
8. **单列项」（如挂油、锅底盐）如果已经分摊进各项，不要作为一行列在明细里**——会被误读成要额外相加。要么分摊后不单列，要么单列时**明确标「已分摊，不另加」**。

**例外**：他明确说「给我表格」「截个图看」时才用宽表。

### 🔴🔴 条目必须逐个去薄荷查，禁止拿相近条目顶替（2026-10-25 原话）

> **「这一轮你去跟薄荷库里对照一下，尤其是牛肉卷，不能用牛腩代替。」**

实测踩坑：牛肉卷 110g 用 `082116 牛腩`（332kcal/脂肪29.3）顶替，真实条目 `fd6297be 肥牛卷` 是 250kcal/脂肪18.7——**110g 就虚报 90kcal、11.7g 脂肪**。牛腩是带筋膜厚脂肪的炖煮部位，肥牛是薄切腹肉，两者不是同类。

**硬规则：**
1. 每一项都去 `public_search` + `public_detail` 查**真实条目**，存档里给出**条目名 + code + 每100g 值**。
2. 薄荷没有通用条目时（火锅菜品、加工肉、品牌品居多），**列 2–3 个候选带 code 和数值让他选，不要自己拍板**——他会自己定档（牛肉丸选潮汕手打 174、千层肚取中位数 54、叉烧选非蜜汁 166）。
3. **「取中间值」= 中位数，不是平均值**——端点常有异常（千层肚 37/49/54/56/67，中位 54，均值 61.4 偏高）。
4. 🔴 **已分摊的项不要列成独立行**：锅底挂油按吸油率分摊进各项脂肪后，若再单列一行会被读成要额外相加。要单列就标「已分摊，不另加」。
5. 薄荷免费接口**钠一律返回「—」、嘌呤永远空**——钠要逐项说明替代来源，嘌呤标清哪些是表1-2 查表、哪些是推算。
6. **units 验证过的换算要标出来**：肥牛卷（1片10g→一筷子20g）、鸭掌（1个27.5g可食）有 units 支撑，其余「一筷子/片/口」都是估。

### 🔴🔴 信息密度上限：他要的是「表 + 合计 + 一行备注」，不是分析报告（2026-10-22 原话）

**以下默认不写进正文，除非他问：**

| 默认不写 | 什么时候才写 |
|---|---|
| 三档情景表（油 / 钠的 low-mid-high） | 他问「这个数准不准」「误差多大」时 |
| 误差合成 ±X | 同上 |

一轮塞满五种表格不算「推导充分」，算「没替他筛」。

### 🔴 核算类报告必带的三件套（2026-10 健康助理实战定型）

他重视推导过程，**也极讨厌编造的精确数字**（会凭直觉质疑且常常质疑对）。
一份合格的核算报告必须自带下面三仵——它们不是"加分项"，是**边届**：

**① 数据出处表**（每个数字配来源，拿不到的宁可不给）

| 数据 | 来源 |
|---|---|
| 热量/蛋白/脂肪/碳水/胆固醇/可食率 | `foods.json`（《中国食物成分表》第6版） |
| **嘌呤** | 《成人高尿酸血症与痛风食养指南（2024年版）》**附录1 表1-2** |
| 分级线 | 同上 表1-1：高 150–1000 / 较高 75–150 / 较低 30–75 / 低 <30 mg/100g |

**② 不确定项单独列出来，明说"这个我没数据"**——比硬给一个数安全得多。
实测例：
- 「表1-2 里没有「黑虎虾」这一条，我是用同类虾区间推的，**这是我给你的数字里最不确定的一个**」
- 「凉拌汁的钠：用量未知，**这是全餐唯一无法量化的变量**」
- 「凉拌油你没给，我估 8g，**这是全餐最大误差源**」

**③ 算术自检**——把宏量营养回算一遍总热量看对不对：

```
62×4 + 46×4 + 21×9 = 620 vs 612 → 偏差 +1.3%，通过
```

**为什么这三条必顶**：他要的是**能自己判断该不该信的数字**。给了出处 + 标了不确定项，
他才能自己决定哪些数拿去用。**一个不标来源的精确数字，对他来说比一个标了来源的区间还不如。**

| `boohee.public_detail(code)` | **dict** | 顶层直接有 protein/fat/carbohydrate/fiber_dietary/**natrium**/gi；而**胆固醇、钾、钙、磷、镁、铁、锌、锰、维E 全在 `ingredient` 子字典里**——顶层读不到不等于没录 |
| `boohee.public_search(q)` | **tuple**，`r[0]` 才是 food 列表 | 直接 `for f in r` 或 `r[i]['name']` → `TypeError: list indices must be integers or slices, not str`（同一次会话踩了两次） |
| `Boohee().detail(code)` | **3 元组**（不是 dict） | 先 `r[0]`，且返回的 `calory` 是**列表**不是数字，要自己解析 |
| `boohee.two_step(...)` | **模块级函数** | `Boohee().two_step(...)` → AttributeError，`Boohee` 只有 `detail/nutrients/preview/search/quota` |

**规矩：每接一个新薄荷接口，先 `print(type(r))` 一次再写下游代码。** 比事后 debug 快，
也避免把「我读错字段」误判成「数据源没录」——后者会让你白花一次付费额度，还会写出错误结论。

#### 🔴 有「剩了多少」时：份额 = 整碟 × 吃完比例 ÷ 人数（2026-10-27 晚餐）

### 🔴🔴 一份输出里出现三套数字 = 必须打回重算（本次最大教训）

#### 挑量词时最反直觉的一条：**别挑「勺/粒/盘/瓶」**

`units` 里同一个食物有一堆量词，默认挑哪个直接决定他要不要动手改。
**规则是「挑他会说出口的那个」，不是「挑薄荷列表里的第一个」。**

| | 量词 |
|:--|:--|
| ✅ 他嘴里的话 | **个 / 只 / 颗 / 根 / 块 / 片 / 碗 / 杯** |
| ❌ 计量单位，不是他说话的方式 | **勺 / 粒 / 口 / 把 / 袋 / 瓶 / 罐 / 盘 / 碟** |

实测踩过的：米饭默认挑了「**勺** 40g」（该是「小碗 150g」）、牛奶挑了「**瓶** 1500g」、
苹果挑了「**盘**」、豆腐挑了「**块 450g**」。**这些他全都得手动改，等于默认值白给。**

⚠️ 单位名**不能**决定量级合理性（「瓶」对牛奶是 1500g、对饮料可能才 300g），
还得叠一层**重量合理性加罚**（一份通常 10–600g）。

**推广**：给用户做确认界面时，**先问「他改一个值的最小动作是什么」**。
如果答案是「把那个数改成另一个数」，那么**按钮、下拉、档位全是错的**——
要么给自由输入框，要么给**能整段复制编辑的纯文本**。

**实例**：牛奶瓶身标签是 280mL，模型读成 200（小字看不清就硬报）。

**遇到这种分歧，先问清是哪种情况再下结论**：
1. 他喝了不止一瓶（照片里只有一瓶）
2. 实际倒出来的量 ≠ 瓶标（瓶里装的是另倒的）
3. 模型把标签看错了
4. 他记的是别处的数

**前三种要改流程，第四种不用——结论不同，处理方式完全不同。**
**问清楚之前，不要在报告里用任何一个数下结论。**

## 唯一消除不掉的误差：这一碟到底多重

照片估重是**物理难题**——人类专家看照片误差 41-53%，实测同一张面汤图跑两次
一次 250g 一次 140g。对策只有两条：

1. **让他拍照时放个参照物**（筷子、勺子、一次性杯子）——最有效，每次主动提一句
2. **他手上有实物，比照片准**——觉得不对说一声就行

⚠️ 提这个时必须点明：**薄荷的 AI 相机同样是从照片估重，上限一样**，
不是我们方案独有的缺陷。否则他会误以为花钱能买掉这个误差。

## 🔴 叫健康助理干活：query-file 的写法（2026-10 实战定型）

用户说「**交给健康助理跑**」时，不是把问题原样转发，而是**写一份任务书**。

```bash
# 写任务书
write_file ~/AppData/Local/hermes/cache/query_xxx.txt
# 后台跑（分析要几分钟）
hermes -p health chat -c "Bot Chat" -Q --query-file "<绝对路径>" > out.txt 2>&1
```

🔴 **`-c` 后面必须用已存在的 chat 名。** 2026-10-26 我随手写了 `-c "燕麦评估"`，
直接报 `No session found matching '燕麦评估'`、`exit 1`、输出 166 字节就结束——
**看起来像模型挂了，其实是会话名不存在。**
→ 一律用 `-c "Bot Chat"`（既有会话，带上下文和额度状态）；真要新开会话必须加 `--create-if-missing`。

### 任务书里必须写进去的六句

| # | 写什么 | 为什么（都是实测出来的） |
|:--:|:---|:---|
| 1 | **判断维度由他指定**：「主要判断嘌呤和脂肪，蛋白缺口不作为主要依据」 | 不指定它就会夹带别的维度来论证 |
| 2 | **「不要为了维护上一轮结论而辩护，错了就认」** | ⭐ **效果最好的一句**。加上它之后，它连续几轮主动认错（实锤了「用油 33g 全算入口」「餐次搞错」「300mg 不是指南」） |
| 3 | **「不确定就说不确定，不要编」** | 它会主动标「这个我没数据」「这是推算不是查表」 |
| 4 | **「口径与上一轮一致」（并列明上一轮的假设）** | 不写它可能换口径，**两个数就不可比了** |
| 5 | **「结论先行」** | 否则先讲一堆原理 |
| 6 | **「仍然不要走薄荷」（额度/限流状态下）** | 否则它可能自作主张去调接口 |

### 🔴 最强的追问方式：直接质问「你这个数/标准是哪来的」

本次最大的一次纠错就是这么出来的——我不直接反驳它，而是让它**引原文**：

> 「**三百 mg 这个线，出处是什么？是《食养指南》里的哪一条？原文怎么写的？**
> 这条是给痛风患者的，还是给无症状高尿酸血症的？」

→ 它去 grep 了指南全文，发现**根本没有 mg/天 数字**，自认「给临床惯例披上了指南的外衣」。

**比「我觉得你太严了」有效得多。质问出处 > 争论结论。**

### 🔴 等它的姿势：**不要在前台长时间 sleep**（本会话连中断两次）

健康助理一轮要 **3–8 分钟**。本会话用 `terminal(sleep 280 / 290)` 在前台等，
**两次返回「Orphan recovery: interrupted side-effecting tool」**——等待期间会话被打断，
拿不到输出。**但后台进程本身照常跑完了，只是结果没读到。**

**两个可行姿势，按场景选：**

**① 首选：后台 + notify，人不等**
```bash
# background=true, notify=true
cd ~ && hermes -p health chat -c "Bot Chat" -Q --query-file "<path>" > "$LOCALAPPDATA/Temp/health_xxx.txt" 2>&1
# 然后先做别的事，或直接结束本轮；完成通知会自动回到会话
```

**② 必须当场等：分段轮询，每次 ≤240s，单段失败就重试读文件**
```bash
sleep 240; tail -110 "$LOCALAPPDATA/Temp/health_xxx.txt"
# 没写完就再轮一次，不要一次 sleep 300+
```

**验证经验**：`sleep 240` / `sleep 285` 成功；`sleep 280` / `sleep 290` 被中断。
**没写完不代表跑挂了**——先 `wc -c` 看文件大小，再决定是重试还是继续等。

🔴 **~126 字节 = 它还在跑，不是挂了。** 那个大小正好是输出开头的两行
（`Warning: Unknown toolsets: a2a` + `↻ Resumed session ...`），正文一个字都还没刷出来。
实测同一进程：先 126 → 再等 200s 后 4116；另一次 126 → 之后 4949。
**看到 126 就再等一轮，绝对不要重发任务**（重发＝两条并行的健康助理，可能双写）。

🔴 **不要用 `kill` 来「重启」任务书**（2026-10-26 实踩）：任务书发到一半想补需求，
我把后台进程 `kill -9` 后再发新版——第二次跑回来头部写着
`Session ... already has a live owner (cli, pid 140160, running 0m). Only one surface at a time may run a session, because a second one would`
**报文被截断在这句中间，第二部分（我要补的那个需求）直接没了**，而且 log 里看不出是失败。

**判据：一个 session 同时只能跑一个 surface。**
→ 任务书发出前把需求想全（一次会话不轻易拆两轮）；
→ 确实要补需求：**等上一轮自然结束**再发，不要 kill；
→ 已经 kill 了：先 `ps -W | grep <pid>` 确认进程真没了、再等十几秒让锁释放，才发新任务；
→ 新任务书的输出文件**先看头几行**，出现 `live owner` 就说明撞锁了，重跑而不是读那份残缺结果。

### 🔴 写任务书之前先 `cat quota.json`，不要凭记忆写「不要走薄荷」

2026-10-20 实测：当天已烧到 **49 / 50**，只剩 1 次付费。**先看额度，再决定口径**：

```bash
cat ~/health/fooddb/boohee_api/quota.json   # 例：{"2026-10-19":59,"2026-10-20":49}
```

| 剩余付费次数 | 任务书里的主路径 |
|:--|:--|
| ≥ 样数 | 照常 `two_step()` |
| **≤ 1–2 次** | **主路径改成全免费**：`anchor()` / `public_search()` 锚 code → `public_detail(code)` 拿 热量/蛋白/脂肪/碳水/纤维/钠/GI/GL；嘌呤走表1-2；糖/钙查自建成分表，查不到就明写「没数据」 |

**实测效果：一整餐（口蘑/菜心/牛肉/杂粮饭 4 样）全程 0 次付费，`quota` 49 → 49**，
报告质量没有下降——因为缺的那几项本来就该查表，不该指望薄荷。

⚠️ 反过来说清楚：**付费接口真正不可替代的只剩「糖 / 饱和脂肪 / 钙 / 嘌呤」四个字段**，
而这四个都能用「表1-2 + 成分表 + 推算并标注」替代。**额度紧张时损失比想象中小，别为此砍掉核算的完整性。**

### 🔴🔴 默认就是两段式：**先返回数字 → 他确认 → 才存档**（2026-10-26 用户当面定的默认流程）

**用户原话：**

> **「以后这个食物我发给你之后，你应该先返回给我你算出来的营养素，然后我确认之后再存档，这个工作流程以后要都记住了。」**

**这不是「他说了才做」，是默认行为。** 之前我把他报的一顿早餐算完就直接写进 `diet/` 并回复「已写入 xxx 字节」——
**他当场把流程改了。** 核算和落盘必须分开，确认权在他手上。

| 阶段 | 做什么 | 禁止 |
|:--:|:--|:--|
| ① 核算 | 出数字、给合计、标误差与出处 | **不写任何文件** |
| ② 他确认 | 他说「对」「就这样」「存档」 | — |
| ③ 存档 | 才写 `diet/YYYY-MM-DD.md`，写完回读报字节数 | 没确认前不许写 |

**判据：凡是他「报了一餐 / 发了一张标签」而没有明说「存档」的，都走 ①②，停在 ②。**
**反过来说**：他已经确认过的那一顿，后续更新不必再问一遍——只问新增的部分。

⚠️ 这条覆盖早先「他报了就直接记」的默认。**算对了但提前落盘，一样是错。**

### 🔴 包装营养成分表发多张时：以**最后一张**为准，并在任务书里写明作废前一版

2026-10-26 他先发了一张商品页截图（1661kJ / 11.9 / 8.4 / 67.5 / 纤 17），几分钟后补了一张更完整的
（**1603kJ / 13.1 / 8.8 / 54.4 / 纤 16.2 / 钠 6**），并说「以我最后发的这一版为准」。

**两张的碳水和纤维关系不一样**：前一版碳水 67.5 已含纤维（1661 kJ 用 蛋白17+脂肪37+碳水17 正好算平），
后一版碳水 54.4 **不含**纤维 16.2（13.1×17 + 8.8×37 + 54.4×17 + 16.2×8 = 1602.7 kJ ≈ 标称 1603）。
→ **同一款产品不同批次/不同版本标签，口径可能不同。不要假设「同一款就一样」。**

**做法**：① 以最后一张为准 ② 在任务书里显式写「前一版作废」并列出前一版的数值，
防止健康助理混用 ③ 用 GB28050 能量系数反算，验证碳水与纤维是否重叠。

### 🔴🔴 两段式：「只分析」和「存档」必须是两轮

用户的常见指令形态是：**「分析一下，并且在我确认之后存档。」**

这不是一句话两件事，是**他要先看数、再落盘**。任务书按两轮拆：

| 轮 | 任务书必须写 | 禁止 |
|:--:|:--|:--|
| **第 1 轮** | **「本轮只做核算与分析，不写任何文件」** + 逐条列出禁改对象（`diet/`、`reviews/`、`profile.md`、skill） | 任何落盘 |
| **第 2 轮（他已确认）** | 写清**只更新哪一个文件**、新增哪一节、**改写哪一节** | 新建 `reviews/`、改 `profile.md` |

**第 1 轮收尾必须让它自报「本轮没有写任何文件」并给出参照**（「`diet/xxx.md` 仍是 HH:MM 的版本，NNNN 字节」）——
这样你事后一眼能核出它有没有偷偷落盘。

🔴 **还有一个更隐蔽的坑（2026-10-24 踩的）：只写「以文件现存的为准」，会让已核算好的项永远进不了文件。**
那天午餐和蛋糕都只在对话里核算过，文件里只有早餐；我写了「以文件里现存的为准」，
它就老老实实只写早餐，午餐和蛋糕至今没落盘，用户还以为早存了。
→ **第 2 轮任务书必须逐个列出「这次要写进去的行和数字」（表格整块照抄），再补一句「与文件现存记录冲突时以文件为准」。**
两句都要，只写后者等于让它什么都不做。

**第 2 轮要防的坑：新餐次写进去了，旧的汇总节忘了改。** 文件里会同时存在
「截至 13:5x，仅含早餐 + 午餐」和新的全天合计，**两套账并存**。
→ 任务书里点名要它**改写汇总节**（「全天合计」要换成收盘视角、「距目标还有多少」不再叫「晚饭空间」），
不要只写一句「更新合计」。

#### 🔴 残留的不止汇总节——**文件头也常常写着一句旧口径**（2026-10-25 实锤）

实测：汇总节从「截至午餐」改成「截至加餐」之后，**文件头第 7 行还留着「汇总节是『截至午餐』口径」**。
→ 任务书里必须写：**改完跑一次 `grep -n "截至X\|只到X"` 自查，命中 0 条才算完**，并要它把 grep 结果贴回来。
→ 收尾自报里加一条「明确回答：有没有残留旧措辞」。**只靠它自觉，一定会漏。**

**新增餐次时汇总节的正确写法**：标题改成 `## 汇总（**截至加餐 · 晚饭未吃 · 今日尚未收盘**）`，
表里加一行新餐次，合计行同步改，并在表下留一行 🔴 提示「本表只到 X，不是收盘数」。

#### 🔴 他选定口径后，第 2 轮要「锁死」并写进文件（2026-10-21 原话）

我给完 A/B/M 三档后，他直接说：**「算法别变了 就按刚刚那个存档吧」**。

→ 生成了三档对比后他选一档，就是**永久锁定**，不是「多给几种参考」。第 2 轮任务书必须：
1. **开头写「口径已锁死，不许再换、不许重算」**，并把具体算式写进去（例：薄荷猪小排 295 + 吸油 12.5%）
2. **数字直接照拄入账**，并明确「不要重新讨论三档」
3. 在文件里注明「**已锁定、不再变更**」，以后同一天的后续更新不再翻案
4. **本轮 0 次付费接口调用**（数字都有了，再调就是浪费额度）

→ 反过来说：**不要在存档后再提升口不一致的警觉**——他会觉得你在翻烧饼。
可以继续提升口的只有一种情况：**他说新信息、自己要求重算**。

### 🔴 验证动作写进任务书让它自报，你只做二次核对

```
1. ls -la 报出字节数和 mtime（改前/改后）
2. 把新增小节的标题、以及汇总表的实际内容 grep 出来贴回来
```

实测这一轮它回的是：`10,832 → 15,946 字节`、三个小节的真实行号（152 / 154 / 209）、汇总表原文。

### ⚠️ notify 回来的「Background process completed」是同一次运行，不要重发结论

`terminal(background=true, notify=true)` 跑完，会话里会**再插一条**完成通知——**这时结果早就读过、也已经汇报过了**。

**正确处理：核一下文件有没有变（`wc -c` + mtime + `quota.json`），然后一行确认。**
不要把整份分析再讲一遍。实测两次通知，输出文件字节数完全没变（7308 / 8146），
`diet` 文件 mtime 也没变 → **一句「内容没变，等你确认」就够了。**

## 🔴 记忆分层：哪些健康内容该进系统记忆，哪些只能进健康助理自己的 profile

2026-10 用户主动问过一个很好的问题：

> **「这些记忆，它不能只是健康助理的记忆吗？就是跟我健康状况有关的，还是说它必须要放在总的这个记忆里边呀。」**

### 判据只有一条：**谁会用到，不是「这条属于哪个领域」**

| 类 | 放哪 | 例 |
|:--|:--|:--|
| **A 路由与边界** | 🔴 **必须进系统记忆** | 「健康助理」四个字 → 调 `hermes -p health`、数据在 `~/health/`、主 Hermes 不自己做健康判断 |
| **B 领域专业知识** | **只进健康 profile 的 skill** | 薄荷 API 的 429/`success:false` 坑、嘌呤阈值口径、可食部折算 |
| **C 关于「这个人」的认知** | 🔴 **必须进系统记忆** | 「他对营养/价格估算会凭直觉质疑且常正确」「拒绝持续手工记录方案」「没说≠没发生」 |

### ⚠️ 最容易搞错的是 C 类

**C 类看起来像健康内容，其实不是——它是思维方式，跨领域有效。**
「他会质疑我的数字且常常是对的」这条，**主 Hermes 给你报价、评方案、算成本时同样要用**。
放进健康 profile 就是放错了地方。

### B 类是纯浪费：系统记忆被专业知识挤爆

审计时发现系统记忆里有一条 **211 字的「薄荷 API 全套坑」**，而健康 profile 的 `meal-photo-analysis` 
里有**一模一样的一份**。**主 Hermes 永远不做嘌呤核算，记这些没有意义。**

**盘查口诀**：每条 >150 字的领域条目，问一句「**主 Hermes 会在什么场景用到它？**」
答不上来 → 移进对应 skill，系统记忆只留一行指针。

### 🔴 发现的结构缺口：触发词不在任何地方

那次审计还查到：**系统记忆里没有「健康助理」这个触发词**（只在一条偏好里顺带提了一句），
而本 skill 早先的 description 也只写了「发餐食照片要核算、分析饮食营养……」——
**意味着用户直接说「让健康助理看看」时，路由靠的是语义猜测，不是明确规则。**

→ 已把「健康助理」写进 description（本 skill 顶部）。
**推广**：凡是有独立 profile 的领域，**触发词必须同时出现在「系统记忆」和「该领域 skill 的 description」两处**——
只写一处，新话题下就会漏。
