# 健康域派活：任务书 / 两段式 / 双轨复核 / 异常登记

> 2026-11-17 实录。一次会话内连派 6 轮给 health profile，从「小红书菜谱还原晚餐」
> → 核算 → 汇总稿 → 选品研究 → 纤维质疑 → 数据修正 → 写入档案，全程走这套姿势。

---

## 一、派活命令（本次实际跑通，比老写法更省事）

```bash
# 1) 任务书写到 cache，不用 _task_*.md 临时文件
#    C:/Users/<user>/AppData/Local/hermes/cache/query_<主题>_<日期>.txt

# 2) 后台跑 + notify，输出全量落盘到 Temp（不要接 tail）
hermes -p health chat -c "Bot Chat" -m deepseek-v4.1-flash -Q \
  --query-file "C:/Users/<user>/AppData/Local/hermes/cache/query_xxx.txt" \
  > "$LOCALAPPDATA/Temp/health_xxx.txt" 2>&1     # terminal(background=true, notify=true)

# 3) 完成通知到达后 read_file 那个 Temp 文件，再自己复核
```

- `-m deepseek-v4.1-flash` 显式给模型，别依赖 profile 默认值漂移。
- 输出**重定向到文件**，不许 `| tail -N`（老坑：which 会截掉回执前半段）。
- 一次调用实测 30–180 s；`background=true` + `notify=true` 一次搞定，不用手工轮询。
- 会话是**保留**的（`-c "Bot Chat"` 续同一条），所以能说「上一轮你算过的那份」。

## 二、任务书必备八项（缺一项它就自由发挥）

1. **日期 + 当日档案绝对路径 + 已有小节清单 + 当前字节数/mtime**
2. **用户原话逐字引用**（不改写、不概括）——它常从原话里挖出你没注意的口径
3. **口径档位**：生/熟、可食部、哪条库条目、用哪个包装标签、借档怎么标示
4. **禁止项清单**（见下）
5. **交付格式**（逐项一行 + 合计 + 来源标签 + 数据完整性 + 换算过程）
6. **验算要求**（让它自己跑一遍算术自检并贴出残差）
7. **本轮是「只核算」还是「写入」**——必须明写
8. **边界自查要求**：收尾自报「本轮没有写任何文件」并回读字节数/mtime 作证

### 禁止项固定四条（每轮都抄一遍，不省）

```
- 只核算不落盘（或：本轮授权写入 XXX，其余一律不许动）
- 不写劝诫 / 不评价饮食好坏 / 不给改进建议（他没问就别给）
- 「打算吃」不算已吃，只做推演并单独标注
- 库内没有的就写没有，不许用均值或估算硬填
```

## 三、两段式：核算稿 → 他说「写」→ 写入轮

他的分界（沿用 2026-11-05 定的规则）：

| 他说的话 | 你该做的 |
|:--|:--|
| 报了一餐，没说「记」 | 出核算稿、**不落盘**，结尾明写「待确认」 |
| 「你肯定要把它写进档案呀」/「记一下」 | 进写入轮 |

**写入轮的三件套**（少一件就是假记完）：

1. **新增小节**（格式与既有餐次节完全一致，含来源列）
2. 🔴 **重出「今日汇总」小节**，时间戳改成实际写入时间——他明确要求「记完即重出当日汇总」。
   只加小节不重出汇总 = 没记完。
3. **回读验证** + 边界自查（profile.md / reviews/ / skill 的字节数与 mtime 作证未动）

> 校验器 `verify_diet_tables.py` 会逐表重算并打印 ALL PASS / FAIL。
> **FAIL 不等于档案错**——先看是不是校验器自己的缺陷（见第七节）。

## 四、主 Hermes 的独立复核（不许只听它自报）

它说「写入完成」只是自报，必须自己验：

```bash
# 1) 派活前先存基线
stat -c '%s %y' health/diet/YYYY-MM-DD.md health/profile.md > /tmp/before.txt

# 2) 派活后比对
stat -c '%n %s %y' health/diet/YYYY-MM-DD.md health/profile.md

# 3) 小节结构
grep -n '^## ' health/diet/YYYY-MM-DD.md

# 4) 合计行
sed -n '<晚餐合计行号>p;<汇总合计行号>p' health/diet/YYYY-MM-DD.md

# 5) 验算器
python tools/verify_diet_tables.py diet/YYYY-MM-DD.md
```

**必须核的三件事**：① diet 文件字节数/mtime 确实变了；② profile.md、reviews/ **没变**；
③ 各餐小计相加 == 汇总合计（拿它给的行号自己再 grep 一次）。

## 五、🔴 库内数值可疑 ≠ 录入错误（本次最重要的一条）

2026-11-17 连环翻车实录：

1. 健康助理算 VE 时发现「素鸡 17.8 mg/100 g、香干 15.85 mg/100 g」离谱，判为「库内录入错误」。
2. 我跟着复述了一遍「豆制品不可能有这个量级」。
3. 下一轮交叉校验：**这两个值与《中国食物成分表》完全一致**（素鸡 17.8、豆腐干(酱油干) α-TE 16.41）。
   → 可疑的是**成分表本身这一项**，不是录入。它推翻了自己，也推翻了我。

### 正确处置（三步，顺序不能反）

```
① 判异常：拿「该条自身的其他字段」做自洽校验
   例：VE/脂肪 > 1.0 mg α-TE/g 脂肪 → 高于任何食用油脂，判可疑
② 交叉校验：查《中国食物成分表》/NLC / 同源条目
③ 分岔：
   有出处 → **不许改数**，登记为 excluded，排除出计算但保留原值
   无出处 → 标「缺录(null)」，**不许用均值或估算补**
```

铁律：**宁可判「无法判定」，不许静默记 0，不许改数据源原值，修一条登一条。**

### 为什么是「覆盖层 + 登记表」而不是硬改缓存

`boohee.public_detail()` **每次实时拉 API**，本地没有可写的权威库
（`cache.json` 只缓存付费接口结果）。硬改缓存会被下次拉取覆盖 = 假修。

```
health/fooddb/anomaly_registry.json   登记表：code / field / original / status / reason
health/tools/anomaly_fix.py           覆盖层：status='excluded' 的字段置 None
health/tools/boohee.py  ~第 216 行     在 public_detail 返回前调用 anomaly_fix.apply()
health/tools/DATA_ANOMALY_RULES.md    规则文档（阈值表 / 五步顺序 / 四条铁律 / 变更记录）
```

新增异常**只改 json，不改代码**。改 boohee.py 前先备份（`boohee.py.bak_<时间戳>_pre_anomaly`）。

已登记的类型：豆制品 VE 异常、浆果/燕麦 `fiber=0.0`（蔬菜纤维不可能为 0）、
奶类 `kalium` 空、商品条整行全 0、`燕麦片 fat=0.2`（应为约 7）标 suspect。

## 六、派活时的三个污染源（都实际踩过）

| 污染 | 后果 | 正确做法 |
|:--|:--|:--|
| 把自己的识图结果当数据源写进任务书 | 口径被污染 | 只传**图片路径**，让健康助理自己跑 `recognize.py` |
| 把自己的推断写成「事实」 | 它照着错前提算 | 判断另起一行标「（主 Hermes 判断，仅作定位提示，不作为数据源）」 |
| 把自己看错的地方当「矛盾」写进去 | 它被迫解释一个不存在的问题 | 拿不准就不写；原话以外的东西一律不写 |

**本次实例**：任务书里我把用户说的「吃了一整个西红柿」标成与档案矛盾，
实际「2 个 ×÷2 = 1 个 ≈ 165 g」完全一致。健康助理反过来纠正了我。
→ **任务书里只放原话和事实，判断留给它。**

## 七、`verify_diet_tables.py` 的餐次正则（2026-11-17 已修）

**症状**：带晚餐的档案一律报 `累计块不一致 ✗` + `总计 FAIL`，
而各表逐张重算都 ✓。原因：正则与 meals 列表都没有「晚餐」：

```python
# 第 103 行
re.match(r'^(早餐|午餐|加餐|夜宵|累计)\s+(.*)$', ...)      # ← 缺晚餐
# 第 110 行
meals = [k for k in ('早餐', '午餐', '加餐', '夜宵') if k in rows]  # ← 缺晚餐
```

→ 它把晚餐那行当空气，各餐和少算，跟累计一比就 FAIL。
**已修**（两处都补 `晚餐`），备份 `verify_diet_tables.py.bak_20261117_pre_dinner`。

> 教训：**看到 FAIL 先分辨是档案错还是校验器错**，别急着改档案。
> 判据——「每张表逐项重算都 ✓，只有跨表相加 ✗」→ 九成是校验器缺餐次/缺列。

## 八、研究型问题（「哪个更好」「为什么」）的派活格式

他问选品/优先级时（蓝莓 vs 黑莓、纤维 vs 蔬菜），任务书要额外写：

1. **必须给明确的二选一，禁止「两个都重要」**——写进禁止项，它会照做。
2. **每条判断落到他本人的化验单数值上**（尿酸 454 / TG 3.27 / 糖化 6.3% / 空腹 5.0 / 脂肪肝），
   不许讲通用科普。
3. **要求分三档标证据强度**：有明确证据 / 有机制但证据一般 / 证据不足。
   他尿酸那条最后被判「证据不足，不构成理由」——这种诚实的否定比强行凑理由有价值。
4. **库内没有的字段（维生素 K、叶酸、β-葡聚糖、花青素）要求明写「无可用数据，不纳入判断」**，
   不许拿营销话术顶上。
5. **给两档份量**（50 g / 100 g）让他自己挑，别替他定。
6. 结论后面保留「除非你更在意 Y，那就选 Z」的让步句——他要的是决策依据，不是单一答案。
