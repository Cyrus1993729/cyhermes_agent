# 守护进程失联取证（死了 vs 卡住）

用户说「从 X 点到 Y 点你完全没反应」时，**先取证，别先猜**。
「进程死了没人拉」和「进程活着但事件循环卡住」是两种完全不同的故障，
修法相反：前者要补看护，后者要查阻塞源。猜错就会对着错的假设改一晚上。

触发：
- 用户报 agent/bot/服务在一段时间内无响应，或让你查「为什么没反应」
- 日志里出现 watchdog / 看门狗判死 / 非零退出码
- 需要决定「要不要加自动重启」这类看护设计

不触发：一次工具调用慢、单个 API 超时、用户单纯催进度。

---

## 一、🔴 先统一时区，否则时间线永远对不上

同一台机器上不同日志的时区经常不一样：

| 日志 | 常见时区 |
|---|---|
| 应用主日志（agent.log / gateway.log / errors.log） | 本地时间 |
| 退出诊断日志（gateway-exit-diag.log） | **UTC** |
| 桌面/打包层日志（desktop.log） | **UTC**，行首带 `Z` |

把 `...T10:33Z` 当成 10:33 本地，就会把同一件事算成差 8 小时的两件事。
**开工第一步：拿一条已知事件（比如重启时刻）在两种日志里各对一次，确认换算关系。**

---

## 二、取证四步（按顺序，每步都能独立下结论）

```
① 哪些日志还在写？       ls -lt <logs>/ | head        ← mtime 就是「谁还活着」的旁证
② 按时间窗过滤主日志      找最后一条正常日志 = 卡死起点（早于看门狗判死时刻）
③ grep 看门狗/退出码      watchdog / exit code / SIGKILL / OOM
④ 判断：进程到底退出了没有（见第三节，别只看那行 CRITICAL）
```

### 常见判死机制长什么样

```
CRITICAL <watchdog>: event loop missed N consecutive liveness probes;
  dumping all thread stacks and exiting with code 75
  so the service supervisor can restart it.
```

典型参数：探针间隔 30s + 单次超时 10s + 连续 3 次 → **循环必须连续约 2 分钟不响应**才触发。
所以「最后一条正常日志」到「判死时刻」之间那段空窗，才是真正的卡死时长；
**不要把「判死时刻 → 恢复时刻」整段都算成看门狗的责任。**

---

## 三、🔴 关键判断：日志说「我要退出」≠ 「真的退了」

判死分支的典型顺序是：

```
log CRITICAL → faulthandler.dump_traceback() → 写哨兵/ledger → os._exit(code)
```

`CRITICAL` 打在最前面。后面**任何一步卡住**（尤其 dump 写到一个被阻塞的 stderr/
无人读取的管道，或 Windows 控制台被选中文本卡住写操作），进程就会「循环已死、
但进程挂着」。这两种形态的用户体感一样，修法完全不同。

### 三个反证手段（按可靠性排序）

**① 生命周期哨兵反证（最硬）**

很多守护进程会在 `<state>/…lifecycle.json` 之类的地方留一个哨兵：
启动时读、退出时写。判据：

- 启动时**只要**看到 `phase == "running"`（上一个生命没走完退出路径）→ **必然**留下
  「上次异常退出」的记录（exit-diag 里一条 + 主日志一条 WARNING）
- 若本次启动**没有**这条记录 → 说明上一个生命执行过「正常退出标记」
  → 紧接着的硬退出（`os._exit`）必然执行 → **进程确实是死的**

反过来：如果进程是「活着但卡死」、后来被重启/关机带走，哨兵会停在 `running`，
**下次开机一定会留下那条异常退出记录**。所以「没有记录」本身就是证据。

残余不确定项记得排查：哨兵文件是否被外部删除/重置（看 mtime、看心跳文件是否还在刷新）。

**② 读源码确认最终退出调用**

`sys.exit()` 在**非主线程**里只结束那条线程（Python 官方明确说明）；
`os._exit()` 才是硬退整个进程。看门狗跑在独立线程里，两者行为天差地别——
**必须打开源码看最后一行到底是什么。**

**③ 抓外部证据**

- Windows：Security 4689（进程终止审计）**默认不开**，开了也补不回历史；Application 日志
  找应用崩溃/Error Reporting 记录
- 进程外的转储工具（procdump 之类）在杀进程前抓全量 dump，比进程内自抓更可靠
  （注意：按「窗口无响应」判定的工具，检测不到 asyncio 事件循环卡死）

## 四、🔴 证据陷阱清单

| 陷阱 | 真相 |
|---|---|
| 「心跳表里那行还活到 X 点」 | 先确认**那张表登记的是哪个进程**。Hermes 的 `gateway_heartbeats` 登记的是桌面/serve 后端，**不登记 `gateway run` 进程**，pid 对不上就别拿它证明 gateway 死活 |
| 「桌面/父进程日志里没有退出记录」 | 可能只是它不写这类日志，不等于没有监督逻辑；但「事故期间确实没人拉起」这个结果判断本身成立 |
| 「MCP 子进程杀不掉 = 僵尸进程」 | Windows 上先查权限/进程身份识别/终止等待逻辑，别直接套 Unix 的僵尸概念 |
| 「请求慢 133 秒 = 事件循环卡死」 | 正常异步等待不会堵循环；真正可疑的是**异步函数里调了同步接口**、等锁、`Future.result()`、`thread.join()`、子进程等待、日志/控制台写阻塞 |
| 「后台 review/子任务跑在独立线程就不会堵主循环」 | 独立线程本身不堵，但它和主循环之间可能有「桥」：共享锁、共享会话、同步等待、共享日志输出。要找桥，别只盯它内部 |
| 「时间上紧挨着 = 因果」 | 时间接近只提供调查方向，不是定罪证据 |

## 五、修看护：那些不写清楚就等于没修的细节

```
A 计划任务/服务 → 常驻 supervisor → 真实工作进程
  · supervisor 必须持有【真实工作进程的句柄】，拿它自己的退出码
    —— 只启动一个 launcher 再返回，钩子里看到的只是 launcher 的退出码，等于瞎的
  · 防双开要靠进程内单实例保护，不能只靠调度器的 MultipleInstances=IgnoreNew
  · 取消调度器默认的「执行时限」（Windows 计划任务默认 72 小时会被掐）
  · 抗重启抖动：退避 5/15/60s，连续失败转低频 + 告警
  · 区分「人为停止 / 升级 / 正常闲置退出 / 异常退出」，不是所有退出都该立刻重启
  · 直接用目标平台的解释器起进程，少套一层 shell（shell 会吞掉真实退出码与进程身份）

B 让判死时留下堆栈
  · dump 调用处显式传文件句柄：dump_traceback(file=<常开句柄>, all_threads=True)
  · 只调「全局 enable(file=...)」管不到显式 dump 调用
  · dump 前先写一行上下文：时间 / PID / 探测失败次数 / 主循环线程 ID
  · stderr 追加到文件只能当补充出口；重定向到 PIPE 又没人读，会制造新的阻塞

C 分级响应（比「立刻关掉看门狗」好）
  · 第 1 次失败：抓堆栈
  · 第 2 次：再抓一份 + 独立告警（告警不能依赖已经卡住的循环）
  · 第 3 次：最后取证后退出的，交给 supervisor
  · 多份间隔几秒的堆栈，能区分「同一把锁一直没拿到」和「程序还在缓慢推进」
```

### 🔴 不要做的事

- **不要长期关掉看门狗**：等于拆了安全阀，循环真卡住时变成「进程活着但永远不响应」的静默假死，更糟
- **不要重启前删锁文件**（lock / pid / 单实例文件）：旧进程没死就会双开抢资源
- **不要按进程名批量杀**（`python.exe` 之类）：会把你自己的诊断进程一起带走
- **不要把「正常闲置退出」当故障**（很多网关有 scale-to-zero / idle 退出）——
  supervisor 必须认识这类正常退出，否则会变成「睡 X 分钟被叫醒一次」的抖动
- **不要没有取证就上自动重启**：那是把「卡死」变成「每 X 分钟重启一次」的节奏性故障，
  比原来更难查。重启必须带：退出码记录、启动标识、退避、告警、连续失败显式报「仍在故障中」

## 六、报告给用户：按证据强度分栏，别把嫌疑当结论

| 判断 | 证据强度 |
|---|---|
| 看门狗记录了连续多次探测失败 | 已证实（日志原文） |
| 进程随后真的退出了 | 已证实 / 高度可疑（写清用的哪个反证） |
| 此后一直没恢复 | 已证实（无监督进程 + 日志空窗） |
| 循环为什么卡住 | **未确证**（只到嫌疑清单） |

最后一行必须写「未确证」，并说明**缺的是哪份证据**（一般是线程堆栈）。
写成「大概是因为 MCP 超时」然后据此改，下一次就会照着错的假设改。

---

## 七、让外部模型审方案时（这一步有坑）

把完整证据链（时间线原文、机制常量、已查证的环境事实）喂给外部模型做红队审查是值得的，
本次实扫它提了五条我没想到的（Windows 控制台选中文本阻塞写、supervisor 必须持有真实子进程句柄、
分级响应、锁/管道清理风险、procdump 外部取证）。

**但它会拿「不一定」来打你「已经证实」的结论**（本次：它说「未必真的以 75 退出了」）。
处理姿势：

1. **先回本机反证，再决定采不采纳**——本次用生命周期哨兵反证它错了（源码是 `os._exit` 不是 `sys.exit`，
   ），不能把它的质疑直接转述给用户当成「我的结论不够硬」
2. **它也可能抓住你真用错的证据**——本次它指出我把后端心跳表当成了工作进程的心跳，
   这条它是对的，**要当场认账并告诉用户「这条记我的账」**
3. 交付分三块：它说对的 / 它说错的（附我的核实结果）/ 它对用户的实际结论
