# 日报生成/投递分离架构（方案 C+D）— 2026-08-13 落地

> 背景：跨境日报 cron 连续两天"验证总结顶包日报正文"（8/12 response_len=529、8/13 response_len=573），用户拍板采纳 Opus 评审的方案 C+D。本文件记录完整方案、Opus 评审要点、落地实现与验证。

## 一、问题本质（为什么 prompt 措辞修不好）

连续两天事故的共同模式：
1. agent 在任务中间轮输出日报正文（当作步骤完成标志——"输出即完成"心智）
2. 流程末尾的验证步骤让 agent 产生"汇报验证结果"冲动（8/13 的验证脚本是 agent **自创**的，prompt 根本没要求）
3. agent 最终回复=验证总结，cron 只投递 final response → 正文被顶掉

**为什么第一版铁律措辞无效**：prompt 明确写了"最终回复必须 ONLY 是日报全文、禁止输出验证总结"，agent 仍违反（原话"日报正文已在上一轮完整输出"）。这是训练先验（completion 倾向+汇报倾向）对抗措辞约束——**不要用 prompt 对抗模型本能，胜率不稳定**。

## 二、Opus 评审结论（四方案对比）

| 方案 | 内容 | 代价 |
|:--|:--|:--|
| A（最优） | 交付变成 tool 副作用：`push_report(file)` 脚本自己读文件推 TG（带幂等键），agent 最终回复随便 | 需改 Hermes 工具/框架 |
| B | 投递层 post-hook 取草稿文件而非最终回复 | 框架侧改动 |
| **C（不改代码最佳解）** | **拆两个 cron**：Job A 生成写文件不投递；Job B 只有一句"read_file 原样输出"——Job B 无流程上下文/无验证记忆/无"我已输出过"信念 | 纯配置 |
| **D（必做补丁）** | 验证记账前移、流程不以校验结尾、中间步骤禁输出正文（以 tool call 收尾）、投递守卫 | 最小改动 |

**Opus 对"read_file 钉死"版（第二版 prompt）的警示**（未验证就被 C 取代）：
- 同一 bug 下沉一层：模型可能回"文件内容已读取如上"（tool result ≠ text response，但模型常不区分）
- max_tokens 截断：15-17KB ≈ 5-8k output tokens，可能收半截日报（比验证总结更糟，看起来正常）
- read_file 格式污染（行号/分页复述）
- 陈旧文件静默通过（写盘失败→读昨天文件）
- **兜底分支有毒**："文件不存在或为空→今日无新动态"让写盘失败伪装成正常无新闻日——必须改显式报错

**用户拍板**：不采用 A/B（改代码/框架），采纳 C+D。

## 三、落地实现

### Job A（生成任务 f4506e87cc69，17:00，deliver=local）
- 第 4.5 步：审查修复后**覆盖写入** `output/_draft_cb.txt`（投递任务唯一内容来源）
- 第 6 步：最终回复=一行完成确认（deliver=local 不投递）
- 🔴 铁律：① 全程禁止中间 text response 输出日报正文（只写文件，中间步骤以 tool call 收尾）② 禁止自创验证脚本 ③ 无新闻日写草稿"📦 今日跨境无新动态…"照常存档 ④ 生成失败**不更新** _draft_cb.txt（投递任务靠 mtime 检测告警）
- 清理了与"不投递"矛盾的旧指令（第 4 步"最终回复必须输出完整日报全文"、qwen 引擎路径 c 里的同款话术）

### Job B（投递任务 e8e436bbf9b1，no_agent，`15,45 17 * * *`，deliver=origin）
- script: `deliver_cb.py`（**相对路径**——cronjob create 的 script 参数必须相对 `~/AppData/Local/hermes/scripts/`，绝对路径报 "Script path must be relative to ~/.hermes/scripts/"）
- 17:15 首投；17:45 重试（Job A 慢时补投——DeepSeek 过载日 Job A 实测 23 分钟完成）

### deliver_cb.py 逻辑（~80 行）
```
is_today(path): mtime 日期 == 今天
mark_mtime(): 读 _cb_delivered.txt（记录上次投递时的草稿 mtime）

main():
  1) 草稿 is_today 且 mtime != 标记 → deliver(草稿)   # 未投递过本次内容
  2) 草稿缺失/过期 → 存档 is_today 且 mtime != 标记 → deliver(存档)  # 兜底
  3) 全缺 → 当前 ≥17:40 → 输出"⚠️ 跨境日报生成失败：草稿与存档均缺失或过期"；否则静默

deliver(path):
  守卫: ≥5000 字符且以 ⚡ 开头（正常日报）| <2000 字符含"无新动态"（无新闻日）→ 通过
       否则输出"⚠️ 日报内容异常（长度/header 不符），未投递"
  通过 → 写标记（记录本次 mtime）→ stdout 写全文
```

## 四、验证（8/8 分支 ad-hoc PASS）

场景：首次投递输出全文+写标记 / 幂等静默 / 存档兜底投递 / mtime 变化重投 / 异常内容守卫告警 / 无新闻日投递 / 缺文件不抛异常。

**验证姿势（比 Temp 脚本更干净）**：execute_code 里 `importlib.util.spec_from_file_location` 加载模块 → monkeypatch `dc.DRAFT/MARK/ARCHIVE` 到临时目录 → `contextlib.redirect_stdout` 捕获 main() 输出断言。**避免 hermes-verify-*.py Temp 脚本的自激循环**（创建/删除计入 changed paths 触发重新验证）。

## 五、设计原则（可迁移到其他长文档 cron）

1. **控制面与数据面分离**：对话流=决策调度，文件=交付物；长文档不穿过 LLM 生成通道两次
2. **交付是动作不是话**（Do, don't say）：投递由脚本执行并返回结果，不靠模型在正确时刻说正确的话——任何"最终回复必须是 X"都是脆弱契约
3. **顺应模型本能**：让最终回复是它爱写的简短回执（"已推送 20 条，存档 2026-08-13"），长文交给机制
4. **验证不产生文本，只产生退出码**：校验失败=非零退出+stderr；禁止 agent 自建验证（它写验证脚本本身就是"缺少合法收尾动作"的症状）
5. **幂等 + 大声失败**：投递带去重键（mtime 标记）；缺文件/陈旧一律显式告警，绝不降级成看似正常的空结果
6. **知道字节预算**：交付物接近 max_tokens 时经模型转发必出截断事故——这类内容设计上就不该走生成通道
