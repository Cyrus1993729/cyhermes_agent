## 脚本

### api_probe.py
- 用途：日报 cron 第 0 步 + 第 1.6 步 DeepSeek 体检（2026-08-14 起两处调用）
- 行为：真实 chat completion（model=deepseek-v4-flash, max_tokens=5, 25s 超时），阈值 30s
- 输出：`OK <秒>` / `SLOW <秒> http=N` / `ERROR <异常类型>`
- key 读自 `Desktop\各类api key\deepseek api key.txt`

### report_gen_qwen.py
- 用途：DeepSeek 过载时用 qwen3.7-max 生成完整日报
- 用法：`python report_gen_qwen.py --candidates <json> --mode five|cb --out <file>`
- 规则内嵌 FIVE_RULES / CB_RULES 常量（与 cron prompt 第 2/3 步一致：投资视角/小白教学结构、硬性规则、禁止词、背景行限制、篇幅）
- qwen key/base_url 从 config.yaml `providers.qwen-bailian` 正则提取（复用 qwen_review.py 模式）
- 候选注入：每条约 400 字符摘要截断；输出写入 UTF-8（含 CRLF，read_file 可能误判 binary，用 python 读）
- 实测：59 条候选生成 2149 字符 / 133s，质量达标（投资视角、数据点、格式正确）

## 二次探测（2026-08-14 落地，解决"单次采样抓不住波动过载"）

背景：8/12、8/14 实测过载形态是**全天波动**而非固定高峰——api_probe 启动时探测 1.66s 返回 OK，但取候选后每次 API 调用 50-217s（8/14 五类日报 19 分钟才到 API call #5，日报迟到 ~40 分钟）。单次采样只能抓住"稳定持续过载"，对"探测瞬间快、随后慢"无效。

**方案（用户拍板，两个日报 cron prompt 均更新）**：新增**第 1.6 步二次探测**——
- 取候选（第 1 步，耗时 1-2 分钟）后**再次运行 api_probe.py**
- 判定逻辑：「**第 0 步与二次探测任一 SLOW/ERROR → 切 qwen 引擎**；两次都 OK → deepseek 正常生成」
- 原理：取候选的 1-2 分钟天然形成间隔，二次探测落在过载发生后的时段（8/14 过载 11:13 起，取候选结束约 11:12-11:15，能抓到）

**落地姿势**：cronjob update 传完整新 prompt（旧 prompt 从 jobs.json 读，用 `prompt.replace(旧段落, 新段落)` 生成新文件，断言 `count==1` 且 qwen 分支 a) 行保留，读回后 cronjob update；落盘验证 jobs.json 含"第 1.6 步"）。注意 prompt 里的 `\n` 字面量（如新闻清单格式行）在 JSON 参数里要写 `\\n`。

**仍非保险**：波动发生在两次探测之间仍可能漏（概率已大降）；日报迟到 20-40 分钟属可接受波动，投递检查 11:45/17:45 已覆盖完成窗口。

## 验证（ad-hoc 12/12 断言）

- report_gen_qwen：语法 / 真实生成退出码 0 / 输出含 OK / 文件非空 / UTF-8 可解码 / 含"今日速览" / 含"新闻清单" / 空候选报 ERROR+exit 1

## cron prompt 集成设计（已生成待更新）
- 第 0 步：跑 api_probe，记住判定（OK/SLOW/ERROR）
- 第 1 步照常取候选（candidates JSON 落盘）
- 第 1.6 步：再跑 api_probe 二次探测（2026-08-14 已上线）
- 引擎选择步：两次都 OK → 正常编辑；任一 SLOW/ERROR → 跑 report_gen_qwen → 核对草稿（非空/含速览/含清单）→ 成功则跳过人工编辑从第 4.5 步审查继续（pushed 更新用 Python 按标题匹配候选 url，匹配不到跳过并记录）→ 末尾加"⚠️ 今日 DeepSeek 过载，日报由 qwen3.7-max 生成"；失败则退回当前模型（慢总比没有强）
- 审查（GPT/Codex）独立于 DeepSeek 与 qwen，故障域隔离不受影响
