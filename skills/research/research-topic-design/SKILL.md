# 课题 / 命题设计

把"我想研究 X"收敛成"一个有两难、答得出、能落地的具体问题"。
用户常带着一个主题（如"大会员体系"）+ 一份汇报框架来，要求你帮他想命题。

## 核心判据（缺一不可）

1. **必须有对立面（两难）**——存在"不这么做也有道理"的另一条路，才需要研究去裁决。没有对立面的问题是同义反复，写出来必然是模板。
   - 反例："建大会员体系→提升跨业态交叉消费"。交叉消费本就是体系的设计目的，是定义不是结论。
   - 正例："同样的让利，直接降价 vs 积分抵扣，哪个更能促进成交"——两种做法都有真实支持者。
2. **匹配团队知识资产**，不是知识愿望。命题所需输入必须落在成员现有经验 + 公开资料 + 内部数据之内。
   - 先盘清成员构成，据此判断能做什么、不能做什么。
   - 需要"搭建过才知道"的黑箱（系统架构、中台选型、底座设计）或需外部人脉访谈的命题 → 直接放弃，改到"机制设计 / 算账 / 客户研究"层。
3. **产出有形**：方案机制 + 测算表 > 认知报告 > 活动策划。太窄（像活动策划）和太宽（像行业综述）都不合格。
4. **领导 / 评委视角**：结论要能直接变成下一步工作（省钱、卖房、招商），否则"推动落地"模块一定是空的。

## 工作流

1. 先问清约束：交付物形态、汇报框架与时长、死线、小组人员构成、可用资料。缺一项就先把命题悬着。
2. 给 2–3 个候选命题，**每个都标注弱点**（自曝短板，不吹）。
3. 用户否掉时，先承认缺陷、讲清"这个命题为什么立不住"（同义反复？能力不匹配？无痛点？），再重构。不要换词辩护。
4. 收敛后把命题嵌回他的汇报框架（逐模块映射），不要另起一套结构。
5. 命题表述可抬半层防止被听成跑题（例：把"积分玩法"抬成"大会员体系的本质是让利形式的重构"）。

## 用户偏好（重要）

- 用户会质疑你的提案，且常常正确。他要求"站在客观角度、不要讨好式回答"时，必须真的承认缺陷并重构。
- "探讨 / 讨论" = 只输出观点、不动手写文件；不要擅自开始产出交付物。
- 逐项拆解，不要一股脑打包；每个候选都要有取舍对比和弱点说明。
- 他否决一个方向后，不要悄悄换个说法把原方向塞回去。
