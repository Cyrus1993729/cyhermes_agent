# 对端 provider 认证失败的死锁：诊断、取舍与交付口径（2026-11-09 实战）

## 症状

cron 守候任务反复报：

```
⚠️ 妈妈机(妈妈)回复未确认修复成功，30分钟后重试。
回复原文: ⚠️ Provider authentication failed. Check the configured credentials;
raw provider details are in the gateway logs.
```

## 一句话定性

**链路全好，对端脑子坏了。** A2A 消息确实送达（`result.status.state` 仍为 `TASK_STATE_COMPLETED`，正文是这句错误），失败发生在**对端 agent 调用模型**那一步，不在传输层。

## 核心判据：2 秒秒拒 ≠ 网络不通

| 现象 | 含义 | 该做什么 |
|---|---|---|
| **2–3 秒**返回 Provider authentication failed | 401/403 型认证失败：连上了、话说了、被拒 | 凭证/账户问题，重试无用 |
| 卡到 90–150 秒才报错 | 网络不通 / 对端离线 | 查网络、查开机 |
| 秒回 `model not found` / 类似 | 模型名在对端已下线 | 改对端模型名 |

本次实测 **2.3 秒**。这个数直接排掉「网络问题」整条分支，别再去 ping 对端浪费一轮。

## 死锁结构（这类问题真正的难点）

```
守候脚本发现对端 IP 变了
  → 通过 A2A 让对端「自己改配置文件」
    → 对端要动手必须先拉起 agent
      → 拉起 agent 必须调模型
        → 模型认证失败
          → 什么都做不成
```

**结论：provider 挂掉的对端，A2A 只能「对话」，不能「干活」——连「读自己的日志然后报给我」都做不到，因为那也是模型调用。别指望远程修它的配置。**

## 排查顺序（按成本从低到高）

### 1. 先确认对端活着（这一步不需要模型）

`GET <peer>/.well-known/agent-card.json`。能取到 card = 进程活着、A2A 平台正常。本次 0.02s 返回。

### 2. 用最小消息拿真实错误

message part 写「只回复两个字：在线」。拿到的是对端的统一报错，**不是具体原因**；具体原因在对端 `gateway.log` 里，而读它需要模型 → 回到死锁。

### 3. 探测备用通道（决定「能不能远程修」）

全端口扫对端（1–1024 + 常用高位）。本次结果只有 **135/139/445/9900** → 没有 SSH(22)、没有 WinRM(5985/5986)、没有额外 HTTP 管理口。

**445 开着 ≠ SMB 可用**，两种错误要分清：

| 报错 | 含义 | 处理 |
|---|---|---|
| **1702** 绑定句柄无效 | 本机 SMB 客户端问题 | 先查 `LanmanWorkstation` / `RpcSs` 服务状态 |
| **67** 找不到网络名 | 对端没开共享 / 共享不可枚举 | 这条路断了，换方案 |

本次本机服务全 Running，所以 67 是**对端没开共享**，不是本机毛病。

- 本机自检：`powershell -NoProfile -Command "Get-Service LanmanWorkstation,LanmanServer,RpcSs"`
- bash 里路径**必须单引号**：`net view '\\192.168.0.110'`。不加引号双反斜杠会被吃掉，`cmd //c "net view \\\\IP"` 也会被 shell 吞参数（只启动 cmd 不执行）。

### 4. 排除「是不是我改配置害的」——时间巧合最唬人

本次对端 11-08 **16:09** 首次报错，本机 config 改于 11-08 **16:05**，只差 4 分钟，看着像因果。

用备份 diff 一次定死：

```python
import difflib
a = open(bak, encoding="utf-8", errors="replace").read().splitlines()
b = open(cur, encoding="utf-8", errors="replace").read().splitlines()
print("\n".join(difflib.unified_diff(a, b, fromfile="bak", tofile="now", lineterm="", n=1)))
```

本次结果只有一行（`a2a_agents.妈妈.url` `.111 → .115`），**没碰任何凭证** → 纯属巧合。

> **时间接近 ≠ 因果。必须 diff 过才敢下「和我无关」的结论**，否则要么误背锅要么漏掉真因。

### 5. 噪音评估：先数，再定性

`cron/output/<job_id>/` 下每轮一个 `.md`。分类统计：

```python
for f in sorted(os.listdir(D)):
    s = open(os.path.join(D,f), encoding="utf-8", errors="replace").read()
    k = "静默" if "silent (empty output)" in s else ("告警" if "⚠️" in s else "其他")
```

本次 **50 份里 48 静默 / 2 告警**——因为脚本有 `should_warn()`「同一句话 24 小时内只报一次」。

**结论：每天最多一条，不是刷屏。** 别在用户还没问的时候先把他吓一跳。同时「最早一条告警的时间」正好定位故障起点（11-08 16:09）。

## 处理选项：必须交给用户，别自己决定

这类问题**没有 agent 能单方面完成的修复**。给三个明确选项：

1. **能摸到机器** → 提供诊断脚本，让用户在目标机上跑，输出贴回来
2. **能远程桌面/向日葵** → 同上 + 手工检查路径（先看 `gateway.log` 里的 provider 原始报错）
3. **都摸不到** → 只做止血：修本机 config 的陈旧 url、把守候降噪或停掉，等能碰到机器再修

### 必须主动算的那笔账：「不修的代价」

本次结论：

- **IP 漂移只影响「两台机自动找对方」**，不影响对端自己上网/自己跑程序，也不影响用户坐在它面前使用
- **provider 挂了反而不烧额度**——对端原本「每分钟拉起一次 AI 会话」的毛病自动停摆
- **噪音每天 ≤1 条**，且纯脚本不调模型

→ 所以「要不要修」取决于**用户还用不用那台机器**，不是技术必要性。原话判据：「这事急不急，取决于你还用不用那台机器。」

## 「IP 现问」方案（用户提出并当场验证可行）

用户问：「不维护 IP，每次要用的时候现去问对端要最新 IP，可行吗？」

**可行，而且本机早就有实现**：`scripts/fix_mama_ip_v2.py` 的 `discover_peer_ip()` —— 扫 `/<24>.1-254` 的 9900 端口（40 线程 / 单连接超时 0.6s），谁应了就取 card 验 `name` 是否匹配。

- 实测 **5–10 秒**，对「用到再查」完全可接受
- **认名字不认 IP**，对端换多少次地址都找得到
- 前提：① 同一局域网 ② 对端开机且 9900 可达（不在一个网里就彻底扑空，不是「找不到 IP」而是「不在一个网」）

🔴 **配套动作：既然改成「用到再找」，那个每 30 分钟的提前修守候就该停掉**——它的存在逻辑是「趁没用到提前修好」，前提没了就只剩噪音。这话要主动说给用户，他会认同。

⚠️ 但它**只解决「找得到」，不解决「干得了」**（provider 仍要上机修）。两个问题必须分开讲，别混成一个。

## 根治：DHCP 静态绑定

对端 IP 反复漂移（本次实测四代：`.108`(state 记的) → `.111` → `.115`(config 里的) → `.110`(真实)）。根因是没做固定分配。

- MAC 从 ARP 拿：`arp -a` 过滤 `192.168.0.`
- 在路由器上按 MAC 绑固定 IP，五分钟，一劳永逸
- ⚠️ `nbtstat -A <IP>` 反查主机名本次「找不到主机」→ **别指望用主机名代替 IP**

## 交付口径（用户当场纠正，硬要求）

用户原话：「现在出了什么问题，请用通俗易懂的语言向我解释」「有必要修吗，或者如果他的ip一直变，会影响什么使用吗？」

- ❌ **第一版回复堆了错误码、MAC、端口、扫描结果** → 被要求重讲一遍。
- ✅ **正确姿势**：
  1. 先一句话说清「谁坏了、坏在哪一层」，用生活化比喻——本次用「人还在工位上、能接电话，但登录系统的工卡失效了，所以只能应声不能干活」
  2. 再给**分层的「影响 / 不影响」清单**（IP 变只影响自动互找，不影响对端自用、不影响你坐在它面前用它）
  3. 最后才上技术依据（秒拒 vs 超时、端口扫描结果）
  4. 建议结尾明确说「急不急取决于你还用不用那台机器」，**把决策权交回用户**
- 用户问「有没有必要修」时，**先算成本和收益再答**，不要直接上手修或直接劝修。他更在意「不管会怎样」而不是「怎么修」。
