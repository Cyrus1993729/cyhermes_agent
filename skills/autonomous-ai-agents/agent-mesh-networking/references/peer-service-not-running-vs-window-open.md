# 对端「窗口开着但服务没起」：gateway 进程 ≠ 桌面客户端（2026-11-09 实测定型）

场景：对端 provider 已经修好（用户上机换了 key + 模型名，它自己那侧验证四个模型全绿），
但本机扫不到 9900，守候一直不通。用户连问两遍：「窗口是开着的」「重启电脑后双击 Hermes 打开桌面客户端是不是就解决」。

## 一、决定性事实：谁在监听 9900

本机实测（可作为任何一台机的判定模板）：

```
Hermes.exe (PID 9404)  父进程 explorer.exe（用户双击启动的壳）
  └─ python -m hermes_cli.main --profile default se[rv…]   ← 桌面端自己拉起的只有这个

python -m hermes_cli.main gateway run (PID 10192 → 真身 10316)
  父进程已退出 → 独立启动，NOT spawned by Hermes.exe
  ** 10316 才是绑 0.0.0.0:9900 的那个进程 **
```

```bash
netstat -ano | grep LISTENING | grep ':9900'
#   TCP  0.0.0.0:9900  0.0.0.0:0  LISTENING  10316
powershell -NoProfile -Command "Get-CimInstance Win32_Process -Filter \"ProcessId=10316\" | Select-Object ProcessId,Name,CommandLine | Format-List"
# CMD: "…\.hermes-runtime\python\…\python.exe" -m hermes_cli.main gateway run
```

**开机自启项里通常没有 hermes**（本机只有 AweSun）→ **重启电脑不会把 gateway 带起来**。

## 二、判据表（照这个三行下结论，别猜）

| 现象 | 结论 |
|:---|:---|
| ping 通 + 135/139/445 通 + **9900 不通** | **gateway 没跑**。不是网络问题、不是防火墙——防火墙是丢 SYN 后超时，这里是**根本没有监听者** |
| 9900 通 + agent-card 正常 | 正常 |
| 9900 通 + agent-card 报错 | 服务在、插件异常，转去看 gateway.log |

全端口扫一遍确认「一个 Hermes 端口都没有」比反复试 9900 更有说服力：
只剩 `135/139/445` 三个 Windows 自带端口 = 整台机上没有 Hermes 在对外服务。

## 三、🔴 「打开客户端」为什么不够 —— 回答口径

用户会用生活语言问（「双击客户端是不是就好了」「是不是要手动重启界面里的 gateway」）。
**第一次就必须讲成两个东西**，别用「服务」这种含糊词带过：

- **Hermes.exe = 壳**（你双击的那个窗口，它只拉 `serve`）
- **`gateway run` = 里子**（真正开 9900 对外接客的进程，要单独启动）

加上「开机自启里没有 hermes」这条，直接把「重启电脑」这个选项也判掉——**重启电脑 + 双击客户端，9900 照样不开**。

## 四、Windows 远程修复通道：三种失败码的含义完全不同（2026-11-09 补全）

此前只记了 1702 / 67。本次补齐最关键的一个：

| 错误 | 含义 | 能否靠它远程修 |
|:---|:---|:---|
| **67 找不到网络名** | 共享服务没启用 / 共享名不存在 | ❌ 不能 |
| **WinError 5 拒绝访问**（Python `os.listdir(r"\\IP\C$")` 直接抛） | **SMB 通了、共享在，只是没有有效凭证** | ✅ **能 —— 只要拿到那台机的账号密码** |
| **1327 用户帐户限制阻止了此用户进行登录**（附「不允许使用空密码」） | 账户是**空密码**，Windows 默认策略禁止空密码远程登录 | ❌ **永远不能**，除非对方先设密码 |

🔴 **1327 的决策价值**：用户说「那台机器我没设密码」时，**别抱着侥幸去试** IPC$ / C$ / ADMIN$ -
这是「限用空密码的本地帐户只允许控制台登录」策略，跟共享配置无关。本会话三个共享全部 1327，白跑一轮。
直接给结论：「必须上机，或者先去设个密码」。

顺带：`net view \\<IP>` 报 **1702 绑定句柄无效** 是**本机** SMB 客户端/RPC 侧的问题，不代表对端。
别把 1702 当成对端拒你——改用 `os.listdir(r"\\IP\C$")` 才能拿到真实的 WinError 5 / 67 / 1327。

## 五、对端 provider 修好之后的正确推进顺序

provider 修好 ≠ 能远控。正确的下一步不是继续猜，而是：

1. **确认对端机器活着**（ping + 135/139/445）→ 活着就排除「没开机」
2. **全端口扫确认 gateway 没跑** → 排除「网络/防火墙」
3. **让用户在对端自证**：对端 provider 已恢复时，**它自己的人机界面是能干活的**。
   把「重启 gateway + 查 9900 + 贴日志」写成一段**可直接复制粘贴的任务书**让用户在那边交给对端，
   比远程逐条指挥快得多（本会话就是这么收尾的）。
4. 实在卡住：让用户设一个 Windows 密码 → 以后走 WinError 5 那条路（远程直接读配置/日志/改文件）

## 六、交付节奏教训

- 这类排障本会话**连跑十几次工具调用才给第一句结论**，用户中途插话「还没收到完整回复」。
  → 每查实一条（机器活着 / 9900 没起 / 空密码被拒）就冒一句 1–3 行，别憋到全查完。
- 用户问「有必要修吗 / 影响什么」时，**先算噪音成本再定性**：cron 的 `no_agent` 脚本不烧额度，
  `should_warn` 有 24 小时去重 → 实测 50 次运行里只有 2 次真告警 = **每天最多一条**。
  别把「每 30 分钟一条」这种没数过的说法甩给用户。
- `--probe` 静默（空输出、exit 0）**本身就是结论**：它表示 `discover_peer_ip()` 没扫到，
  即「对端 A2A 没在监听」，不是脚本坏了。别再去重复跑第二遍。
