# 评估类 sign-off 的 prompt 写法(2026-08-15 Hermes Studio 评估实踩)

## 核心:prompt 显式要求「拒绝附和」

评估类 sign-off(用户要求"同样的问题问 Opus"、装不装决策)的 prompt 输出要求里必须写:

> 不要附和 Hermes 的结论;指出你认为站不住脚的地方;你无法验证的明说,不要假装知道。

效果实测:正是靠这句,Opus 才独立抓到 Hermes 两处遗漏——① 并发写冲突没查(共享工作区+多执行器+@all=两个 Agent 同时改文件,未见文件锁);② "40+ 变更记录、30+ 测试文件"被 Hermes 当质量证据(测试文件数量≠覆盖率,40 commit 对模块是小规模)。若只写"请评估"会得到附和版结论。

## 让 Opus 区分「功能路径」与「信任边界」

prompt 里明确要求 Opus 分开回答两个问题,并声明后者优先:

- **功能路径**(有没有用):机制是否真实、架构本质是什么(本次:Hermes Studio 群聊 = 消息总线+@路由+上下文投影+handoff 状态机,真机制但非"共享大脑")
- **信任边界**(安不安全):第三方持有 API key、真实权限执行命令、Web 控制台、邀请码机制 → "Web 端口没绑死 127.0.0.1 或邀请码弱 = 远程代码执行"结构

## 配套:事实核查分工

Opus 无联网权限 → 它声明"无法验证"的项由 Hermes 回源核实(GitHub API 查仓库/star,读 config.ts/security.ts 证实或证伪担忧),两边做完交付物才可信。详见 SKILL.md 主文件「事实核查分工」条目。

## 交付模板

Opus 核心判断(置信度标注)→ Hermes 一致/分歧(被说服就明说,附双方理由)→ 结论+优先级 → 零成本验证第一步(让用户先验证需求,再承担风险)。
