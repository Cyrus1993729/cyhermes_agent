# Skill 瘦身：按行区间拆分 + 零丢失校验

**触发**：用户说「这个 skill 太肥了 / 加载太贵」，或自己发现某 SKILL.md 超过 20KB（几万字进上下文，之后每次 API 调用都在重复付费）。

**铁律**：用户的原话是「任何内容都不要丢」。所以做法是**原文按行区间整段搬移**，不是重写、不是压缩、不是「我记得大概写了什么」。

---

## 一套可复用的做法

### 1. 先备份，且后续重读源固定为备份

```python
bak = os.path.join(BASE, f"SKILL.md.bak_slim_{stamp}")
shutil.copy2(SKILL, bak)          # copy2 保原始字节（CRLF/编码不动）
SRC = sorted(glob.glob(os.path.join(BASE, "SKILL.md.bak_slim_*")))[0]
orig = io.open(SRC, encoding="utf-8").read()   # ← 之后每次重跑都读这个
```

🔴 **二次执行必须读备份，不能读 SKILL.md**：第一版脚本读的是 `SKILL.md`，改了行区间后重跑时，源文件已经是上一轮瘦身的结果 → 会把瘦身后的文件再切一遍。`SRC` 指向备份后这个坑自动消失。

### 2. 拿分节行号图

```bash
grep -n "^## \|^### " SKILL.md
```

输出形如：
```
8:## 触发条件
29:## 版本门槛
47:## 平台直连路径
67:## 日常使用与诊断
113:### 改名
176:## IP 监控与联动
207:## 安全铁律
276:## 关键事实
```

### 3. 决定「留」与「搬」

| 留在 SKILL.md | 搬进 references |
|---|---|
| 触发条件、路线/选型决策表 | 逐条踩坑史（坑1~坑N） |
| 最小可用命令序列、config 样例 | 一次性实测记录、时间线 |
| 诊断命令速查表 | 超长 runbook、完整输出原文 |
| 安全铁律的**浓缩版**（数行） | 铁律全文 + 历次形态实案 |
| references 索引表 | 跨机分享/迁移类长流程 |

### 4. 按行区间切片，整段搬移

```python
def seg(a, b):                     # 1-based 闭区间
    return "".join(L[a-1:b])

ref1 = """# 标题

> 从 SKILL.md 整段搬移，原文未改。什么时候读：<一句话触发场景>。

""" + seg(29, 66) + "\n" + seg(111, 127)
```

**每份搬出去的 reference 开头必须有一句「什么时候读」**——否则未来不会有人翻它，等于删掉了。

### 5. 新 SKILL.md = 保留段 + 手写浓缩块 + 索引表

索引表每行三列：`文件名 | 内容一句话 | 什么时候读`。这是瘦身后**唯一**能把人导回细节的东西。

### 6. 🔴 零丢失校验（这一步才是这个方法的全部价值）

```python
allnew = new + "".join(io.open(os.path.join(REF, f), encoding="utf-8").read() for f in ref_names)
orig_lines = [l.strip() for l in orig.splitlines() if l.strip()]
newset = set(l.strip() for l in allnew.splitlines() if l.strip())
missing = [l for l in orig_lines if l not in newset]
print(f"原文非空行 {len(orig_lines)}，缺失 {len(missing)}")
for m in missing[:10]:
    print("  MISSING:", m[:120])
```

**缺失必须为 0 才能收工。** 再加一道交叉校验：挑一个特征串（本次是 `grep -c "坑[0-9]"`）数原文与拆分后的合计，两者应相等。

---

## 实测结果（2026-10-20，agent-mesh-networking）

| 指标 | 瘦身前 | 瘦身后 |
|---|---|---|
| SKILL.md | 60,789 B / 285 行 | **10,058 B / 135 行（-83%）** |
| 搬出的 reference | — | 4 份，合计约 55KB |
| 非空行覆盖 | 222 | 缺失 **0** |
| 特征串交叉校验 | 含「坑N」24 行 | 拆分后合计 **24** 行 |

效果：加载这个 skill 从 6 万字节降到 1 万，每次 API 调用省约 1.5–2 万 token 的过路费；真遇到细节场景再按索引翻厚的那几份。

---

## 坑

1. 🔴 **第一次跑就漏了整整一节（17 行）**：按标题行号切分时，「平台直连路径」这一节（47–66）既没进保留段、也没进任何 reference——因为保留段从 67 行标题开始切，而 ref1 只切了 29–46。**没有校验的话，这次瘦身会静默丢掉一整节操作步骤**，而且跑完看不出来。
   - 修正方式就是把 ref1 改成 `seg(29, 66)`，源固定为备份后重跑一次。
   - 教训：**分节边界要拿 `grep -n` 的输出逐段核对「这个区间落在哪个文件里」，别凭感觉**。
2. **`grep -c` 的计数会分散到多个文件**：拆分后单看某个文件的计数会变少，要看**合计**。
3. **标题行的归属最容易漏**：`seg(67,109)` 与 `seg(69,109)` 差的就是那个 `## 标题`。校验会以「MISSING: ## XXX」的形式直接点名。
4. **CRLF 会被吃掉**：`io.open(...).read()` 走通用换行，再写回就变 LF。markdown 无影响；若原文件对换行敏感，要 `newline=""` 且用二进制比对。
5. **备份文件别堆**：重跑会再生成一份 `.bak_slim_<新时间戳>`，其中可能只是上一次瘦身的结果。收尾时删掉非原始那份，只留最老的一个备份。
