# 第三方工具/项目采用评估

## 触发条件

- 用户看到第三方工具/AI 应用/开源项目（小红书/推特/GitHub 推荐），问「要不要下载/安装/用」
- 工具持有 API key、能执行命令/改文件、开 Web 控制台等敏感面时**必须**走本流程
- 结论可以是「不装」——评估的目标是正确决策，不是促成安装

## 核心原则（2026-08-15 Hermes Studio 评估沉淀）

1. **功能路径 vs 信任边界是两个独立问题，后者优先**。先问「安不安全」再问「有没有用」。功能读 README/源码即可；信任边界必须查：认证模块、默认监听地址、默认凭据、沙箱、外部可接入面（邀请码/端口/共享链接）
2. **读源码验证机制，不信宣传话术**。README 的 bullet 是营销；机制要看实现：执行器是否真实（如群聊的 agent 类型 hermes/codex/claude）、状态管理是否完整（重试/租约/幂等）
3. **弱证据清单**（数量≠质量）：
   - 测试文件数量/commit 数量 → 说明不了覆盖率或有效性
   - star 数（非官方项目）→ 可刷，可疑信号不是可信信号
   - 演示视频/小红书推荐 → 推广话术的形状
4. **身份核实**：先确认仓库真实存在（GitHub API：stars/topics/README），再确认官方 vs 第三方——蹭知名品牌名（如 Hermes）需要多一分警惕
5. **默认配置安全检查**（评估下载决策必查项）：
   - `BIND_HOST`/listen 默认是 127.0.0.1 还是 0.0.0.0（后者=局域网暴露）
   - 默认凭据（admin/123456 类）
   - 认证是否可关闭、CORS 默认策略
   - 是否持有用户全部 API key + 有真实命令执行权限 + 有外部真人可加入面 = 五属性叠加 RCE 结构

## 流程

1. **功能验证**：源码/README + GitHub API 核实 + 关键机制读实现（不读实现不下"是真机制"结论）
2. **信任边界**：查认证/监听/凭据/沙箱/外部接入面（见核心原则 5）
3. **增量清单**：区分「真实增量」和「听起来厉害但用不上」（对照用户实际工作流，一条条过）
4. **双模型 sign-off**：技术/投资方案须外部大模型（Opus 优先）独立评估——喂足背景（用户画像+内容+自己的发现+明确要求批判不附和），见 `opus-deep-thinking` skill
5. **交付双视角**：Opus 核心判断 / 自己判断（一致/分歧，被说服就明说）/ 结论+优先级 / 最小风险验证路径
6. **不装也给出零成本替代验证路径**（如「把管线中间输出推 Telegram 两周验证需求」），需求证实才承担风险

## 最小风险安装路径（若验证为真才执行）

- 隔离环境（VM/容器），不装主力机
- 额度上限的子 API key，不放主力 key
- 不启用邀请/共享功能；`BIND_HOST=127.0.0.1` 显式绑定
- 工作目录指向空目录
- 先只用核心功能（如 Web UI）跑两周，高级功能（如群聊）后开

## 坑

- 只读功能路径（mention-routing/relay 类）就下结论 = 漏掉信任边界。评估「要不要装」，先读 auth/security/config
- 引用「测试文件 30+、commit 40+」当质量证据 = 弱证据当强证据（Opus 实踩批评）
- 双模型 sign-off 时，自己的分析要主动标注哪些是核实哪些是推断（Opus 会基于你的转述判断，它会明确说明无法验证的部分）
- 名称确认：封面 OCR/ASR 都可能读错产品名（Holmes vs Hermes），用帧内运行时自述+GitHub API 双重确认（见 `xiaohongshu-analysis` skill）
