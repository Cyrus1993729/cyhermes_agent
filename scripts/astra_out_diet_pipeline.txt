# 求助：中餐照片营养核算流水线的架构评审

我在给一位中国用户（男，33 岁，减脂+血脂管理）搭一套「拍食物照片 → 自动算营养素」的离线流水线。
现在卡在一个架构问题上，想请你判断思路对不对，以及正确的做法应该是什么。

**你可以否定我的设计。** 我需要的是批判性判断，不是认可。数据如果和我说的对不上，直接指出来。

---

## 一、用户诉求（决定成败的约束）

1. **零操作、零坚持**。用户明确拒绝任何需要"持续手动记录/录入/整理"的方案（血压自测、逐日饮食记录、穿戴数据导出，全部当面否决过）。
2. **确认边界极窄**。用户原话："我只想负责核实这个，我不想我又不是厨师，我哪知道厨师放了多少颗糖，我咋给你核？"
   → 他**只愿意核对**：这道菜**叫什么**、这一碟**大概多重**。
   → 他**拒绝核对**：放了多少糖/油/酱油、生重熟重、可食部比例。
3. **不花钱**。否决了薄荷健康 365 元/年会员（其图片识别被划进企业会员、需商务报价）。
4. 用户对**成本/精度类论断会凭直觉质疑，且往往正确**；会揪出分析里的牵强归因。

## 二、现有架构（已落地并跑通）

```
① 手机拍餐食照片
      ↓
② 多模态模型识图（opencode 网关的 minimax-m3）
   一次输出 JSON，含两部分：
   ├─ dishes：[{name 菜名, gross_g 整碟毛重, method 做法, vessel 容器}]
   └─ items ：[{name 食材名, raw_g 毛重, edible_g 可食重, state 生熟, confidence, basis}]
      ↓
③ 把 dishes 发给用户，只问一句：「菜名对不对 + 这一碟多少克」
   （卡片示例：`香菜炒牛肉 —— 约 200g（蓝白条纹碗，整碗连汤汁约200g）`）
      ↓
④ 用户回「对」或「牛肉175g、饭90g」→ 程序按下发修正
   （改菜名 / 按做法查油量表 / 按整碟重量等比校准所有原料）
      ↓
⑤ 每样食材查《中国食物成分表》第6版（**本地库 2393 条，含中国疾控中心官方源**）
   → 蛋白/脂肪/碳水/热量/嘌呤
      ↓
⑥ 出报告
```

**关键点：第②步里，模型一次性做完「识别菜名」和「拆成原料」两件事。拆解是模型凭训练常识做的，没有联网、没有菜谱库。**

## 三、我踩过的坑（都是实测，不是推测）

### 坑 1：用油量高估 4 倍

模型对「凉拌牛肉」给了 12g 油（豆油 8g + 辣椒油 4g），**用户实测只放了 3g**。

我的诊断：提示词原本让模型"看照片上的油光估油量"，而**油光和用油量基本无关甚至反向**——
凉拌菜淋 3g 就油亮，炒菜下锅 15g 菜上反而看不到油。

**已改**：模型不再估油，只标「做法」（凉拌/清蒸白灼/少油快炒/家常炒/红烧糖醋/干煸油炸/水煮麻辣/煮汤炖），
程序按做法查表给油量（凉拌 3g、清蒸 2g、少油快炒 6g、家常炒 10g、红烧 18g、油炸 30g）；
用户纠正一次就写入 `oil_profile.json` 的用户校准区，以后同类做法沿用。

### 坑 2：菜名不稳定（同一张图三次三个名字）

凉拌生菜 → 炒生菜 → 生菜。我一开始以为是模型采样随机，查下来是**我自己把 `max_tokens` 设成 3000**，
而 minimax-m3 会先输出上万字符的 think 块，JSON 被截断 → 解析失败 → 静默降级到别的模型 → 不同模型判断不同。
改成 8000 后三次全稳（菜名+做法都一致）。

**教训**：菜名摇摆会连锁——菜名变 → 做法判断变 → 油量从 3g 变 10g。

### 坑 3：复合菜在成分表里不存在

《中国食物成分表》只有食材（番茄、鸡蛋、猪五花肉），**没有「番茄炒蛋」「红烧肉」这种复合菜**。
所以必须拆成原料再查表。库里有 2393 条，但全是基础品类 + 极少数熟食单品（叉烧肉、烧鹅、卤驴肉）。

**实测确认库里没有**：宫保鸡丁、鱼香肉丝、糖醋里脊、糖醋排骨……一律查不到。

### 坑 4：模糊匹配会静默给错数字

菜名直接丢库会命中错误的条目，而且不报错：
- 「红烧肉」→ 叉烧肉 196 kcal（应为 400+）
- 「番茄炒蛋」→ 番茄酱 86 kcal
- 「紫米饭」→ 糯米饭团 333 kcal / 脂肪 17.6g（应为 ~116 kcal / 0.3g）

**已加**：模糊匹配告警 + 加工品纠偏表 + 菜名别名表（2393 条库启动自检，0 失效映射）。

## 四、核心问题（要请你判断的）

**用户的原话（这是本次求助的起因）：**

> "这里边有个问题就是大依靠大模型现有的常识来算，那有没有可能某个菜名大模型现在的常识里他没有这个东西，
> 没有这道菜，那不就是会不会出现这种问题。如果会的话，那这道菜不就出 bug 了？识别不了了，只能瞎猜了。
> **我希望可以有一个相对固定的程序，让大模型知道第一步怎么做、第 2 步怎么做、第 3 步怎么做，
> 这样的话就是误差可能还是会有，但是起码流程是相对确定的。**"

### 我做的实测（纯文本给菜名，让模型拆成原料）

```
宫保鸡丁      ✅ 认识（川菜，标准做法）
擂椒皮蛋      ✅ 认识（湘菜：皮蛋+烧焦的辣椒+蒜+酱油+醋+油）
秃黄油拌饭    ✅ 认识（苏州菜：蟹黄蟹膏+猪油）
撒撇          ✅ 认识（云南傣族，能说出「苦撒用牛胆汁 / 柠檬撒」两种分支）
凤凰盏        ⚠️ "could refer to a few things... I cannot accurately determine"
轻食鸡胸肉沙拉 ✅ 认识
```

**结论 1**：覆盖度比我预期高（连极冷门的地方菜都认识）。
**结论 2**：不认识时它倾向说"不确定"，不是硬编。
**结论 3**：拆解根本不需要图片（模型原话："no image was provided，但我能基于菜名拆"）——它在做「菜名 → 原料」的知识检索。

### 我目前想到的（但不确定对不对）的改进方向

**方向 A：把"生成数字"改成"做选择题"**
现在模型是自由生成（"凉拌菜大概放 8g 油"）——不可复现、不可检查。
改成让模型只做分类（"这道菜是【炒】还是【拌】"、【猪】还是【牛】），数字由程序查表给。

**方向 B：菜品模板库**
用户确认过一次的菜，存成固定配方（`dish_templates.json`），下次零模型参与 → 完全复现。
这是用户早前提过的"联网搜菜谱"的本地方案。

**方向 C：菜型 × 主料 二维网格兜底**
即使不认识「撒撇」，也能判出它是"凉拌 + 牛杂"→ 按格子里的先验配比给。
9 种做法 × 12 类主料 = 108 格，模型总能填进一格，不会崩。

**方向 D：提示词里加「第 0 步：先判断认不认识」**
`known: certain / variant / guess / unknown`，unknown 时明确要求"不要编"+ 压低置信度。

**我实测发现"联网查菜谱"帮不上忙**：同一道凉拌牛肉的菜谱油量从 1g 到 50g（差 50 倍）；
《中国居民膳食指南》推荐每日烹调油 25–30g，但实际人均摄入 43.2g。菜谱记录的是"某个厨师的某个做法"，方差比模型猜测还大。
